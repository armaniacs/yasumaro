# PBI: webhook送信先の専用許可リストと保存時pre-flight

## ユーザーストーリー
webhookを使う利用者として、保存の時点で宛先が送れるかどうかを知りたい、なぜなら「保存成功」を信じたまま送信時に無音遮断され、記録が消えたと誤認する事故を防ぎたいから。

## ビジネス価値
- 保存時に宛先の有効性が分かり、保存成功と送信可否の矛盾をなくす
- 用途別に許可集合を独立管理し、他用途の宣言追加で勝手に広がらない
- 既存宛先は無効化されず、更新で設定が無音に壊れない
- 測定方法: 保存時pre-flightの許可・非許可シナリオが緑で、初期集合が宣言origin集合と一致することがpinで確認できること

## BDD受け入れシナリオ

```gherkin
Scenario: 既存の許可宛先は保存でも許可される
  Given 専用リストの初期集合に既存の宣言originが含まれている
  When 利用者が許可されるURLを入力して保存する
  Then 保存は成功し宛先が許可と表示される
  And 保存時の表示と送信時の判定が一致する

Scenario: リスト外の宛先は理由付きで拒否される
  Given 許可リスト外のoriginのURLが入力されている
  When 利用者が保存を実行する
  Then 保存は拒否され理由が表示される
  And 送信が試行されないためblocked履歴が残らない
```

## 受け入れ基準
- [ ] 専用リストが新設され、初期集合が宣言origin集合と一致する
- [ ] 既存宛先は無効化されず引き続き送信できる
- [ ] 保存時と送信時が同じ基準で検証され、非許可宛先は理由付きで拒否される
- [ ] https以外は新規保存のみ拒否され、既存宛先は祖父条項で維持される
- [ ] 保存UIに有効性が日英で表示され、URL全文は表示しない
- [ ] READMEとPRIVACYに初期集合の扱いが明記される
- [ ] manifestへの新規権限追加は行わない

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 日英UI両方での保存許可と理由付き拒否の利用者シナリオ

### 統合テスト
- 保存と送信の同一基準の共有確認
- 祖父条項の維持確認

### 単体テスト
- 許可・非許可の表駆動テスト
- 初期集合のpinテスト

M （要チームでの見積もり）

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 保存と送信の判定源を共有し、pinで固定する
- 非機能要件: 秘匿に配慮し、理由表示はorigin単位にする
- ロールバック手段: 専用リストを無効化すれば現行判定に戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -rn "webhook" src/dashboard --include="*.ts" -l | grep -v __tests__ | head -5
```

確認結果:
- 専用リストは未実装。送信時判定は宣言全体の流用
- 参照実装が `feature/carried-over-candidates` にある（初期集合31パターン・祖父条項の方針を参照せよ。現行mainの宣言集合と一致するか再実測すること）

### 実装手順
1. Outside-Inで保存許可と拒否の失敗試験から書く
2. 専用リストを新設し、初期集合を宣言origin集合に合わせる
3. 保存時に同一基準の検証を走らせ、日英で表示する
4. READMEとPRIVACY（2ファイル同一）に扱いを明記する

### 落とし穴
- 既存宛先を無効化しないこと。祖父条項を守る
- token入りのURL全文を表示しないこと
- 保存と送信で判定源を分けないこと
