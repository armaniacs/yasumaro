# PBI: utils 層分類リストを一元化し文書とルールのドリフトを検出する

優先度: 順位 4 / 4（RICE: 2.4 = Reach 6 / Impact 1 / Confidence 0.8 / Effort 2 pt。全候補5件中5位・1位は台帳清掃）
backlog: [2026-09-17-00-backlog-arch-review-0917b.md](2026-09-17-00-backlog-arch-review-0917b.md)（台帳）
依存: なし（PBI 05 完了済みが前提）

## ユーザーストーリー

拡張機能を保守する開発者として、層境界ルールの層ファイルリストと `dev-docs/LAYERS.md` の分類表の差異を機械的に検出してほしい、なぜなら現状は二重管理で人力照合に頼っており、分類表の陳腐化が境界違反の不可視化につながるから。

---

## 背景（現状と課題）

層境界ルール `local/utils-layer-boundary`（`eslint/rules/utils-layer-boundary.mjs` の冒頭付近で定義される `LAYER0_FILES` / `LAYER1_FILES` / `LAYER2_MODULES`）が層ファイルリストの SSOT とされ、`dev-docs/LAYERS.md` の分類表は文書として対応関係を記述している。`LAYERS.md` の機械検査節には「両者に差異を見つけたら分類表・ルールのどちらが正しいかを判断し、揃えること」の規定があるが、機械検査は存在せず人力照合に頼る。

構造的な差もある。`LAYERS.md` の `^src/utils` 記載は58行、ルールのリストは46エントリである。文書側には未分類・対象外ファイルが含まれるため正当な差だが、正当な差とドリフトを区別する手段がない。分類表が陳腐化するとルールは「リストに無いファイル」を検査できず、境界違反が不可視化される。これは PBI 05 が防ごうとした病の再発経路である。

既知の暫定許可として、`eslint.config.js` のルール配線付近に `storage/defaults.ts` から `aiSummaryCleaner/rules.js` への暫定許可が1件ある。純粋定数抽出か再分類かの判断を ADR に起こすことが、`eslint.config.js` のコメントと `LAYERS.md` の機械検査節の既知の暫定許可項に付帯事項として指定されている。

対応方針は、着手時に案A（単一マップ）か案B（軽量検査スクリプト）かを判断し、理由を本 PBI に記録すること。いずれの案でも、上記暫定許可の ADR 起票をスコープに含める。

スコープ外: 物理的な再階層化（ディレクトリ移動）と Layer 1 の厳密化（「Layer 0 以外への静的 import 禁止」への拡張）。後者は `LAYERS.md` の未分類・後続対応項に記載の通り、分類の完了後に検討する。

## BDD受け入れシナリオ

```gherkin
Scenario: ルールと文書の差異は機械的に報告される
  Given ルールのリストに登録されたファイル
  When LAYERS.md からその記載を削除する（または逆方向にルールから削除する）
  Then lint:layers-docs（または生成・検証機構）が差異を報告する

Scenario: 未分類・対象外の正当な差は偽陽性にならない
  Given 未分類・対象外の正当な差（LAYERS.md の未分類・後続対応項に記載のファイル群など）
  When 検査を実行する
  Then 許可リストまたは明示マーキングにより偽陽性にならない

Scenario: 暫定許可は ADR で裁定される
  Given storage/defaults.ts から aiSummaryCleaner/rules.js への暫定許可
  When 本 PBI を完了する
  Then dev-docs/ADR/ 配下に判断（純粋定数の抽出か再分類か）を記録した ADR が存在し、lint:adr-links が PASS する
```

## 受け入れ基準

- [ ] ルールの層ファイルリストと `LAYERS.md` 分類表の差異を検出する仕組み（案Aの生成・検証機構または案Bの `lint:layers-docs` スクリプト）が存在する
- [ ] 未分類・対象外の正当な差が許可リストまたは明示マーキングで区別され、検査が偽陽性にならない
- [ ] `defaults.ts` から `aiSummaryCleaner/rules.js` への暫定許可について、純粋定数抽出か再分類かの判断を記録した ADR が `dev-docs/ADR/` 配下に存在し、`lint:adr-links` が PASS する
- [ ] 実装方式（案A vs 案B）の選択と理由が本 PBI に記録されている
- [ ] `package.json` への npm スクリプト追加と CI（`npm run validate` 等）への組み込み可否の判断が記録され、組み込む場合は配線済みである
- [ ] `npm run lint` が green であり、既存の層境界ルールのテストが壊れていない

## テスト戦略

- 案Bの場合、`scripts/lint-adr-links.mjs` の慣習に倣う。すなわち Node 標準のみのスクリプトとして `scripts/` 配下に配置し、差異があれば非ゼロ終了＋件数を標準エラー出力、差異がなければ成功メッセージを出してゼロ終了する
- 検知シナリオは一時的な fixture（一時ディレクトリに切り出したルールリストと文書抜粋、または実ファイルの一時改変）で検証し、正方向・逆方向の両方で差異報告を確認する。実ファイルの一時改変を使う場合はテスト後に必ず復元する
- 境界シナリオは未分類・対象外の代表例（`LAYERS.md` の未分類・後続対応項に記載のファイル群）を含めて検査を実行し、偽陽性が出ないことを確認する
- 層境界ルール自体の回帰として、`eslint/__tests__/` 配下の RuleTester テスト（違反パターンと許可パターンの両持ち）が green であることを確認する
- ADR 起票後は `npm run lint:adr-links` が PASS することを確認する

## 実装ガイド（着手時の調査・設計手順）

### 確認ポイント（着手前に読む）

- `eslint/rules/utils-layer-boundary.mjs` 全体（冒頭付近の `LAYER0_FILES` / `LAYER1_FILES` / `LAYER2_MODULES` 定義、`matchesAny` による接尾辞照合、`create` 内の `ImportDeclaration` フック）
- `eslint/__tests__/utils-layer-boundary.test.ts`（違反パターンと許可パターンの両持ち、`UNLISTED_FILE` による対象外の pin、暫定許可の pin 状況）
- `dev-docs/LAYERS.md` の機械検査節（SSOT の宣言、既知の暫定許可、未分類・後続対応の各項）と各 Layer セクションの分類表
- `scripts/lint-adr-links.mjs`（スクリプト慣習の参照。ADR ディレクトリ走査・非ゼロ終了の書き方）
- `eslint.config.js` のルール配線付近の許可エントリ（暫定許可1件の `from` / `to` / `reason`）

### 案A/B の判断基準

- 案A（単一マップ）を選ぶ条件: 分類の正本を1つの JSON/TS マップに集約し、ルールと `LAYERS.md` の生成・検証の両方に使うことで、二重管理そのものを消したい場合。分類の追加・移動が今後も頻繁に発生する見込みがあり、マップ駆動の生成に耐える分類の安定度がある場合に適する。反面、ルール（ESLint 実行時）と文書生成の両方がマップに依存するため、移行時の整合性確保と既存テストの更新が必要になる
- 案B（軽量）を選ぶ条件: 現状の二重管理は残したまま、ドリフトの早期検出だけを低コストで実現したい場合。`lint-adr-links.mjs` の慣習に倣った照合スクリプトで、ルールの各エントリが `LAYERS.md` の正しい見出し配下に存在することを検査する。反面、二重管理自体は残るため、分類更新時の二箇所編集は引き続き必要になる
- いずれを選んでも、選定理由（上記の観点での比較結果）を本 PBI の受け入れ基準「実装方式の選択と理由」に残すこと
- いずれの案でも、`package.json` に npm スクリプトを追加し、CI（`npm run validate` 等）への組み込み可否を判断して記録すること。組み込まない場合は理由（実行コスト・誤検出率など）を残すこと

### 暫定許可の ADR 起票手順

- `eslint.config.js` の許可エントリの `reason` と `LAYERS.md` の既知の暫定許可項を起点に、純粋定数の抽出か再分類かを検討する
- ADR は `dev-docs/ADR/` 配下に作成し、`lint:adr-links` が PASS すること（`## Implements` 節を書く場合は実在パスを記載する）
- ADR で再分類と判断した場合は、ルールのリストと `LAYERS.md` の分類表の両方を揃え、本 PBI の検査機構でも差異が出ないことを確認する
