# PBI: Obsidian If-Match競合検出と412明示分岐

## ユーザーストーリー
Obsidianに保存する利用者として、競合を検出して知らせてほしい、なぜなら競合時に「保存成功」と表示されたまま記録が無音で失われることがあり、最も取り返しがつかないデータ損失だから。

## ビジネス価値
- 競合による無音データ損失を検出可能な412に変える
- 実行時検出により対応環境だけ有効化し、非対応環境の誤発火を避ける
- 測定方法: 412競合時に再取得後1回上限の再書き込みで完了し、非対応環境で現行動作が維持されること

## BDD受け入れシナリオ

```gherkin
Scenario: 競合を412として検出し再取得後1回の再書き込みで解決する
  Given ETag対応が実行時検出で確認されている
  And 同時編集が重なり書き込みが競合している
  When If-Match付きの保存を行う
  Then 412が競合として記録される
  And 再取得後に1回だけ再書き込みして記録を完了する

Scenario: 再書き込みでも競合が続く場合は1回で止まる
  Given If-Match対応が確認されている
  And 再書き込みでも412が返り続ける
  When 解決を試みる
  Then 再書き込みは1回で止まり競合として残る
  And 24時間失効だけで黙って消えない

Scenario: ETagを返さない環境では現行動作を維持する
  Given ETagが無いことが検出で分かっている
  When 保存する
  Then If-Matchなしのまま保存され412分岐は発火しない
```

## 受け入れ基準
- [ ] If-Match対応を実行時検出する（バージョン決め打ちなし）
- [ ] 対応環境ではIf-Match付きPUT、非対応環境では現行動作になる
- [ ] 412が競合として明示される（通知・履歴・理由で追跡可能）
- [ ] 再取得後1回上限の再書き込みが行われ、2回目以降は再試行しない
- [ ] unsafe系の同時再送禁止は緩和されない
- [ ] 24時間失効だけで黙って消える経路が無い
- [ ] pinテストが実装と同一コミットに含まれる

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- ETagと412を返す互換サーバでの保存フロー検証
- ETagなしスタブでの現行動作維持の確認

### 統合テスト
- 検出結果の配線検証
- 412時の再取得と1回再書き込みの経路確認

### 単体テスト
- 412分類と再書き込み許可条件の表駆動テスト
- 再送契約維持の表駆動テスト
- 弱いETag形式の不一致テスト

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 検出と判定を表駆動でpinする。実Obsidian確認は手動項目に分離する
- 非機能要件: 再書き込みはpipeline層に固定し、再送契約は変えない
- ロールバック手段: If-Match付きPUTを無効化すれば現行動作に戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -rn "If-Match\|ETag" src/ --include="*.ts" | grep -v __tests__ | head -5
```

確認結果:
- If-MatchとETagの使用実績はゼロで未実装
- 参照実装が `feature/carried-over-candidates` にある（検出手段・412分岐・再書き込み条件の方針を参照せよ。現行mainに合わせること）

### 実装手順
1. 実行時検出の失敗試験から書く（バージョン決め打ちなし）
2. 412の分類と明示を追加する
3. 再取得後1回上限の再書き込みをpipeline層に入れる
4. pinテストを同一コミットに含める

### 落とし穴
- 再書き込みは再取得後に1回だけにすること
- unsafe系の再送契約を緩めないこと
- 弱いETagの扱いを外さないこと
- 実Obsidian確認は手動項目として残すこと（偽陽性はfail-openに相当）
