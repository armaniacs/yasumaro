# PBI: ログ出力の機密性分類ポリシーの策定

## ユーザーストーリー

開発者として、ログ出力時に機密情報を適切に扱うためのポリシーがほしい。なぜなら、どの情報が機密で、どのようにマスクすべきかの基準がなく、OAuthトークン漏洩のようなインシデントが再発するリスクがあるから。

## ビジネス価値

- 機密情報のログ漏洩を未然に防止
- ログ監査時のコンプライアンス対応を簡素化
- 開発者の判断負荷を低減

## BDD受け入れシナリオ

```gherkin
Scenario: 開発者がログ出力コードを書く際にポリシーが参照される
  Given 開発者がエラーレスポンスをログ出力するコードを書く
  When コードレビューが行われる
  Then ポリシーに基づいて機密情報のマスクが検証される
  And マスク漏れがあれば指摘される

Scenario: 既存のログがポリシーに準拠しているか監査できる
  Given 本番環境のログが存在する
  When 定期監査が実施される
  Then ポリシーに基づいて機密情報の露出がチェックされる
  And 違反があれば修正チケットが作成される
```

## 受け入れ基準

- [ ] `docs/LOG_SENSITIVITY_POLICY.md` が作成されている
- [ ] 以下の機密レベルが定義されている:
  - [ ] **Level 1 (Secret)**: APIキー、トークン、パスワード、秘密鍵 → 絶対出力禁止
  - [ ] **Level 2 (Confidential)**: ユーザーID、メールアドレス、IPアドレス → マスク必須
  - [ ] **Level 3 (Internal)**: リクエストID、セッションID → 状況に応じてマスク
  - [ ] **Level 4 (Public)**: ステータスコード、タイムスタンプ → 出力可能
- [ ] 各レベルに対してマスク方法（例: `***`、ハッシュ化、部分表示）が定義されている
- [ ] 具体的なコード例（マスク関数の実装）が含まれている
- [ ] ESLintルールまたは静的解析での検出方法が検討されている

## テスト戦略（t_wadaスタイル）

### ドキュメントレビュー
- セキュリティ専門家がポリシーをレビュー
- 既存のインシデントがポリシーで防止可能か検証

### 実装検証
- マスク関数の単体テスト
- 既存コードへの適用テスト

## 実装アプローチ

- **Outside-In**: 過去のインシデントから必要な機密レベルを逆算
- **Red-Green-Refactor**: マスク関数を実装し、テストで検証

## 技術的考慮事項

- 作成場所: `docs/LOG_SENSITIVITY_POLICY.md`
- マスク関数の実装場所: `src/utils/logger.ts` または新規モジュール
- 既存のログ出力コードへの影響範囲を調査する必要あり

## 実装者向け注記

### 実装手順
1. 過去のインシデント（OAuthトークン漏洩等）を洗い出す
2. 機密情報の種類とレベルを分類
3. 各レベルに対するマスク方法を定義
4. マスク関数を実装（オプション）
5. 既存コードへの適用方針を決定

### 落とし穴
- ポリシーが厳しすぎると開発者が回避する
- マスク関数のパフォーマンスオーバーヘッド
- 外部ライブラリのログ出力は制御困難

## Definition of Done

- [ ] ポリシーが作成され、チームに共有されている
- [ ] マスク関数が実装され、テストで検証されている
- [ ] 既存のログ出力コード至少くとも1つに適用し、有効性を確認
