# PBI: piiSanitizer タイミング flake の処置

## ユーザーストーリー
開発者として、piiSanitizer の性能回帰テストを負荷時にも安定させたい。なぜなら、フルスイート負荷時に 500ms 閾値を 518ms で超過して赤になり、リリース CI を止めうるから

## ビジネス価値
- リリースゲート（`npm run validate`）の誤赤をなくし、6.9.77 リリースを止めない
- バックトラッキング保護の回帰検出力は維持する（テストの削除はしない）

## BDD受け入れシナリオ

```gherkin
Scenario: 負荷時にもタイミングテストが緑になる
  Given フルスイート実行中の高負荷状態
  When   separator-less extra-long digit テストを実行する
  Then   閾値内に収まるか、負荷に依存しない判定方式で評価される

Scenario: 性能回帰は依然として検出される
  Given バックトラッキング保護を外した実装（意図的劣化）
  When   同テストを実行する
  Then   失敗として検出される（検出力の喪失なし）
```

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- なし（単体レベルのタイミング判定）

### 統合テスト
- フルスイートでの緑確認（負荷時の安定性）

### 単体テスト
- 閾値テスト自体（分布測定つき）
- 劣化版での赤確認（検出力の証明）

比率: E2E:統合:単体 = 0:1:10

## 実装アプローチ
- **Outside-In**: 現行テストの失敗条件（負荷時の分布）を先に測定 → 方針決定 → 修正 → グリーン
- **Red-Green-Refactor**: 劣化版で赤→修正版で緑を確認

## 見積もり
1 ストーリーポイント（要チームでの見積もり。分布測定が主体）

## 技術的考慮事項
- 依存関係: なし（単体テストの閾値のみ）
- テスタビリティ: 経過時間の分布を複数回測定し、中央値＋マージンで閾値を決める
- 非機能要件: `dev-docs/TEST_RULE.md`（実時間待ちの禁止と代替手段）に沿うこと。安易な `sleep` 追加やテスト削除はしない

## 実装者向け注記

### 現状コードの確認
（着手前に必ず実行すること）
```bash
# 対象テストの確認
grep -n "toBeLessThan(500)" src/utils/__tests__/piiSanitizer.test.ts
# 単独実行で緑であることの確認（差分無関係の flake である根拠）
npx vitest run src/utils/__tests__/piiSanitizer.test.ts
```

確認済み（2026-11-22）: 対象ファイルに差分なし。単独実行で 75/75 緑。フルスイート負荷時のみ 518ms で失敗した実績あり。

### 実装手順
1. 当該テストを N 回（目安10回）実行し、経過時間の分布（中央値・最大値）を記録する
2. 分布に基づき方針を確定する（例: 閾値を P99＋余裕に緩和／リトライ付き判定／非ゲート化）
3. 方針どおりにテストを更新し、フル `npm run validate` で緑を確認する
4. 保護を外した劣化版で赤になることを確認し、検出力の証跡を残す

### 落とし穴
- テストを削除・skip するとバックトラッキング回帰を見逃す。検出力の維持が必須条件
- 閾値緩和は根拠（分布データ）なしに行わない
- CI 環境とローカルの速度差を考慮し、ローカルの余裕だけで決めない
