# PBI: CI環境でのみ失敗するドメインフィルタ保存フローE2Eの解消

## ユーザーストーリー
開発者として、`test` / `usability` CIジョブが緑になることがほしい。なぜなら、赤が常態化すると回帰検知のシグナルが失われ、新規バグの混入に気づけなくなるから

## 優先度
- 順位: 1 / 全3候補（2026-09-19 リリース後残課題。台帳: `pbi/2026-09-19-00-backlog-post-v699.md`）
- RICEスコア: 45（Reach=15 / Impact=1.5 / Confidence=1.0 / Effort=0.5人週）
- 根拠: 失敗はPR #150マージ時から継続しており、CIの赤が常態化してマージ判断のシグナルを失っている。全PRのCI実行ごとに影響し、修正によって他候補のパリティゲート監視も含むCI全体の信頼性が回復する

## 状況
- 失敗テスト: `testDir/e2e/usability/dashboard-task-flows.spec.ts`「Dashboard settings task completion @extension › user adds a domain filter, saves, and it survives a reload」
- CI（ubuntu headless + xvfb）で3リトライ全滅（17-18秒、`expect(locator).toBeVisible()` 失敗）。ローカル（macOS headed）では未検証
- 同一失敗はPR #150でも発生しておりpre-existing。CIの失敗アーティファクト（スクリーンショット等）は取得済み
- 参考: 6.8.20で同種の「ドメインフィルタ保存直後リロードで設定が反映されない」タイミング問題を修正済み。同クラスの未修正経路か、CI環境固有（xvfb描画・タイムゾーン等）の可能性

## BDD受け入れシナリオ
Scenario: CI環境でドメインフィルタ保存フローが完了する
  Given CI（ubuntu headless + xvfb）でビルド済み拡張がロードされている
  When  ダッシュボードでドメインフィルタを追加し保存し、ページをリロードする
  Then  フィルタがリロード後も表示され、当該E2Eがパスする

Scenario: 失敗時の診断情報で原因が特定できる
  Given 当該E2EがCI環境で失敗した
  When  アーティファクト（スクリーンショット・トレース・ページ状態）を確認する
  Then  失敗原因（アプリ側の不具合 / テストの待機不足 / CI環境固有の描画差異）が判別でき、対処が決まる

## 受け入れ基準
- [ ] 失敗原因が特定され、記録されている（テスト側の待機不足 / アプリ側の不具合 / CI環境固有差異のいずれかに分類）
- [ ] 対処後、CI環境で当該テストが3連続パスする
- [ ] 修正がテストの検証意図（フィルタ保存の永続化の検証）を損なっていない
- [ ] `test` / `usability` 両ジョブが緑になり、ローカルでも当該specがパスする

## テスト戦略
- E2E: 当該specの安定化が主題。フレーキー化の元（固定sleep・不完全な待機）があれば待機戦略へ修正
- 統合/単体: 対象外（e2eの安定化が目的）。アプリ側不具合と判明した場合はそのロジックに単体テストを追加
