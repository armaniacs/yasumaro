# PBI: 台帳に残る「意味が壊れた」文字化け断片の復元（自動検出できない層）

## ユーザーストーリー

PBI 台帳の読者（これから実装する開発者、レビュアー、後任）として、**過去の PBI に残った意味の壊れた断片が復元され、著者が書いた主張のまま読めること**がほしい。なぜなら台帳は「なぜこの修正をするのか」を後から読む唯一の記録であり、断片が壊れていると主張そのものが読めなくなるからである。とくに `pbi/2026-10-18-10-fix-opfs-v2-verify-before-delete.md` の「重複で skip は失敗ではない」は、主語が壊れているために逆の意味にも読めてしまう。誤読したまま実装すると、その PBI が潰そうとしている設計へ誘導される。

  - Confidence: 100%。確定例 3 件を 2026-10-19 にファイルを読んで確認済み（下記「背景」）

## 背景（発見の経緯）

2026-10-19 の一括修復で、`pbi/` の 2 クラスの破損が直っている。

1. 非 CJK 文字の混入（ハングル等。台帳では韓国語の「呼び出し」が混入していた 1 件）
2. 日本語文中への中国語簡体字の混入（18 ファイル 118 行）

この 2 クラスは現在クリーンで、文字種をスクリプトで走査すれば検証できる。

**第三のクラスが残る**: 以前の自動修復が著者の語を無関係なラテン文字・日本語に置き換えてしまった断片（および同じ修復パスが置換対象と認識せず取り残した断片）で、文が著者の書いた意味を成さなくなっている。これはスクリプトでは見つけられない。日本語はラテン文字の識別子とかな・漢字を正当に連結するため、`[A-Za-z]+[ぁ-んァ-ヶ一-龥]+` のような regex は `PBI実装状況一覧` のような正常なテキストにも一致してしまう。

### 確定例（2026-10-19 にファイルを読んで確認）

`pbi/2026-10-18-10-fix-opfs-v2-verify-before-delete.md`:

- 5 行目: `前提で_regexp 精装機器Jpaまで拡張機能を更新する` — 著者は「利用者が拡張機能を更新し続ける限り」に相当することを書いたと読めるが、文脈だけでは復元できない
- 15 行目: `**真Organisationには「重複で skip」は失敗ではない**` — 太字の主語が意味を成さない。この PBI の核心の主張
- 15 行目: `purely な副作用` — 日本語の語が英語の副詞に置き換わったと見られる

### git 履歴の実測（2026-10-19）

上記 3 例はいずれも、当該ファイルの新規作成コミット `99736f59`（2026-10-18）に既に存在する。2026-10-19 の一括修復コミット `61694c84` もこの 3 例を直していない。一方で同じ `61694c84` は、**同じファイル内の同種の断片を複数修復している**（`行われるため`、`ひとつの機会`、`全エラーを握り潰す`）。つまり第三のクラスは「置換痕」と「置換漏れ」の両方を含み、`git log -p` で見える「直前の姿」自体が既に壊れている。ファイルが最初から壊れていれば、git 履歴からは原文を復元できない。

### 未確定の全体像

対象ファイルと行の正確な集合はまだ列挙されていない。**その列挙が本 PBI の最初の成果物**であり、復元はその一覧に基づいて 1 箇所ずつ行う。`pbi/00-INDEX.md` の 2026-10-19 アーカイブ履歴には、残課題 (2) として「PBI 10 に深い文字化け断片が残る」と既に記載されている。

## 影響

- **誤読による手戻り**: PBI 10 の `真Organisation...` は「重複で skip は失敗ではない」という引数であり、素朴な `count === records.length` ゲートを退ける根拠になっている。主語が読めないと逆（skip は失敗）に読め、その PBI が潰そうとしている設計を正当化してしまう。断片は設計判断を反転させうる位置にある
- **台帳の信頼性低下**: 台帳は「なぜ」を後から読む唯一の記録である。意味の壊れた断定が残ると、レビュー時に検証できない主張がそのまま通る
- **復元そのもののリスク**: 復元は著者の語を復活させる作業であり、推測を含む。根拠を残さない復元は、原文より悪い「もっともらしい別の主張」を作り、実装者を誤った設計に誘導しうる。したがって未確定は未確定として残すことが影響の一部である
- **影響範囲は限定的**: ドキュメントのみで、実行時挙動・保存データ・ユーザー体験には影響しない

## テスト戦略

- **自動テストは無い。** 意味の正しさはスクリプトで検証できない。ここを緑で代替しないことが本 PBI の本体である
- **(a) 回帰防止（スクリプトで確認できる唯一の層）**: 非 CJK 文字と簡体字の混入が 0 であることをスクリプトで確認する。確認対象は `pbi/` の全 Markdown（アーカイブを含める判断をした場合はその範囲も）
- **(b) レビュー必須**: 復元箇所の前後を読んだレビューを必須にする。`npm run validate` の緑は意味の正しさを何も保証しない
- **(c) 再現手順の記録**: 棚卸しの再現手順（どのファイルを、どの候補抽出で、どの順に読んだか）を残す。第三者が同じ一覧に到達できることが、棚卸しの完了条件
- **`npm run validate` は docs のみの変更でも通すが、通ったことをもって終わりにしない**（意味のレビューが本体）。ADR リンクと lint はドキュメントでも壊れうるため、門は通す

## 実装メモ（実装者向け）

### なぜスクリプトで検出できないか（2026-10-19 実測）

対象は `pbi/` と `dev-docs/archived/pbi/` の Markdown 1,457 ファイル。素朴な候補抽出の偽陽性を実測した。

```
候補 A: ASCII 英数字の連続が、かな・漢字に空白なしで直接隣接する行 → 6,749 行
候補 B: 小文字ラテン語（4 文字以上）＋助詞が空白区切りで並ぶ行       → 31,423 行
```

真陽性は一桁に留まる見込みで、この種の regex は**検出器にならない**。`PBI実装状況一覧`、`gist の`、`redirect を` のような正当な語が大量に混ざる。したがって棚卸しは「候補を出す」段と「人間が読んで判定する」段に分ける。

### 推奨する棚卸し手順（3 段）

1. **Pass A — git diff を読む（最も確実）**
   2026-10-19 の一括修復コミット `61694c84` の `pbi/` に対する差分を、ハンク単位で全部読む。置換の `-` 側と `+` 側の対は、自動修復パスが下した判断そのものである。`+` 側が「もっともらしいが元の主張と違う」箇所と、`-` 側に残った断片を拾う。同種の一括修復パスが他にもないか、`git log --numstat -- pbi/` で変更量の大きいコミットを洗う。この段は候補数が小さく、根拠（コミット）が最初から付く点で最も費用対効果が高い。
2. **Pass B — 高精度の候補抽出（取りこぼし対策）**
   「英語の副詞・一般語が日本語の助詞と並ぶ」形（`purely な` 型）と「日本語として成立しない漢字二字の連結」を候補にする。`skip` / `throw` / `count` / `profile` / `worker` などの識別子、ファイルパス、コード span の中身は除外する。除外リストはリポジトリ自身（コード span と `git grep` で拾える識別子）から作る。候補数は Pass A より多いが、読む量を現実的な範囲に絞れる。
3. **Pass C — 文脈を読んで判定する**
   候補の各行を前後 5 行と節全体、およびその PBI の目的と併せて読み、`確定` / `正常（正当な識別子の連結）` / `未確定` の 3 値で判定する。`未確定` はそのまま残す。判定結果は「ファイル:行 / 現在の文字列 / 判定 / 復元案 / 根拠」の**行の配列**として残す（表でも箇条書きでもよいが、1 行 1 断片を崩さない）。

本文だけでなく、見出し・表・コードブロック外の注釈も同じ基準で見る。断片は主張の中だけでなく、表のセルや完了記録にも現れうる。

### 確定例（2026-10-19 時点の判定）

| ファイル:行 | 現在の文字列 | 判定 | 復元の根拠 |
|---|---|---|---|
| `pbi/2026-10-18-10-...md:5` | `前提で_regexp 精装機器Jpaまで拡張機能を更新する` | 未確定 | 文脈から「利用者が拡張機能を更新し続ける限り」相当と読めるが、`99736f59` の時点で既に壊れており原文は履歴に無い |
| 同 `:15` | `**真Organisationには「重複で skip」は失敗ではない**` | 未確定（主張の向きは復元可） | 同節の続きが「INSERT OR IGNORE の skip は既に移行済みの行を指す」と説明しており、向きは確定できる。主語の語だけが不明 |
| 同 `:15` | `purely な副作用` | 未確定 | 文脈は「完了が立たないまま再読込と warn を繰り返す」という負の副作用。日本語の語が英語副詞に置換されたと見られる |

### 落とし穴

- **`git log -p` で見える「直前の姿」自体が既に壊れていることがある。** 実測: PBI 10 の 3 例は新規作成コミット `99736f59` から存在し、修復コミット `61694c84` も直していない。過去の自動修復が同じファイルを複数回触っている可能性があるため、直前の版が壊れていればさらに前のコミット、最終的にはファイル新規作成時点へ遡る。そこでも壊れていれば git 履歴からは復元できない（＝「未確定」に落とす）
- **復元した文が技術的に正しい主張になるかを必ず確認する。** PBI の主張は実装者との契約であり、書き換えると実装者が間違った設計に誘導される。とくに PBI 10 の `真Organisation...` は「重複 skip は失敗ではない」という引数で、逆向きに復元すると素朴な `count === records.length` ゲートを正当化してしまう
- **一括置換で直さないこと。** 同じ文字列（`skip`、`count` など）は正常な箇所にも現れる。1 箇所ずつ文脈を読む
- **`dev-docs/archived/pbi/` 側にも同種の断片が残っている可能性がある**（1,408 ファイル）。棚卸しの対象に含めるかを明示的に決める。推奨: 候補抽出はアーカイブまで回す（同じスクリプトで追加コストが小さい）が、**復元は live な判断に効く箇所を優先し、アーカイブは「未確定」の記録に留める**。理由は、アーカイブが既に完了した判断の記録で書き換えの便益が小さく、推測を混入させるリスクは live 側と同じだけ大きいため
- **復元は git 履歴の書き換えではない。** 過去のコミットはそのまま残す。新規コミットで直し、`git revert` で戻せる範囲を超えない
- **一覧に断片を引用するときはコード span で正確に写す。** 要約や言い換えをすると後から照合できない。本 PBI 自身がコード span の中だけに壊れた断片を持つのはこのため
- **`dev-docs/` は英語のみの方針**（`dev-docs/DOCUMENTATION_GUIDE.md`）。本 PBI が触るのは日本語の台帳（`pbi/`）であり、この方針を変更しない

### 着手前に潰すべき判断

owner 判断は 2 点。

1. **アーカイブ（`dev-docs/archived/pbi/`）を復元対象に含めるか。** 推奨は「棚卸しには含める・復元は live 優先」。含めない場合もその理由を完了記録に残す
2. **復元の粒度。** 「意味が確定できる断片だけ復元し、残りは未確定として残す」を推奨。全部を推測で埋める案は、原文より悪い別の主張を作りうるため採らない
