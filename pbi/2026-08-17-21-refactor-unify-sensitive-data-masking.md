# PBI: 二つの機密データマスキングシステムを統一する

## ユーザーストーリー
開発者として、`src/utils/redaction.ts` と `src/utils/logMasker.ts` の二つの並列マスキングシステムを統一したい。なぜなら、異なるフィールドリストと異なる戦略（[REDACTED] vs ***）を使用しており、一部の秘密が一方のシステムを通過してもう一方を通過しないリスクがあるから。

## ビジネス価値
- 機密データの漏洩防止が1つのCanonicalな場所で管理される
- 新しい機密フィールドの追加が1箇所で完結する
- 二重マスキングやマスキング漏れのリスクを排除

## BDD受け入れシナリオ

```gherkin
Scenario: APIキーのマスキングが統一される
  Given ログにOpenAI APIキーが含まれている
  When ログが出力される
  Then redaction.ts と logMasker.ts の両方で同じマスキングが適用される
  And マスキング結果が一致する

Scenario: 新しい機密フィールドの追加
  Given 開発者が新しいAPIプロバイダーを統合する
  When 機密フィールドを追加する
  Then 共有マスキングモジュールに1箇所追加するだけで
  And すべてのマスキングシステムで利用可能になる

Scenario: メールアドレスのマスキング
  Given ログにメールアドレスが含まれている
  When logMasker.ts でマスキングする
  Then 部分的にマスキングされたメールアドレスが表示される
  And redaction.ts でも同じ結果になる
```

## 受け入れ基準
- [ ] 共有機密データマスキングモジュールが `src/utils/sensitiveDataMask.ts` に作成される
- [ ] 互換性のないフィールドリストが統一される
- [ ] マスキング戦略が1つに統一される
- [ ] `src/utils/redaction.ts` が共有モジュールをimportする形に変更される
- [ ] `src/utils/logMasker.ts` が共有モジュールをimportする形に変更される
- [ ] 既存のテストがすべてパスする
- [ ] 新しい統合テストが追加される

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- ログ出力時に機密データがマスキングされることを確認

### 統合テスト
- 共有マスキングモジュールのエクスポートインターフェース検証
- 既存のマスキング戦略がすべて新しいモジュールにマッピングされることの確認

### 単体テスト
- 各フィールドタイプのマスキングロジック
- マスキング結果の正確性
- 互換性マッピングの網羅性

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

3pt （要チームでの見積もり）

## 技術的考慮事項
- 依存関係: なし
- テスタビリティ: 共有モジュールは純粋関数としてテスト可能
- 非機能要件: マスキング性能を維持

## 実装者向け注記

### 現状コードの確認
```bash
# 既存のマスキングシステムを検索
grep -rn "SENSITIVE_KEYS\|LEVEL1_FIELDS\|LEVEL2_FIELDS" src/
grep -rn "redactSensitiveData\|maskSensitiveData" src/
```

### 実装手順
1. `src/utils/sensitiveDataMask.ts` を新規作成
2. 既存のフィールドリストを統合
3. マスキング関数を共有モジュールに移動
4. `src/utils/redaction.ts` を共有モジュールをimportする形に変更
5. `src/utils/logMasker.ts` を共有モジュールをimportする形に変更
6. 既存テストを更新
7. 新しい統合テストを追加

### 落とし穴
- フィールドリストの統合時に重複を確認する必要がある
- マスキング戦略の統合時に既存の動作が変わらないように注意する
