# PBI: ドメインポリシーのblob-tier readerと監査pin拡張

## ユーザーストーリー
ブラックリストに追加した利用者として、設定マイグレーションの折り畳み後も遮断が効き続けてほしい、なぜなら遮断したはずのサイトが静かに記録されるのは中核的な信頼を壊すから。

## ビジネス価値
- 折り畳み適用済みDBでもドメインポリシーと委譲フラグが読めるようになる
- 未申告の読み手を監査pinで自動検出し、同根の盲区の再発を防ぐ
- 測定方法: fold前後のtwin回帰が緑で、未申告の読み手追加でpinが赤になること

## BDD受け入れシナリオ

```gherkin
Scenario: ブラックリストの遮断が折り畳み後も効く
  Given blacklistモードで特定ドメインを遮断している
  And 折り畳み適用済みのデータベースがある
  When そのドメインのページを開く
  Then content側の判定でも記録対象から除外される
  And SW側の判定と一致する

Scenario: 未申告の読み手はpinが失敗する
  Given 監査pinが走査対象を定めている
  When 申告なしでport経由の読みを追加する
  Then pinが失敗して未申告箇所が指摘される
```

## 受け入れ基準
- [ ] 4キーがTOP_LEVEL_ONLY_KEYSに追加され、折り畳み後のDBでも読める
- [ ] blob読み手が追加され、折り畳み前後で判定が変わらない
- [ ] 委譲フラグの再読みがblob書き込みでも起きる
- [ ] 監査pinが拡張され、未申告の読みで失敗する
- [ ] E2E追加は最小限で既存スイートが緑のまま

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 追加は最小限（1本以下）。既存スイートの緑を維持する

### 統合テスト
- 折り畳み適用済みDBでの遮断判定
- 折り畳み未適用DBでの現行一致（twin回帰）
- 委譲フラグの再読みとSW起動時refreshのtwin確認

### 単体テスト
- 監査pin拡張の表駆動テスト
- pin失敗のRed側確認

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

## 見積もり
M （要チームでの見積もり）

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: fold適用のテストピースで検証する。InMemory既定値では隠れるため使わない
- 非機能要件: B8（パス単位照合の非対称修正）と混ぜない
- ロールバック手段: 読み手追加の差し戻しで現行動作に戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -rn "domainPolicyPort\|TOP_LEVEL_ONLY_KEYS" src/ --include="*.ts" | grep -v __tests__
grep -rn "raw-owned-keys-audit-pin" src/ --include="*.ts" | head -3
```

確認結果:
- blob-tier読手は未実装。監査pinは現行範囲のまま
- 参照実装が `feature/carried-over-candidates` にある（port経由読み・lockstep pinの方針を参照せよ。丸写しではなく現行mainに合わせること）

### 実装手順
1. Outside-Inでtwin回帰の失敗試験から書く
2. 4キーの追加とblob読み手を追加する（blob優先・top-levelフォールバックの順序を契約として明記）
3. 監査表とlockstepで同時追加する。片方だけ残さない
4. onChanged監視を拡張し、委譲フラグの再読みを通す

### 落とし穴
- 書き込み側はblobに書くため、読みはblobを先にすること
- 未折り畳みlegacy DBのtop-levelコピーは陳腐化し得るためフォールバックに限定する
- pin:459相当の早期returnは未申告記録に変えること
