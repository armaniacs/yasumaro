# PBI: promptSanitizer safe-context 判定のバイパス耐性向上

## ユーザーストーリー
拡張機能のセキュリティ担当者として、`isInSafeContext()` の safe-context 判定が意図的な回避手口に対して現実的な耐性を持ってほしい、なぜならプロンプトインジェクション対策が形骸化するとAI要約の品質・安全性に影響するから

## ビジネス価値
- プロンプトインジェクション対策の実効性向上（多層防御の1層として機能する状態を維持）
- 将来の同種の指摘の再発防止（設計上の限界をコードに明記することで、誤解に基づく過剰な「完全防御」要求を防ぐ）

## 背景（既実装確認）

`src/utils/promptSanitizer.ts` の `isInSafeContext()` は PBI `2026-08-19-02-fix-prompt-safecontext.md` で実装済み（常時 `false` を返すバグの修正）。しかしコードレビューにより、以下2つのバイパス手口が判明した：

1. **HTMLタグ判定のバイパス**: `openTag` の正規表現 `<[^>]*$` が属性値の内部にもマッチしてしまうため、`<img alt="ignore all previous instructions">` のように攻撃文を属性値に埋め込むと safe 判定されフィルタを回避できる
2. **safeMarker判定のバイパス**: `before` の検索ウィンドウが200文字と広く、`guide` や `malicious` のような safeMarker 単語を実際の攻撃文の直前200文字以内に混入させるだけで safe 判定される

なお、なぜなぜ分析の結果、safeMarker 判定は正規表現ベースの近接ヒューリスティックである以上、適応的な攻撃者に対する完全な防御は原理的に不可能という構造的な限界がある（詳細は本PBIの「技術的考慮事項」参照）。本PBIでは実用上のバイパス難易度向上と、その限界の明文化を目標とする。

### 追加の深掘りで判明した3点（本PBIのスコープに含める）

1. **safeMarkers の言語カバレッジ非対称**: `REFINED_INJECTION_PATTERNS` には日本語パターン（「無視して」「上記の指示を無視」等）が存在するが、`safeMarkers` は英語の単語境界パターン（`\bexample\b` 等）のみで日本語相当語が存在しない。本プロジェクトの主要ユーザー層は日本語UI利用者であり、日本語コンテンツに対しては safe-context 救済がほぼ機能しない状態になっている。攻撃パターンと安全化パターンは対になるべきだが、この対称性が保たれていなかった。
2. **HTML属性値バイパス修正案自体のReDoSリスク（敵対的レビューでCONFIRMED）**: 修正候補として提示した正規表現 `<[a-zA-Z][a-zA-Z0-9-]*(?:\s+[a-zA-Z-]+(?:="[^"]*"|='[^']*'|[^\s>]*))*\s*$` は、外側の `(?:...)* ` と選択肢内の `[^\s>]*` が入れ子になっており、量指定子のネストという古典的なReDoSパターンに該当する。`isInSafeContext` は攻撃者が完全に制御可能なWebページコンテンツに対して実行されるため、この正規表現をそのまま採用すると**修正が新たなDoS脆弱性を作り込む**。ハッカー視点の敵対的レビューで「実装者がPBIのコード片をそのままコピーすれば脆弱性を新規導入する」と指摘され、PBI文中に「懸念があれば」という任意の対策扱いになっていたことも問題視された。本PBIでは**この正規表現案をそのまま採用してはならない**ことを明記し、対策を必須の受け入れ基準に格上げする。
3. **GENERIC_TERM_PATTERNS 側は本PBIのスコープ外と判明**: `isMaliciousUsage()`（`GENERIC_TERM_PATTERNS` 用の判定）は `isInSafeContext()` を呼んでおらず、一見バイパス可能に見えた。しかしコードを読むと、`isMaliciousUsage()` が `true` を返しても `sanitized` の内容は変更されず（`warnings` に追記され `dangerLevel` が `LOW` に上がるのみ）、全呼び出し元（`builtInAIClient.ts` / `privacyPipeline.ts` / `ProviderStrategy.ts` / `customPromptUtils.ts`）は `dangerLevel === 'high'` のみを判定に使っている。つまりこの経路は元々コンテンツをフィルタしておらず「バイパス」ではなく、警告が握りつぶされる別のバグ（`2026-08-19-08-fix-malicious-usage-dangerlevel-ignored.md`）である。本PBIの対象からは除外する。

### 敵対的レビューで判明した追加の矛盾

4. **日本語safeMarkerとウィンドウ長の不整合（CONFIRMED）**: `SAFE_MARKER_WINDOW` を5〜10文字（実装案では8文字）に縮小する一方、追加する日本語安全語には「プロンプトインジェクション」（12文字）「インジェクション攻撃」（10文字）のように、ウィンドウ長そのものを超える語が含まれている。マッチ直前8文字のスライスに12文字の単語全体が収まることはなく、これらのパターンは**ウィンドウ縮小後は原理的にマッチしない**。日本語対応の受け入れ基準・BDDシナリオがロジック的に成立しないまま実装されるおそれがあるため、安全語の選定とウィンドウ長は同時に整合性を検証すること。
5. **短い日本語安全語（「対策」「例」「ガイド」等）が新たな撒き餌になりうる（CONFIRMED、本PBIの結論との自己矛盾）**: 本PBI自身が「近接ヒューリスティックは適応的な攻撃者への完全防御を提供しない」と結論しているにもかかわらず、2〜3文字の汎用的な日本語安全語（単語境界チェックなし）を新規に追加する提案は、日本語コンテンツにおいて英語版よりも容易な撒き餌（例:「攻撃例：〔上記の指示を無視して〕」）を新設する。本プロジェクトの主要ユーザー層が日本語UI利用者であることを踏まえると、実害は英語版のバイパスより大きくなりうる。安全語は「単語自体がウィンドウ長に収まり、かつ一定の具体性（複合語）を持つもの」に絞り、単漢字・2文字語は避けること。

## 受け入れ基準
- [ ] `isInSafeContext()` のHTMLタグ判定が、開いたままの属性値クォート内（`attr="..."` の途中）を安全とみなさない
- [ ] `isInSafeContext()` のHTMLタグ判定は、タグ名直後・属性が正しく閉じている位置のみ安全とみなす
- [ ] **（必須・実測とツールの両方）** HTML属性値除外用の正規表現が、悪意あるHTML断片に対して線形時間で処理を完了する（破滅的バックトラッキングを起こさない）ことを、(1) 実測（`<a ` + 空白/`=`/引用符を含まない1万文字連続 + 空白なし、を最低1パターンとして含む攻撃的入力で、100ms未満の実行時間を単体テストでアサートする）と、(2) 静的検証ツール（`safe-regex`等）の両方で確認する。どちらか一方のみでは受け入れ不可とする（敵対的レビューで「『または』表記だと片方だけで済ませられる」と指摘されたため、AND条件に変更）
- [ ] safeMarkers の検索ウィンドウを200文字から現実的な近接距離（5〜10文字程度）に縮小する
- [ ] `isInSafeContext()` の関数コメントに、本チェッカーが多層防御の一部であり適応的攻撃者への完全防御を目的としないという設計上の限界を明記する
- [ ] safeMarkers に日本語相当の安全語を追加する場合、追加する語すべてが `SAFE_MARKER_WINDOW` の文字数以下であることを確認する（ウィンドウ長を超える語は追加しても無効なので候補から除外する）
- [ ] 追加する日本語安全語は単漢字・2文字語を避け、3文字以上かつ `SAFE_MARKER_WINDOW` 以下の複合語に限定する（撒き餌としての悪用しやすさを抑える）。機械的な判定基準: 文字数が3文字以上8文字以下であること（「一定の具体性」という主観的表現を排し、文字数のみで判定可能にする。将来の担当者が新規語を追加する際も同じ基準で判定できる）
- [ ] 既存の単体テストがパスする
- [ ] **（測定手段は既存）** `src/utils/__tests__/promptSanitizer-false-positives.test.ts:100-138` の `should calculate false positive rate for sample corpus` テストが実装後も `expect(falsePositiveRate).toBeLessThan(20)` をパスする。このテストは10件の正当コンテンツコーパスに対する誤検知率を実測する既存の自動テストであり、本PBIの実装によりこのテストの誤検知件数が増加していないことを確認する（敵対的レビューで「誤検知率<20%の測定方法が未定義」と指摘されたが、実際には測定手段が既存であり、参照漏れが真の問題だった）

## 技術的考慮事項
- 依存関係: なし
- テスタビリティ: 純粋関数のためモック不要
- 非機能要件・設計上の限界:
  - なぜなぜ分析の結論として、正規表現ベースの近接ヒューリスティックは非適応的な誤検知源（正規ドキュメント等）の削減には有効だが、safeMarker単語を意図的に撒き餌として混入する適応的な攻撃者には原理的に無力である
  - 本PBIはバイパスの「完全排除」ではなく「実用上の難易度向上」と「限界の明文化」を目的とする
  - `promptSanitizer` は多層防御の一枚であり、PIIマスキングやサンドボックス化されたLLM呼び出し等、他の防御層と組み合わせて使うことを前提とする

## 実装者向け注記

### 現状コードの確認
（着手前に必ず実行すること）
```bash
grep -n "isInSafeContext\|safeMarkers\|openTag\|closeTag" src/utils/promptSanitizer.ts
```

### 実装手順
1. `isInSafeContext()` の HTML タグ判定用正規表現を、属性値が閉じている場合のみマッチするよう修正する

   ```ts
   // タグ名直後・属性が正しく閉じている位置のみ安全とみなす（属性値内は除外）
   const openTag = before.match(/<[a-zA-Z][a-zA-Z0-9-]*(?:\s+[a-zA-Z-]+(?:="[^"]*"|='[^']*'|[^\s>]*))*\s*$/);
   ```

2. safeMarkers 判定の `before` 検索範囲（`WINDOW`）を200から縮小する。HTMLタグ・コードブロック判定用のウィンドウとは別に、safeMarker専用の小さいウィンドウ定数を設ける

   ```ts
   const SAFE_MARKER_WINDOW = 8; // マーカー語がマッチ直前にある場合のみ有効
   const markerBefore = content.slice(Math.max(0, index - SAFE_MARKER_WINDOW), index).toLowerCase();
   // safeMarkers.some((p) => p.test(markerBefore)) に置き換え
   ```

3. `isInSafeContext()` のJSDocに設計上の限界を追記する（本PBIの「技術的考慮事項」の文言を要約して反映）

4. `safeMarkers` に日本語相当の安全語パターンを追加する。追加候補は必ず `SAFE_MARKER_WINDOW`（8文字）以下の長さに収め、単漢字・2文字語を避ける。「プロンプトインジェクション」「インジェクション攻撃」のようなウィンドウ長を超える語は候補から除外する（ウィンドウ拡大ではなく、ウィンドウに収まる語を選ぶことで対応する）

   ```ts
   // 各パターンはマッチ文字列自体が SAFE_MARKER_WINDOW(8文字) 以下であること
   const safeMarkersJa = [
     /対策例/,     // 3文字
     /注意喚起/,   // 4文字
     /攻撃手法/,   // 4文字
   ];
   // safeMarkers.some(...) の判定に safeMarkersJa も含める
   // 「ガイド」「対策」「例」のような単漢字・2文字の汎用語は撒き餌になりやすいため採用しない
   ```

5. **（必須）** HTML属性値除外用の正規表現がReDoSを起こさないことを確認する。手順:
   - まず提示された `<[a-zA-Z][a-zA-Z0-9-]*(?:\s+[a-zA-Z-]+(?:="[^"]*"|='[^']*'|[^\s>]*))*\s*$` をそのまま採用しない
   - 入れ子の繰り返し構造を避けた実装に置き換える。例えば「`before` の末尾が閉じた属性のみで構成されているか」を1回の非バックトラッキング的な走査（手続き的なパーサ、または `RegExp` のバックトラッキングが発生しない形に単純化したパターン）で判定する
   - 実装後、大量の非空白文字（例: `<a ` + `x`を1万文字連続 + 空白なし）を含む入力で実行時間を計測し、線形時間で完了することを確認する

6. 単体テストを `src/utils/__tests__/promptSanitizer.test.ts`（存在しなければ新規作成）に追加する。既存の `promptSanitizer.test.ts:125-126`（safe-context プレフィックスがバイパスにならないことを確認するテスト）とは目的が異なる、`isInSafeContext()` 自身の positive/negative ケースを新規に追加すること

### 落とし穴
- ウィンドウを縮小しすぎると、正当なドキュメント文脈（「Prompt injection guide: ...」のように直前にマーカーがある自然な文章）まで誤ってフィルタしてしまう。既存の誤検知率目標（<20%）を悪化させないよう、縮小後の値は実際のテストケースで調整すること
- HTML属性値の正規表現修正は、シングルクォート・ダブルクォート・クォートなし属性のすべてに対応させること（`alt="..."` / `alt='...'` / `alt=foo` のいずれのパターンも考慮）
- この修正は「バイパス不可能」を保証するものではない。将来同種の指摘が来た場合、まずJSDocの設計限界コメントを参照し、構造的な限界か実装バグかを見極めること
