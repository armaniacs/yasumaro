# PBI: 選択範囲の記録（ハイライト部分だけ記録）

## ユーザーストーリー

長文記事を読むユーザーとして、選択した段落だけを記録したい。なぜなら、ページ全体の記録はノイズが多く、読んだ部分だけを構造化して残したいから。

## 優先度

- 順位: 3 / 9（全候補）
- RICEスコア: 8.0（Reach=12 / Impact=2 / Confidence=50% / Effort=1.5人週）
- 根拠: 記録単位がページ全体のみで、「この段落だけ残したい」需要（ユーザージャーニー J3）に応えられていない。類似ツール比較では、Obsidian Web Clipper のハイライト相当が Yasumaro の唯一の欠落。ページ全体記録のノイズ低減にも効くため、9件中3位とした
- 軸との整合（自律解決済み）: 選択範囲は既に収集している本文の部分集合なので、軸3「収集を増やさない」には反しない。ユーザーアクション起点の保存は、手動記録（MANUAL_RECORD・今すぐ記録ボタン）という前例が既にある

## ビジネス価値

- 読んだ部分だけを構造化して残せるため、記録の再読コストが下がる
- ページ全体記録のノイズが減り、AI要約の文字数効率と精度が上がる
- 測定方法: E2Eテスト（ページで選択して記録すると保存内容が選択範囲になる）の緑、既存テスト全緑、手動記録に占める選択範囲記録の割合

## BDD受け入れシナリオ

```gherkin
Scenario: 選択したテキストだけを手動記録する
  Given ユーザーが記事ページで1段落を選択している
  When ユーザーがポップアップの今すぐ記録ボタンを押す
  Then 選択テキストだけが既存の記録パイプラインを通って保存される
  And 保存された記録が選択範囲由来であると判別できる

Scenario: 選択が空のときは通常のページ記録にフォールバックする
  Given ユーザーがページで何も選択していない
  When ユーザーがAlt+Shift+Yで手動記録を実行する
  Then ページ全体が既存の記録パイプラインを通って保存される
  And 記録はエラーにならず完了する

Scenario: 選択テキストが10,000文字を超える
  Given ユーザーが10,000文字を超える範囲を選択している
  When 手動記録を実行する
  Then 選択テキストは10,000文字以内に正規化されて保存される
  And 保存は失敗しない
```

## 受け入れ基準

- [ ] ポップアップの今すぐ記録ボタンとAlt+Shift+Yのどちらでも、選択がある場合は選択範囲だけが記録される
- [ ] 選択が空の場合は、従来どおりページ全体が記録される（後方互換）
- [ ] 連続空白の圧縮と行区切り文字（U+2028 / U+2029 / U+0085）の正規化が適用される
- [ ] 10,000文字を超える選択テキストは切り詰められ、記録が完走する
- [ ] 記録は既存のプライバシーパイプライン（PII マスキング、AI要約クレンジング、プライベートページ判定）を必ず通る
- [ ] 選択範囲由来の記録であることを判別できる

## テスト戦略

### E2Eテスト

- 記事ページでテキストを選択して手動記録すると、保存される記録が選択範囲のテキストになる（headed は owner 手動でも可）
- 何も選択していない状態での手動記録が、従来どおりページ全体を保存すること

### 統合テスト

- 選択テキスト付きの手動記録（MANUAL_RECORD）が、PII マスキングとAI要約クレンジングを含む既存パイプラインを通ること
- 選択が空のときに通常のページ記録へフォールバックすること

### 単体テスト

- 選択テキストの正規化: 連続空白の圧縮、行区切り文字（U+2028 / U+2029 / U+0085）の置き換え
- 10,000文字上限の切り詰め

### 実装手順

1. E2E: ページで選択して記録すると、保存される記録が選択範囲になる失敗テストを先に書き、赤を確認する
2. 統合: 選択付き手動記録がパイプライン経由で保存される、選択が空ならフォールバックするテストを書く
3. 単体: 選択テキストの正規化と10,000文字上限のテストを書く
4. 実装: MANUAL_RECORD の経路でアクティブタブの content script に選択テキストを問い合わせ、メッセージに載せる
5. 実装: src/utils の sanitize 系を再利用して選択テキストを正規化し、上限を適用してから記録経路に渡す
6. 実装: 選択が空の場合は従来のページ記録へフォールバックさせる

### 落とし穴

- 選択テキストの正規化を独自実装しない。連続空白の圧縮と行区切り文字（U+2028 / U+2029 / U+0085）の正規化は src/utils 側の sanitize 系に既存がある。markdown 注入防止の pin テストが既存のため、正規化を差し替えると pin テストが壊れる
- 10,000文字上限の扱い（切り詰めるか記録を拒否するか）を決めずに着手しない。このPBIは切り詰めを採用する
- src/utils や src/content 配下を新規ファイルへ分割した場合は、manifest.json の web_accessible_resources の更新を忘れない（過去に Content Script の動的インポート失敗の前例あり）
- 選択範囲は既に収集している本文の部分集合なので、新規の収集経路を増やす実装にしない。手動記録の入口（今すぐ記録ボタン・Alt+Shift+Y）と自然に統合する
