# PBI: 端末間のエンドツーエンド暗号化同期

## ユーザーストーリー
複数の端末(自宅の PC と職場の PC など)で Yasumaro を使う利用者として、閲覧履歴と要約を端末間で同期したい。ただし同期先のサービス事業者にも中身を読まれないようにしたい、なぜなら現状の GitHub Gist 同期は記録の本文を平文のまま Gist に置くため、トークンの漏えいや事業者側の閲覧で履歴が丸ごと読めてしまうから。

## 優先度
- 順位: 09/12
- RICE スコア: 0.3(Reach 4 × Impact 2 × Confidence 0.5 ÷ Effort 13 ≒ 0.31)
  - Reach 4: 複数端末で使う利用者に限られる。単一端末の利用者には影響しない
  - Impact 2: 同期を使う利用者にとっては、履歴の秘匿性が根本から変わる
  - Confidence 0.5: 鍵の配送(端末間で鍵をどう共有するか)と競合解決の設計が未確定
  - Effort 13: 暗号形式の設計、同期先の抽象化の拡張、競合解決、鍵の復旧導線まで含む
- 根拠: 価値は大きいが、同期を使う利用者が限られ、設計の不確実性が高い。現状の Gist 同期は実験的機能(N=1)であり、利用実績を見てから投資を判断する

## ビジネス価値
- 同期先の事業者やトークンを得た第三者が、履歴と要約を読めなくなる
- 「データはローカルのみ」という製品方針を、同期を使う場合にも実質的に保てる
- 測定方法: 同期先に置かれたデータが暗号文のみで、URL・タイトル・要約の平文を含まないこと(同期先の API レスポンスを検査するテストで確認)

## BDD受け入れシナリオ

```gherkin
Scenario: 同期先には暗号文だけが置かれる
  Given 利用者が端末 A で暗号化同期を有効にし、同期用パスフレーズを設定している
  And   端末 A に「https://example.com/secret」の記録がある
  When  同期が実行される
  Then  同期先に送られる本文は暗号化された封筒形式のみである
  And   本文に URL、タイトル、要約の平文が含まれない

Scenario: 別の端末で同じパスフレーズを入力すると記録が復元される
  Given 端末 A の記録が暗号化されて同期先に置かれている
  When  利用者が端末 B で同じ同期先と同じ同期用パスフレーズを設定する
  Then  端末 B の履歴に端末 A の記録が表示される

Scenario: パスフレーズが違うと復号せず、既存の記録も壊さない
  Given 端末 B に既存の記録がある
  When  利用者が誤った同期用パスフレーズで同期を実行する
  Then  復号に失敗した旨が表示される
  And   端末 B の既存の記録は変更されない
```

## 受け入れ基準
- [ ] 同期先へ送る本文が、認証付き暗号(AES-GCM)の封筒形式のみである
- [ ] 鍵は利用者のパスフレーズから端末上で導出し、鍵もパスフレーズも同期先へ送らない
- [ ] 復号失敗(パスフレーズ違い・改ざん)はフェイルクローズで、ローカルの記録を変更しない
- [ ] 同じ記録を 2 端末で更新したときの競合解決の規則が決まっていて、テストで固定されている
- [ ] 既存の平文 Gist 同期の利用者に、移行手順と既存 Gist の扱いが示される
- [ ] `public/PRIVACY.md` と `docs/PRIVACY.md` の同期の記述が、送信内容(暗号文のみ)に合わせて更新され、両ファイルが同一

## テスト戦略(t_wadaスタイル)

### E2Eテスト
- 同期先を模したローカルのスタブサーバーに対して、2 つのプロファイルで送受信し、記録が往復すること

### 統合テスト
- 同期先へ送るリクエスト本文に、記録の URL・タイトル・要約の平文が含まれないこと
- 改ざんした暗号文を受け取ったとき、ローカルの SQLite に書き込みが起きないこと

### 単体テスト
- 封筒の暗号化・復号の往復、誤った鍵での復号失敗、IV の使い回しがないこと
- 競合解決の規則(更新時刻・端末 ID の比較)

## 実装アプローチ
- **Outside-In**: 「同期先に平文が出ない」統合テストを最初に書き、送信経路の外側から固める
- **Red-Green-Refactor**: 暗号形式は既存の封筒形式を再利用できるかを先に確かめ、新しい形式は最後の手段にする

## 見積もり
13 ストーリーポイント(要チームでの見積もり)。8 SP を超えるため、着手前に分割と設計相談が必要。分割の候補は「暗号形式と鍵導出」「同期先への送受信」「競合解決」「既存 Gist 利用者の移行」。

## 技術的考慮事項
- 依存関係: 同期先の抽象(`SyncTarget`)の拡張。受信(pull)の口が現状のインターフェースに無い
- テスタビリティ: 暗号部分は Web Crypto のみで閉じるため、単体テストで往復を検証できる
- 非機能要件: PBKDF2 の反復回数など暗号パラメータは `cryptoParams.ts` の単一の定義に従う。パスフレーズを忘れた場合は同期先のデータを復旧できないことを UI で明示する

## 実装者向け注記

### 最初にやるスパイク
1. 鍵の扱いを決める: マスターパスワードから同期用の鍵を派生させるか、同期専用のパスフレーズを別に持つか。マスターパスワードの変更(鍵のローテーション)時に同期先の暗号文をどうするかも合わせて決める
2. 既存の封筒形式(`encryptEnvelope` / `decryptEnvelope`)と暗号化バックアップ(分割バックアップ含む)の形式を、記録単位の同期にそのまま使えるか確かめる。サイズ上限(`resolveEnvelopeBase64Cap`)が記録単位で足りるかも見る
3. `SyncTarget` は送信専用(`sync` / `syncBatch` / `testConnection`)で受信の口が無い。双方向にするための最小の形を決める。ファイル冒頭のコメントにある「2 つ目の実装が出たら共通化を再検討する」という条件に当たる
4. 同期先の候補(Gist の継続、他のストレージ)と、追加の host permission の要否を洗い出す

### 既存の関連コード
- `src/background/syncTargets/SyncTarget.ts`: 同期先のインターフェース(実験的、実装は Gist のみ)
- `src/background/syncTargets/gistSyncTarget.ts`: Gist 同期。記録を Markdown にして `https://api.github.com` へ送る(secret gist だが本文は平文)
- `src/background/syncTargets/settingsConfiguredCheck.ts`: 同期先の設定済み判定
- `src/utils/crypto/envelope.ts`: AES-GCM の封筒形式(`encryptEnvelope` / `decryptEnvelope` / `decryptBackupEnvelope`)
- `src/utils/crypto/primitives.ts`: 鍵導出(PBKDF2)、AES-GCM の暗号化・復号、IV と salt の生成
- `src/utils/crypto/cryptoParams.ts`: 暗号パラメータの単一の定義
- `src/utils/masterPassword.ts`、`src/utils/storage/encryptionSession.ts`: マスターパスワードと暗号化セッション
- `src/dashboard/encryptedBackupService.ts`、`src/dashboard/encryptedBackupSplitCodec.ts`: 暗号化バックアップの書き出し・読み込み
- `src/offscreen/schema.ts`: `browsing_logs` の `gist_synced` 列(同期済みフラグ)

### 範囲
- 含める: 記録(URL・タイトル・要約・タグ・メタデータ)の暗号化同期
- 含めない: 設定値や API キーの同期、リアルタイム同期、3 台以上での同時編集の最適化
