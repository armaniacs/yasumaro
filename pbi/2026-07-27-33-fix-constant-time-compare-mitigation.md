## 背景

PBI-11 の検証により、`src/utils/crypto/index.ts` の `constantTimeCompare()` フォールバック実装（`timingSafeEqual` が利用不可の場合の文字ループ比較）が **Chrome Service Worker 環境で定数時間性を保証しない** ことが判明した。

実 Chrome ブラウザでのベンチマーク計測結果：
- earlyMismatch（先頭不一致）: 平均 0.00525ms
- lateMismatch（末尾不一致）: 平均 0.00340ms
- Welch の t 値: **2.2381**（\|t\| > 1.96、統計的に有意な差）

V8 の JIT 最適化（分岐予測、キャッシュラインの違い等）により、不一致が発生する位置によって実行時間が変動する。

## なぜなぜ分析の結論：追加緩和策は不要

### Why 1: なぜ PBI-33 を作成したのか？
→ PBI-11 の検証でタイミング差が判明したため

### Why 2: なぜそのタイミング差が問題になるのか？
→ 理論上、攻撃者が比較時間の差から不一致の位置を推測できる可能性があるため

### Why 3: なぜ攻撃者がそのタイミング差を測定できるのか？
→ `constantTimeCompare` はパスワード検証に使われるため、認証リクエストの応答時間から推定できる可能性があるため

### Why 4: なぜこの攻撃が現実的な脅威なのか？
→ **現実的な脅威ではない**

`constantTimeCompare` の使用箇所を確認した結果：
- `verifyPasswordWithPBKDF2()` 内で使用（`src/utils/crypto/index.ts:376, 384-385`）
- この関数は `encryptionSession.ts` と `masterPassword.ts` から**ローカルで呼び出されているのみ**
- ネットワークに公開される API は存在しない
- タイミング差は **1.85μs**（0.00525ms - 0.00340ms）
- ネットワークレイテンシは **10-100ms**（10,000-100,000μs）
- タイミング差はネットワークレイテンシの **5-6桁小さい**

### Why 5: なぜ PBI-33 を作成する必要があるのか？
→ **必要がない**

### 結論

| 観点 | 評価 |
|------|------|
| 攻撃面 | ローカルのパスワード検証のみ。ネットワークに露出しない |
| タイミング差 | 1.85μs。ネットワークレイテンシに比べて無視できる |
| フォールバック使用頻度 | `timingSafeEqual` が利用可能な Chrome バージョンでフォールバックは実行されない |
| 防御の深さ | `timingSafeEqual` が利用可能な場合はそちらが使われるため、フォールバックは事実上デッドコード |

追加緩和策は不要と判断し、本 PBI をクローズする。フォールバック実装はそのまま維持する。

## 緩和策の候補（評価済み・却下）

### 候補A: 定数時間比較ライブラリの採用
→ 却下。フォールバックはローカル使用のみでネットワークに露出しないため、ライブラリ追加のコストに対するメリットがない。

### 候補B: 実装の見直し
→ 却下。V8 の最適化によるタイミング差は攻撃面に影響しないため、実装見直しの必要がない。

### 候補C: timingSafeEqual が利用可能な場合のみ使用し、利用不可の場合はフォールバックなし
→ 却下。`timingSafeEqual` が利用不可の環境でもフォールバックで機能するため、セーフフォールバックは不要。
