# PBI: 閲覧ログ取込のAI修復提案

## ユーザーストーリー
取込で残った利用者として、修正不能行の直し方をAIに提案してほしい、なぜなら形式の違いを手作業で直すのは負担が大きく誤りも増えるから。

## ビジネス価値
- 失敗行の救済率が上がり移行の完了率が上がる
- 差分確認により誤った取込を防ぐ
- 測定方法: 失敗行に対する修正案の提示と確認後取込が完了すること

## BDD受け入れシナリオ

```gherkin
Scenario: 失敗行の修正案が差分で示される
  Given 失敗行が残る取込結果がある
  When 利用者がAI修復を選ぶ
  Then 修正前後の差分が示される
  And 選択行だけ再検証して取り込める

Scenario: 送信抑止が守られる
  Given 失敗行が残る取込結果がある
  When AI修復を使わずに終える
  Then 外部送信は行われない
  And 理由と件数の報告は残る
```

## 受け入れ基準
- [x] 取込後に失敗行だけを対象にAI修復が選べる
- [x] 送信前に汚染除去が行われ件数と文字量が抑えられる
- [x] 選択行だけ再検証して取り込める
- [x] `npm run validate` が通る

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 失敗行から修正案の提示と確認後取込までの操作確認

### 統合テスト
- 差分確認から再検証までの連携
- 送信抑止の確認

### 単体テスト
- 件数と文字量の上限
- 差分表示の内容
- 鍵のロック中の案内分岐

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

M （要チームでの見積もり）

## 技術的考慮事項
- 依存関係: PBI 2026-11-23-05 の寛容本体に依存する。本PBI単独では着手しない
- テスタビリティ: 実時間待ちは使わない。AI呼出しは境界で差し替えて検証する
- 非機能要件: 自動送信と自動取込はしない。利用は明示操作のみとし監査記録を残す。鍵のロック中は使えない案内にする
- ロールバック手段: AI修復の入口を無効化すれば寛容本体のみの運用に戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。

```bash
grep -rn "importFromJson\|importValidatedRows" src/dashboard --include="*.ts" | grep -v __tests__
grep -rn "exportHmacSigner\|sanitize\|cleans" src/dashboard src/utils --include="*.ts" | grep -v __tests__
```

確認結果:
- 寛容本体は別PBIで追加される前提。AI修復の入口は未実装
- 送信範囲は失敗行のみとし、事前に汚染除去する方針で確定済み

### 実装手順
1. Outside-Inで修正案提示から確認後取込までの失敗試験から書く
2. 規則で直せる行は規則で直し、残りだけAI対象とする
3. 提案は修正前後の差分で示し、選択行だけ再検証して取り込む
4. 監査記録を残し、文書に利用条件を明示する

### 落とし穴
- 自動送信しないこと。明示操作なしに外部へ送らない
- 有効行を含めて送らないこと。失敗行のみに絞る
- ロック中の扱いを変えないこと。使えない案内を出す
