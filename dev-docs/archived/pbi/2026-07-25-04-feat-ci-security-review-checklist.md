# PBI: CI/CDセキュリティレビューチェックリストの作成

## ユーザーストーリー

開発者として、GitHub Actionsワークフローをレビューする際に、セキュリティリスクを見逃さないためのチェックリストがほしい。なぜなら、`${{ }}` 式展開の危険性やシークレット漏洩のリスクを体系的にチェックする仕組みがなく、個別のインシデント対応に終始しているから。

## ビジネス価値

- CI/CDパイプラインのセキュリティ脆弱性を未然に防止
- セキュリティレビューの効率化と品質向上
- インシデント発生率の低減

## BDD受け入れシナリオ

```gherkin
Scenario: 新規ワークフロー作成時にチェックリストが参照される
  Given 開発者が新しいGitHub Actionsワークフローを作成する
  When PRレビューが行われる
  Then チェックリストの項目がレビューコメントとして参照される
  And 主要なセキュリティリスクがチェックされる

Scenario: 既存ワークフローの監査にチェックリストが使用される
  Given 既存のGitHub Actionsワークフローが存在する
  When 定期監査が実施される
  Then チェックリストに基づいてセキュリティリスクが評価される
  And 改善が必要な項目が特定される
```

## 受け入れ基準

- [ ] `docs/CI_SECURITY_CHECKLIST.md` が作成されている
- [ ] 以下の項目が含まれている:
  - [ ] `${{ }}` 式の安全な使用法（env変数経由での展開）
  - [ ] シークレットの適切な取り扱い（ログ出力禁止）
  - [ ] 外部入力（version、branch名等）の検証
  - [ ] 権限の最小化（permissions設定）
  - [ ] サードパーティアクションのピン留め
- [ ] 各項目に「なぜ危険か」「どう修正するか」の具体例が含まれている
- [ ] PRテンプレートにチェックリストへの参照が追加されている

## テスト戦略（t_wadaスタイル）

### ドキュメントレビュー
- セキュリティ専門家がチェックリストの内容をレビュー
- 既存のインシデントがチェックリストで検出可能か検証

### 実地検証
- 既存のワークフローをチェックリストで監査し、検出精度を確認
- 新規ワークフロー作成時にチェックリストが参照されることを確認

## 実装アプローチ

- **Outside-In**: 過去のインシデントから逆算して必要なチェック項目を特定
- **Red-Green-Refactor**: チェックリストを実際に適用してみて、不足項目を追加

🟡中（2pt）

## 技術的考慮事項

- 作成場所: `docs/CI_SECURITY_CHECKLIST.md`
- 参照場所: `.github/PULL_REQUEST_TEMPLATE.md`
- 対象: `.github/workflows/` 配下の全ワークフロー

## 実装者向け注記

### 実装手順
1. 過去のインシデント（コマンドインジェクション、ログ漏洩等）を洗い出す
2. 各インシデントからチェック項目を抽出
3. GitHub Actions公式のセキュリティベストプラクティスを参照
4. チェックリストをMarkdown形式で作成
5. PRテンプレートに参照リンクを追加

### 落とし穴
- チェックリストが長すぎると実用性が低下する
- 具体的なコード例がないと開発者が理解できない
- 定期的な更新プロセスを定義しないと陳腐化する

## Definition of Done

- [ ] チェックリストが作成され、PRテンプレートに参照が追加されている
- [ ] 既存のワークフロー至少くとも1つを監査し、有効性を確認
- [ ] チームメンバーがチェックリストを理解し、使用できる
