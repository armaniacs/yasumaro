## なぜなぜサマリー

- **なぜ上限が 4 箇所に散在するのか** → hop 每に「ここは自分の都合の上限」と個別定義してきたため。validator（最厳値）が実効値を握るが、迂回経路が fail-open。→ 解: 1 テーブル + 意図的分歧は名前付き変種。
- **なぜ update 許可集合が経路で違うのか** → dashboard ゲートを「安全のための狭い subset」として後から足したが、offscreen 直経路（同期系・legacy 移行）の需要が SSOT 側に残ったため。→ 解: SSOT import + named subset + subset テストで政策を文書化。
- **なぜ行 mapper が分裂したのか** → queryPlan 深掘り（PBI-34）が SQL テキストを対象にし、行形（columns・mapper）を対象外にしたため。→ 解: rowCodec で columns を必須化し named 一本化。
- **なぜ requiredKeys が手写しのままか** → API_KEY_FIELDS は SSOT 化したが requiredKeys は「エクスポート時のみ必要な知識」と見なされていたため。→ 解: DEFAULT_SETTINGS からの派生に寄せ、schema 追従を自動化。
- **なぜ archive の shape が 5 hop に重複するのか** → PBI-22 が routing（op ↔ type ↔ workerType）だけをテーブル化し、encode/decode/project を対象外にしたため。→ 解: descriptor 行に codec を携行させ、新 op = 1 行にする。
