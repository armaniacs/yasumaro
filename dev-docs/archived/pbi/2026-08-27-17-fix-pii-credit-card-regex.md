# PBI: piiSanitizer クレカ正規表現 連続16桁未検出

## ユーザーストーリー
プライバシー保護を期待するユーザーとして、クレジットカード番号がハイフンや空白の有無に関わらず確実にマスクされるようにしたい、なぜなら連続16桁のカード番号が未検出のまま保存・送信されるとPII漏洩につながるから。

## 優先度
- 順位: 2 / 17
- RICEスコア: 600（Reach=50 / Impact=1.5 / Confidence=80% / Effort=0.1）
- 根拠: 全PIIマスキング利用者に影響 (Reach=50)。クレカ番号漏洩は中〜高影響だがLuhn検証で一部緩和 (Impact=1.5)。`\d{4}[-\s]\d{4}...` で区切り必須であることは確信80%。正規表現1行追加でEffort極小 (0.1)。

## なぜなぜ分析
- なぜ連続16桁が未検出か: `src/utils/piiSanitizer.ts:83` の `pattern: /\b\d{4}(?:[-\s]\d{4}){3}\b/` が `[-\s]` を必須とし、`4111111111111111` のような連続16桁にマッチしないため
- なぜ区切り必須にしたか: 数値列（例: タイムスタンプやID）との誤検知を抑制するため、区切りを必須とする設計判断があった
- なぜ気づかなかったか: テストが `4111-1111-1111-1111` の区切りありケースのみで検証し、連続16桁のケースが無かった。Luhn検証はあるが検出自体がされないため到達しない
- 解: 連続16桁も検出するパターンを追加（例: `/\b\d{16}\b/` + Luhn検証、または `/\b\d{4}[-\s]?\d{4}[-\s]?\d{4}[-\s]?\d{4}\b/` で区切り任意化。誤検知とのトレードオフを考慮しLuhn検証を維持）

## ビジネス価値
クレカ番号の連続16桁パターンでもPIIマスキングが機能し、ユーザーの決済情報漏洩リスクを低減する。プライバシー保護の完全性を高め、規制（PCI DSS的観点）への準拠を強化。

### 落とし穴
- 連続16桁パターンを追加すると、既存の `driverLicense` (`\b\d{12}\b`) や `frInsee` (`\b\d{15}\b`) との優先順位に注意。`replacements.sort((a,b) => b.length - a.length)` で長い方が優先されるため、16桁は12桁より優先され正しく解決されるが、テストで確認
- `\b\d{16}\b` は `4111111111111111` の前後に `\b`（単語境界）が必要。`"card:4111111111111111"` のように `:` 直後は `\b` が成立するが、`"a4111111111111111b"` はマッチしない。これは既存パターンと同様の挙動で正しい
- Luhn検証が無いと `0000000000000000` のような無意味な16桁もマスクされる。必ず `validateLuhn` が有効であることを確認
