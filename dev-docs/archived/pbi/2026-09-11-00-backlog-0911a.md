## なぜなぜサマリー

- **なぜ token 束縛に穴が残ったのか** → PBI 2026-09-06-01 が「その時点で存在する subtype」のみを表に置いたため。session 系 6 subtype（0906-05）が後から追加された際に表更新が漏れた。→ 解: stagingName を payload に持つ subtype が全て 'staging' 束縛を持つ drift ガードテストで構造的に防ぐ。
- **なぜ pending pages の Save が黙って壊れたままか** → v2 時代の `{type:'record'}` が envelope 移行（VALID_MESSAGE_TYPES 化）で置き換えられず、送信だけが残った。受信側は「未知のタイプは黙って無視」が安全側の設計のため失敗が可視化されない。→ 解: MANUAL_RECORD への移行 + 送信形状のテスト pin。
- **なぜ whitelist が効かないのか** → settings blob マイグレーション（散在キー → 単一 blob）後に、popup 側の直書きだけが散在キーを読み書きし続けたため。→ 解: repository seam 1 本化。
- **なぜ stub が 28 箇所に増えたのか** → archive op が 4 → 14 に増えるたびに「各 backend は対応不可を自身で返す」という方針で行追加したため。政策が 1 箇所に無かった。→ 解: capability seam。
- **なぜ 5000 cap が残っていたのか** → PBI-34 が tag filter の backend 間 divergence を「意図的」として凍結し、dashboard 側は client 代替で凌いだため。→ 解: 3 つの未解決事項（セマンティクス=部分一致維持・性能=実測・divergence=統合）を本ラウンドで決定して統合。
