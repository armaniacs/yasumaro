## 疑問の解決（フェーズ3: なぜなぜ分析）

### 疑問1: 「SqliteClient の 20メソッドは名前が読みやすさを提供しているのでは？ shallow と断定してよいか？」

**なぜ1: なぜ 20メソッドが shallow と見なされるのか？**
→ 各メソッドが `this.call(TYPE, payload, transform)` の1行ラッパーで、interface の幅が implementation と同じだから。呼び出し元が 20個の名前を学ぶコストが、隠蔽される振る舞い（transport + categorization + transform）に見合わない。

**なぜ2: なぜ名前が価値を持つと感じられるのか？**
→ `toggleStarResult(id)` は `call('SQLITE_TOGGLE_STAR', {id}, r=>r.is_starred)` より読みやすい。だが読みやすさは呼び出し側の糖衣構文であり、module の depth（interface 越しに得られる leverage）とは別。名前の価値は `deps.ts` の 1:1 マップでも再現されているが、マップ自体が 20行の重複を生んでいる。

**なぜ3: なぜ deps の 1:1 マップが問題なのか？**
→ `createSqliteClientDeps` が `toggleStar: (id) => sqliteClient.toggleStarResult(id)` と20回繰り返すことで、新しい操作を追加するたびに3箇所（interface / 実装 / deps）に同じ名前を足す必要がある。変更が3箇所に散る = locality が低い。

**なぜ4: なぜ 3ドメインに集約すると locality が上がるのか？**
→ `query` / `mutate` / `maintain` の3つに分けると、新しい query 系の操作は `query` の transform 内部に留まり、interface は変わらない。変更が1 module に局在する。

**なぜ5: なぜ transform を内部 seam に留めるのが depth なのか？**
→ `SqliteRpcClient` の interface は「何ができるか」（query / mutate / maintain）だけを公開し、「どう変換するか」（`res.rows as T[]` / `new Uint8Array(res.data)`）は内部に隠す。呼び出し元が学ぶ interface は小さく、内部の振る舞いは大きい = deep。

**解:** 20メソッドの名前の読みやすさは、3ドメインの intent メソッド（`query` / `mutate` / `maintain`）でも維持できる。transform は内部 seam に留め、interface は intent で集約する。これで depth が上がり、3箇所の重複が解消される。→ PBI 03 の「3ドメイン集約」方針で自律解決。

### 疑問2: 「storage.ts barrel の移行は 50ファイルに影響し、途中で壊すリスクはないか？」

**なぜ1: なぜ 50ファイルの移行がリスクに感じられるのか？**
→ 1つの barrel から 4つの module に散らすため、import パスの置換ミスで `getSettings` が見つからないなどの type エラーが多発する恐れがある。

**なぜ2: なぜ type エラーが怖いのか？**
→ `storage.ts` は `StorageKeys`（types）と `getSettings`（settingsStore）を同じ barrel から再エクスポートしているため、単純に `from '../utils/storage.js'` を `from '../utils/storage/types.js'` に置換すると `getSettings` が消える。

**なぜ3: なぜ 1ファイルで複数の所有 module に分かれるのか？**
→ 1ファイル内で `StorageKeys` と `getSettings` を両方使う場合、2つの import 文に分割する必要がある。機械的な置換では1:1に対応しない。

**なぜ4: なぜバッチ分割が有効なのか？**
→ 10ファイルずつに分けて各バッチで `npm run type-check` を挟むことで、どの所有 module に属するかを1ファイルずつ確認しながら進められる。1バッチの失敗が全体を壊さない。

**なぜ5: なぜ lint seam が必要なのか？**
→ 移行が完了しても新規コードが再び `from '../utils/storage.js'` を書くと後退する。`no-restricted-imports` で禁止すれば、seam が規律を強制し、再発を防げる。Why: 人の記憶ではなく seam が守る。

**解:** 50ファイルの移行は 10ファイルずつのバッチで `type-check` を挟み、1ファイル内で `types.js` と `settingsStore.js` に分割する。完了後は lint seam で再発を防止。→ PBI 04 の「バッチ + lint seam」方針で自律解決。

### 疑問3: 「background → dashboard の import は意図的な共有か、偶然の leak か？」

**なぜ1: なぜ background が dashboard の formatter に依存しているのか？**
→ `deps.ts` が `formatEntriesToMarkdown` を必要とし、既存の実装が `dashboard/obsidianFormatter.ts` にしかなかったため、最も近い実装を import した。

**なぜ2: なぜ dashboard にしかなかったのか？**
→ markdown 生成は当初 dashboard の preview 用に作られ、background の `append_to_obsidian` は後から同じ出力を必要とした。共有の `utils/markdownFormatter.ts` が既に存在するが、deps が古いパスを参照したままだった。

**なぜ3: なぜ utils に既に存在するのに使われなかったのか？**
→ `src/utils/markdownFormatter.ts` と `src/dashboard/obsidianFormatter.ts` の二重実装が併存し、どちらが正か不明確だったため、既存の dashboard 側をそのまま使った。

**なぜ4: なぜ二重実装が併存したのか？**
→ 垂直スライスで dashboard と background が別 PBI で並行開発され、共通化のタイミングがなかった。seam の方向（両方が utils に向かう）が決まっていなかった。

**なぜ5: なぜ utils に集約すると seam の方向が揃うのか？**
→ background と dashboard は別コンテキスト（Service Worker / dashboard page）であり、互いに依存すべきでない。両方が utils という共有の深い module に向かって依存すれば、依存グラフは一方向（inward）に揃い、AI が「markdown は utils にある」と一発で発見できる。

**解:** `utils/markdownFormatter.ts` を正とし、`dashboard/obsidianFormatter.ts` は re-export に縮小、background は utils を直接 import。共有ロジックのみを utils に残し、dashboard 固有の UI 装飾は dashboard に残す。→ PBI 05 の「utils 集約」方針で自律解決。
