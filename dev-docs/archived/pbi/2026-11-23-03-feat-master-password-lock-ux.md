# PBI: マスターパスワードのロック中案内と操作制限

## ユーザーストーリー
履歴を記録する利用者として、ロック中はAPIキーの変更ができないことを画面で理解したい、なぜなら保存成功とAIテスト失敗の分離が起きても原因が分からず設定を繰り返してしまうから。

## ビジネス価値
- ロック中の誤操作を防ぎ、問い合わせと再設定の手戻りを減らす
- 設定順序の案内で保護有効化の失敗を減らす
- 測定方法: ロック中の保存試行が抑止され、案内通りにアンロックへ進めること

## BDD受け入れシナリオ

```gherkin
Scenario: ロック中はAPIキー変更が抑止される
  Given マスターパスワードが有効でロック中の状態がある
  When 利用者が初期設定画面を開く
  Then APIキー欄と保存操作が無効化されアンロック導線が表示される
  And 保存要求は実行されない

Scenario: ロック中のAIテストは原因特定して案内される
  Given マスターパスワードが有効でロック中の状態がある
  When 利用者がAIテストを選ぶ
  Then 復号処理に入る前にロック中の案内が表示される
  And 既存設定は変更されない
```

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 実時間待ちは使わない。表示制御はDOM属性で観測する
- 非機能要件: SW側は無改修でfail-closedを維持する。復号前ゲートの順序は変えない
- ロールバック手段: 画面の無効化判定を戻せば単一形式運用に戻せる。文書のみの差し戻しも可能

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -rn "isLocked\|IS_LOCKED\|masterPassword" src/dashboard --include="*.ts" | grep -v __tests__
grep -rn "isLocked" src/popup --include="*.ts" | grep -v __tests__
grep -rn "マスターパスワード\|ロック中" docs/SETUP_GUIDE.md docs/PRIVACY.md docs/FAQ.md
grep -rn "masterPassword\|session-lock\|authGuard" src/dashboard/__tests__ --include="*.ts"
```

確認結果:
- 画面はAPIキー欄の無効化が未実装。`main.ts` で `isLocked` を参照できるが保存抑止には使われていない
- 文書は順序と制限の記載が不足。`SETUP_GUIDE.md` の一行記載のみで設定順序が不明
- 試験は表示制御の試験が不足。鍵管理の試験はあるが無効化表示の試験は無い
- SW側にアンロック経路は無い。SWは復号できない仕様のため本PBIではSWを変えない

### 実装手順
1. Outside-Inでロック時表示の失敗試験から書く
2. dashboardの初期設定画面に `authGuard.isLocked` 参照の無効化を追加する。APIキー欄と保存操作を止め、アンロック導線を表示する
3. popupはロック中の状態表示とdashboard誘導を出し、記録追加操作を無効化する
4. 文書を更新する。`public/PRIVACY.md` と `docs/PRIVACY.md` は同一内容にする。`SETUP_GUIDE.md` に設定順序を追記し、`FAQ.md` に分離理由を追記する

### 落とし穴
- 無効化は見た目だけにしないこと。保存要求自体を実行しない
- マスターパスワード未設定の利用者の動作を変えないこと。`MASTER_PASSWORD_ENABLED` が偽の場合は従来通り
- 文言は3点に統一すること。保存不可、AI利用不可、記録停止の対応がずれないようにする
- `public/PRIVACY.md` と `docs/PRIVACY.md` の二重更新を忘れないこと
