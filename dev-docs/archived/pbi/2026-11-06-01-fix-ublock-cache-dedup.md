# PBI: uBlockキャッシュの二重保持を解消し設定エクスポートを軽くする

## ユーザーストーリー
重いフィルタリストを使うユーザとして、設定エクスポートがサイズ上限で失敗しないでほしい、なぜなら現状は `ublock_sources` と `ublock_rules` に同内容が二重に保存され (各9.4MB、計約19MB)、28MB設定が10MiB上限に当たって移行もバックアップもできないから

## ビジネス価値
- 設定エクスポート/暗号化バックアップがフィルタ利用者でも成功するようになる (実測28MBが10KB台に)
- chrome.storage 消費量の削減とエクスポート時間の短縮
- 測定方法: 代表的な大規模リスト登録状態で `JSON.stringify(settings).length` が10MiB未満になること

## BDD受け入れシナリオ

```gherkin
Scenario: 大規模リスト登録状態でも設定エクスポートが成功する
  Given 複数の大規模uBlockフィルタリストを登録済みである
  When 設定をJSONエクスポートする
  Then エクスポートファイルが10MiB未満である
  And インポート後に同等のブロック動作が再現される

Scenario: ソース再取得でルールが復元される
  Given 移行先でuBlockソース未登録の状態である
  When ソース一覧を再取得する
  Then マージ済みルールが移行前と同等に再構築される

Scenario: 空状態の回帰なし
  Given uBlockソース未登録の状態である
  When 設定をエクスポートしてインポートする
  Then 従来通り空のまま往復する
```

- 空/1件/大量ソースの境界値

## 技術的考慮事項
- 依存関係: なし (本PBI単独で完結)

- 非機能要件: 保存形式の変更は `setAll` 経由のマイグレーション互換を保つこと。セキュリティ面は現状維持 (署名検証の変更なし)

## 実装者向け注記

### 現状コードの確認
(着手前に必ず実行すること)
```bash
# 機能に関連するキーワードでコードを探す
grep -rn "ublock_sources\|UBLOCK_SOURCES" src/ --include="*.ts" | grep -v __tests__
grep -rn "rebuildRulesFromSources" src/ --include="*.ts" | grep -v __tests__
```

### 実装手順
1. Outside-In: まずE2E相当の往復テスト (失敗を確認) から書く
2. `Source` 型と保存処理 (`sourceManager.ts`) がフィルタ本文を丸ごと保持しているか確認し、保持方針を決める (URL+メタのみ保持し本文は再取得、など)
3. `rulesBuilder.ts` の再構築パスと保存形式を整合させ、旧形式の読み込み互換を残す
4. Red-Green-Refactor で各レイヤーを実装し、グリーンになるたびにリファクタリングする

### 落とし穴
- オフライン時に本文なしソースからルールを再構築できない場合の扱い (前回ルールの保持など) を決めておくこと
- `restorableSettings.ts` の `ublock_rules: object` / `ublock_sources: array` 検証と空の正規形 (`defaults.ts`) の整合を取ること
- 実測値の根拠: 2026-11-06 の移行事例で `ublock_sources` 9943546バイト / `ublock_rules` 9943526バイトとほぼ同サイズだった
