# PBI: DESIGN_SPECIFICATIONS.md の現行化

## ユーザーストーリー
開発者として、設計仕様書（SSOT）を現行リリースと一致させたい、なぜなら SSOT のずれは実装判断の誤りの元になるから。

## 優先度
- 順位: 6 / 9（全候補）
- RICEスコア: 3.2（Reach=1 / Impact=1 / Confidence=80% / Effort=0.25人週）
- 根拠: 設計仕様書（SSOT）のずれが実装判断の誤りの元になるため、実装リスクが小さいドキュメント修正の割に防止効果が高い。RICE スコア 3.2 の同点候補が 2 件あり、raw-owned keys 監査（順位 5）はデータ層の欠陥に直接効くリスク軽減効果が大きいため上位、本 PBI はドキュメント修正としてタイブレークで下位の順位 6 とした

## ビジネス価値
設計仕様書（SSOT）のずれをなくし、実装者とレビュアーが仕様書を信頼して判断できる状態にする。ずれた仕様書は誤った前提での実装とレビューを生み、マージ後の手戻りに直結する。

測定方法: 下記 3 点のずれを実装の実測と突き合わせて解消し、以後のレビュー / PR で「設計仕様書と実装のずれ」の指摘が 0 件であること。

- ずれ 1（§9.3 のセクション見出し）: 設計仕様書は `## Web History` と記述するが、製品がデイリーノートに実際に作成する見出しは `# 🌐 ブラウザ閲覧履歴`（README も同記載）
- ずれ 2（§5.2 の URL 上限）: 設計仕様書は「上限超過で記録を拒否」と記述するが、実装・テストは保存済み URL セット（重複チェック用キャッシュ、`src/utils/storage/savedUrlRepository.ts`）での LRU 退避を示す。SQLite の主記録（OPFS/IDB）とは別層で、仕様書の記述がどの層の話か読み取りにくい
- ずれ 3（版数参照）: 文末の参照が「v2.4.1 - v2.4.4」のまま（現行は 6.9.63、機能は約 30 個）

## 実装者向け注記

### 現状コードの確認
（着手前に必ず実行すること）

```bash
grep -n "Web History" dev-docs/DESIGN_SPECIFICATIONS.md README.md
grep -n "MAX_URL_SET_SIZE" src/utils/urlEntry.ts
```

補足: README の実見出しは日本語（`# 🌐 ブラウザ閲覧履歴`）なので、上の grep は README 側には一致しない。README 側は `grep -n "ブラウザ閲覧履歴" README.md` で確認する。

### 実装手順
1. 上記 grep と `grep -n "ブラウザ閲覧履歴" README.md` で 3 点のずれを実測する。版数は `package.json` の `version`（現行 6.9.63）で確認する
2. `savedUrlRepository.ts` と対応テストを読み、§5.2 の実挙動（拒否 / LRU 退避）を確定させる
3. §9.3 のセクション見出しの記述を実際の見出しに修正する
4. §5.2 を実測に合わせて書き直し、保存済み URL セットと SQLite 主記録（OPFS/IDB）の層の区別を明記する
5. 文末の版数参照を更新し、更新方針（例: 版数依存の記述は必要なときだけ書き、リリース時に見直す）を記載する
6. 役割の明記（機能の全体列挙はしない、README と CHANGELOG が機能の正、設計仕様書は「規則・決まり・制約の防止」）を追記する
7. `node scripts/check-docs-chars.mjs` で文字種を確認する

### 落とし穴
- 🌐 は README の実見出しの引用なのでそのまま記載してよい（製品が実際に描画する記号の引用は許可）。削除すると記述が不正確になる
- §5.2 の修正では「拒否」か「LRU 退避」かの実挙動を実装から確認してから書く。両方の記述がコードに存在する可能性がある（`MAX_URL_SET_SIZE` の定義と保存済み URL セットの LRU 退避は別の場所にある）
- URL 上限は保存済み URL セット（重複チェック用キャッシュ）の話で、SQLite の主記録（OPFS/IDB）とは別層。混同して書かないこと
- 機能の全体列挙をしない。機能の正は README と CHANGELOG で、設計仕様書の役割は「規則・決まり・制約の防止」
- SSOT なので修正時に類似の陳腐化記述（他セクションの版数参照など）がないかも確認する
