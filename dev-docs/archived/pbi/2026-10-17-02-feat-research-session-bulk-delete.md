# PBI: リサーチ・セッションのまとめて削除（セッション/ページ/サブツリー）

## ユーザーストーリー
調べものを整理するユーザーとして、リサーチ・セッション画面でセッションやページをまとめて消したい、なぜなら試し調べやセンシティブな閲覧の痕跡を一括で片付けたいから

## 優先度
- 順位: 02 / 2
- RICEスコア: 32（Reach=30 / Impact=2 / Confidence=0.8 / Effort=1.5）
- 根拠: 利用者はセッション機能利用者に限定されるが、削除できない不便は明確。一時停止（01位・RICE 160）より影響範囲が狭く工数が大きいため後に着手する。依存関係はない

## ビジネス価値
- 誤って混ざった調べもの（画像1枚目のように買い物・投資・回線が1セッションに混在）を単位ごとに消せる
- 測定方法: セッション画面からの削除実行回数、削除後の再表示の正確性、誤削除の問い合わせゼロ

## BDD受け入れシナリオ

```gherkin
Scenario: セッションをまとめて削除する
  Given リサーチ・セッション画面に複数セッションが表示されている
  When  セッション行にチェックを入れて削除を選び、確認で「本当に削除」を押す
  Then  選んだセッション内の全ページが削除され、一覧から消える

Scenario: ページとサブセッションを選んで削除する
  Given セッションを開いてページ行とツリー中間ノード（流入元グループ）が見えている
  When  ページ行と中間ノード（配下サブツリーごと）を選んで削除を確定する
  Then  選んだページとサブツリー配下のページだけが削除され、他は残る

Scenario: 部分失敗したら分かる
  Given 複数件を選んで削除する
  When  途中の1件の削除が失敗する
  Then  成功分は消え、失敗分は残ったままトーストで失敗件数が分かる
```

## 受け入れ基準
- [ ] セッションの summary 行にチェックボックスがある
- [ ] セッション内のページ行にもチェックボックスがある
- [ ] ナビゲーションツリーの中間ノードは配下サブツリーごとの削除として扱える
- [ ] 履歴画面と同じ2段階確認（選択→削除ボタン→バルクバー内の「本当に削除」）である。確認には件数・期間・代表ドメイン/タグを表示し、残りは再グループ化される旨を添える（deep-dig決定）
- [ ] スター付きも確認さえすれば消せる（特別な保護はしない）
- [ ] 未選択時は削除ボタンが押せない。選択件数表示がある
- [ ] 削除後は一覧が再取得・再グループ化され、他パネルと不整合がない
- [ ] 日英の文言（data-i18n）とキーボード操作・フォーカスがWCAG 2.1 AA相当である

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- セッション選択→確認→削除→再表示のハッピーパス
- ページ＋サブツリー選択削除のユーザーシナリオ

### 統合テスト
- 部分失敗（一件目で失敗したら停止）のトースト通知（履歴画面 `sqliteHistoryPanel-bulkConfirm` パターンを踏襲）
- 削除後の再 fetch と件数表示（23件・単独11件など）の更新

### 単体テスト
- 選択状態（セッション/ページ/サブツリー→ID集合展開）の境界値（空・全選択・重複選択）
- `groupResearchSessions` の既存振る舞いが変わらないこと（回帰）

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

## 見積もり
5 SP（要チームでの見積もり。チェックUI＋サブツリー展開＋2段階確認＋再取得を含む）

## 技術的考慮事項
- 依存関係: なし（一時停止 PBI とは独立）
- 削除対象は表示用セッションではなく配下の履歴レコードID（`SessionInput.id` 集合）。セッションは `groupResearchSessions` の grouping に過ぎない
- 削除 API は履歴側の既存削除経路を再利用する（`sqliteHistoryPanelView.ts` の `onDelete`/`onDeleteSelected`/`onDeleteSelectedConfirm` と Panel 側実装を参照）。新規の削除経路を作らない
- サブツリー削除は `buildSessionTree` のノード配下レコードIDの列挙として実装する
- 非機能要件: 最大100セッション表示・大量選択でもブロックしない。MV3 CSP（`innerHTML` はクリア用途のみ、`textContent`/`escapeHtml` 経由）
- 他パネルへの影響: 同一レコードを参照する履歴・ドメイン分析と不整合を起こさないよう、削除後は当該期間の再 fetch を行う

未実装確認済み（2026-10-17）: `researchSessionsPanel.ts` に削除・選択の配線は存在しない。削除は履歴パネルのパターン流用が前提。

### 実装手順
1. E2E（失敗）→統合（失敗）→単体（失敗）の順にテストを書く
2. セッション summary 行・ページ行・ツリー中間ノードにチェックボックスを追加（`renderSession`/`renderTree`/`populateRecord` の拡張）
3. 選択ID集合＋件数表示＋バルクバー（2段階確認）を履歴パターンで実装
4. 既存削除経路でID一括削除→成功時に対象期間を再 fetch して再グループ化
5. i18n 日英キー追加＋a11y（aria-label・フォーカス管理）対応

### 落とし穴
- セッション自体にIDはない。summary 行のチェックは「配下レコードID全選択」として扱うこと
- ツリー表示とフラット表示（`hasNavTrail` 分岐）の両方で選択が効くこと。片方だけの実装にしない
- フィルタ・期間・gap 変更で選択が古くならないよう、再グループ化時は選択をリセットまたは再マッピングする
- 技術レイヤーで PBI を割らない（フロント/バックで分割しない）。価値単位は「選んで消せる」こと

## 深掘りセッション ― 2026-10-17

### 挑戦した仮定
| 仮定 | リスク | 発見 | 決定 |
|------|--------|------|------|
| 履歴の `deleteLog(id)` 流用で足りる | 高（実現可能性） | researchパネルはmodelなし・`lastRows` キャッシュで、履歴の `selectedIds` 状態をそのまま使えない | 新規削除経路を作らず、ID集合→既存削除API→期間再fetchの方針を維持。選択状態は当パネル側に新設する |
| 2段階確認・Undoなし・スター無保護で足りる | 高（ユーザー行動） | 混在セッションの巻き添えは復元不可。本体方針は維持で合意 | 維持。ただし確認を詳細化（下記）して後悔を減らす |
| 削除後の再グループ化は直感的 | 中（依存） | 残りが前後セッションと再結合して「消していないものが動いた」に見える | 確認文と完了トーストに再グループ化の旨を添える |
| 他パネルとの整合は再fetchで足りる | 中（依存） | 履歴側のキャッシュ無効化（`invalidateCache`）と当パネルの `lastRows` 更新の両方が要る | 削除後は対象期間の再fetch＋再グループ化をDefinition側の手順に固定 |
