# PBI: confirm token の防御範囲を評価し、payload 署名への置き換えを判断する

## ステータス: ✅ 完了（2026-09-16）— 提案した置き換えは実施しないと決定

セキュリティ方針を確認したうえで、**現状維持 + ドキュメント修正**を選択した。本 PBI が提案していた payload 署名への置き換えは**実施しない**。

### 決定の根拠

想定脅威は「外部からの攻撃」、ダッシュボードの XSS は対象外と確定した。この前提では、トークンの2段階は攻撃者に対して追加の障壁を持たない（外部からの到達はトークンより手前の3層で阻止されている。詳細は下記「分かったこと」）。

一方で、現状の実装は [[2026-09-16-01-fix-archive-e2e-flaky]] の再発行により実用上の問題なく動作しており、実機確認も済んでいる。往復1回のコストも許容範囲と確認した。

**動作しているものを置き換えるリスクを負うより、何が実際に守っているのかを記録するほうが価値が高い**と判断した。

### 実施したこと

- `src/messaging/sqliteOperationSecurity.ts` — 冒頭コメントに防御層の実態を明記。「トークン必須だから安全」という誤った根拠付けを防ぐ注意を追加
- `dev-docs/SECURITY_REVIEW_GUIDE.md` — 脅威モデルに「誰が破壊的操作を呼べるか」の節を追加

### 再検討する条件

以下のいずれかが成り立つなら、この分析を出発点に新しい PBI を起こすこと。

- ダッシュボードが信頼できない HTML を描画するようになり、XSS を脅威モデルに含める必要が生じた
- `externally_connectable` を宣言する必要が生じ、防御層1が失われた
- 再発行の回避策では吸収しきれない頻度で SW 終了による失敗が観測された

以下の分析は、その際の資料として残す。

## ユーザーストーリー

メンテナとして、破壊的操作の認可が Service Worker のライフサイクルに左右されない形であってほしい。なぜなら現在の confirm token は MV3 の SW 終了で失われる構造的な弱さを持ち、往復も1回余分に必要だから。

## 優先度

- 順位: 未定（着手前に判断が要る）
- 根拠: 現在の実装は [[2026-09-16-01-fix-archive-e2e-flaky]] の再発行で実用上は動いている。これは設計の筋を良くする提案であり、不具合対応ではない

## 背景

PBI 2026-09-16-01 で confirm token の揮発問題を調査した際、なぜなぜ分析から**トークン機構が想定された防御を果たしていない**ことが判明した。

### 分かったこと

**トークン発行は保護されていない。** `create_confirm_token` は `TOKEN_EXEMPT_OPS` に含まれ、トークン無しで誰でも呼べる（`src/messaging/sqliteOperationSecurity.ts`）。

したがって送信者検証を通過できる主体は、**いつでも自力でトークンを取得できる**。トークンは「偽造メッセージを止める」機能を持っていない。

さらに 2026-09-16 の議論で、外部からの到達は**トークンより手前の3層**で完全に阻止されていることを確認した。

1. **`externally_connectable` がマニフェストに無い**（ビルド後の manifest で確認済み）。Web ページも他拡張も `chrome.runtime.sendMessage` で到達できず、ブラウザが配送を拒否する
2. **`checkSenderTrust` が `sender.id === chrome.runtime.id` を要求**（`src/background/handlers/senderTrust.ts`）。この id はブラウザが付与し詐称できない
3. **`DASHBOARD_SQLITE` は `extension-only` 登録**。自拡張の content script すら弾かれる

つまりトークンに到達する主体は既に「自拡張の拡張ページ」に限られており、**外部攻撃者に対する追加の障壁はゼロ**である。

### 実際に果たしている役割

1. **パラメータの束縛**（scopeHash）— 発行時と実行時で引数が変わっていないことの保証。これが実質的な価値
2. **意図の明示** — 「この操作をこの引数で」と2段階で宣言させる
3. **多層防御** — 送信者検証が破れた場合の第2の壁。ただし発行も同じ経路を通るため効果は限定的

### 現在の構造が抱える弱さ

- トークンは `chrome.storage.session` に保存され、**MV3 の SW 終了で揮発する**。発行から検証までの間に SW が落ちると、TTL 内かつ未使用の正当なトークンでも拒否される（2026-09-16-01 で再発行により回避したが、構造自体は残っている）
- 操作のたびに発行と実行で**2往復**必要

## 提案

「発行 → 検証」の2段階をやめ、**送信時に payload から導出した署名を1回で送る**設計に変える。

- 署名鍵は SW 側が保持し、送信側には渡さない…のではなく、実質的価値である「パラメータ束縛」を満たす形を設計する
- SW 終了の影響を原理的に受けない（保存すべき状態が無い）
- 往復が1回減る

### 設計上の論点

- **何を防ぎたいのかの再定義が先**。現在のトークンが偽造を防げていない以上、「送信者検証で十分」という結論もありうる。その場合は scopeHash 相当のパラメータ束縛だけを残す形になる
- 単回使用（リプレイ防止）をどう担保するか。署名だけでは同じ payload を何度でも送れる。nonce や操作の冪等性で代替できるかの検討が要る
- `TOKEN_EXEMPT_OPS` の fail-safe 設計（新規操作は既定でトークン必須）は維持したい。この良い性質を壊さない移行方法が要る

## 受け入れ条件

置き換えを行う場合に満たすべき条件として定義していたもの。**現行実装（置き換えなし）でも3件とも満たされている**ことを確認済みで、これも実装を見送る判断の根拠となった。

```gherkin
Given 破壊的操作のリクエスト
When 引数が発行時から改竄されている
Then 操作は拒否される
# 現行: scopeHash を受信 payload から再導出して厳密比較（fail-closed）

Given 破壊的操作のリクエスト
When Service Worker が発行から実行までの間に終了する
Then 操作は拒否されず、正常に完了する
# 現行: dashboardGateway が mismatch 時に1回だけ再発行して再送（PBI 01）
#       実機でも SW アイドル終了後の破壊的操作が成功することを確認済み

Given 新しい DASHBOARD_SQLITE 操作が追加される
When 認可の設定を書き忘れる
Then 既定で保護される側に倒れる（fail-safe が維持される）
# 現行: TOKEN_EXEMPT_OPS は除外リスト方式。未記載の操作は自動的にトークン必須
```

## 備考

着手前に「現在のトークンは何を守るべきか」をセキュリティ方針として確定させること。それが決まらないまま実装を変えると、防御の意図が曖昧なまま別の形に移し替えるだけになる。
