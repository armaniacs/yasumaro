# PBI: 閲覧ログの寛容インポート本体

## ユーザーストーリー
旧版の履歴を持つ利用者として、欠損行があっても有効行を取り込みたい、なぜなら全件中断では移行が止まり履歴を失うから。

## ビジネス価値
- 旧形ファイルの有効行が取り込めるようになる
- 修正不能行の理由と件数が分かり直し方が特定できる
- 測定方法: 旧形ファイルの有効行の取込と理由報告が完了すること

## BDD受け入れシナリオ

```gherkin
Scenario: 旧形ファイルの有効行が取り込まれる
  Given 別名や別構造を含む旧形の履歴ファイルがある
  When 利用者が移行取込を選ぶ
  Then 有効行が取り込まれ件数と理由内訳が報告される

Scenario: 修正不能行は理由つきで報告される
  Given 修正不能な行を含む履歴ファイルがある
  When 利用者が取込を選ぶ
  Then 有効行だけ取り込まれ修正不能行の理由と件数が示される
  And 0件時の文言は理由つきになる
```

## 受け入れ基準
- [x] 現行rows配列に加え旧キー形式と単独配列が受け付けられる
- [x] 別名の日時と表題と要約と標識が読替えられる
- [x] 同一ファイルの再取込で二重登録が起きない
- [x] `npm run validate` が通る

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 旧形ファイルの取込から報告までの操作確認

### 統合テスト
- 形状別の受入れ
- 再取込の冪等

### 単体テスト
- 別名読替えの境界値
- 報告内容の表示内容
- 0件時文言の分岐

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 実時間待ちは使わない。形状と報告は小さな合成資料で検証する
- 非機能要件: 署名方式は変えない。現行路は維持し移行路は確認後に素通しする。上限と検証順序は維持する
- ロールバック手段: 寛容化の入口を無効化すれば現行の厳密取込に戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -rn "importFromJson\|importValidatedRows\|validateImportRow" src/dashboard --include="*.ts" | grep -v __tests__
grep -rn "validateImportRow\|INSERT_IGNORE" src/offscreen src/messaging --include="*.ts" | grep -v __tests__
```

確認結果:
- 通常取込と移行取込の2経路で確定済み。AI修復の入口は未実装
- 取込は重複無視の性質を持ち、同一urlと日時は既存優先で読飛ばされる
- 旧形の別名や別構造の受入れは未実装。行別理由の報告も不足

### 実装手順
1. Outside-Inで旧形取込の失敗試験から書く
2. 形状判定を追加する。現行rows配列に加え旧キー形式と単独配列を受け付ける
3. 別名を読替える。日時と表題と要約と標識の対応を共通化する
4. 報告を追加する。件数と理由内訳と先頭事例を示し、0件時の文言は理由つきにする
5. 再取込の冪等を試験で固定する

### 落とし穴
- 必須のurlと日時は補完しないこと。既定補完は対象外
- 署名方式を変えないこと。現行路の判定は残す
- 上限を緩めないこと。大きさ確認と行数上限は維持する
