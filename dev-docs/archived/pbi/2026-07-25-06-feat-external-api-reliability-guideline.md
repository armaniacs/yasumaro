# PBI: 外部API連携の信頼性設計ガイドラインの策定

## ユーザーストーリー

開発者として、外部APIと連携する機能を実装する際に、信頼性を確保するための設計ガイドラインがほしい。なぜなら、ポーリング、タイムアウト、リトライ、エラーハンドリングの基準がなく、CWS公開ステップのような障害が再発するリスクがあるから。

## ビジネス価値

- 外部API連携時の障害を未然に防止
- 障害発生時の復旧時間を短縮
- 開発者の設計判断負荷を低減

## BDD受け入れシナリオ

```gherkin
Scenario: 開発者が外部API連携機能を実装する際にガイドラインが参照される
  Given 開発者が外部APIと連携する新機能を実装する
  When 設計レビューが行われる
  Then ガイドラインに基づいて信頼性設計が検証される
  And ポーリング、タイムアウト、リトライ戦略が適切に設計されている

Scenario: 既存の外部API連携がガイドラインに準拠しているか監査できる
  Given 外部APIと連携する既存機能が存在する
  When 定期監査が実施される
  Then ガイドラインに基づいて信頼性設計が評価される
  And 改善が必要な項目が特定される
```

## 受け入れ基準

- [ ] `docs/EXTERNAL_API_RELIABILITY_GUIDELINE.md` が作成されている
- [ ] 以下の項目が定義されている:
  - [ ] **タイムアウト設定**: 接続タイムアウト、読み取りタイムアウトの推奨値
  - [ ] **リトライ戦略**: 指数バックオフ、最大リトライ回数、リトライ可能なエラー
  - [ ] **ポーリング設計**: ポーリング間隔、最大待機時間、タイムアウト時の挙動
  - [ ] **エラーハンドリング**: 一時的エラーと永続的エラーの区別、ユーザーへの通知方法
  - [ ] **サーキットブレーカー**: 連続失敗時の機能停止閾値
  - [ ] **冪等性**: 再試行の安全性確保
- [ ] 各項目に具体的なコード例が含まれている
- [ ] 既存の外部API連携コード（CWS API、Obsidian API等）への適用方針が明記されている

## テスト戦略（t_wadaスタイル）

### ドキュメントレビュー
- インフラエンジニアがガイドラインをレビュー
- 既存のインシデントがガイドラインで防止可能か検証

### 実装検証
- ガイドラインに基づくサンプル実装の作成
- 既存コードへの適用テスト

## 実装アプローチ

- **Outside-In**: 過去のインシデントから必要な設計要素を逆算
- **Red-Green-Refactor**: ガイドラインを実際のコードに適用してみて、不足項目を追加

## 技術的考慮事項

- 作成場所: `docs/EXTERNAL_API_RELIABILITY_GUIDELINE.md`
- 対象: CWS API、Obsidian Local REST API、Gemini API、OpenAI API等の外部連携
- 既存の実装パターン（`fetchWithTimeout`等）を参考にする

## 実装者向け注記

### 実装手順
1. 過去のインシデント（CWS公開ステップの障害等）を洗い出す
2. 外部API連携時の障害モードを分類
3. 各障害モードに対する設計パターンを定義
4. 既存の実装パターンを調査・参考にする
5. ガイドラインをMarkdown形式で作成

### 落とし穴
- ガイドラインが抽象的すぎると実装者が困る
- 全てのAPIに一律適用すると非効率になる場合がある
- API側の仕様変更でガイドラインが陳腐化する

## Definition of Done

- [ ] ガイドラインが作成され、チームに共有されている
- [ ] 既存の外部API連携コード至少くとも1つに適用し、有効性を確認
- [ ] チームメンバーがガイドラインを理解し、使用できる
