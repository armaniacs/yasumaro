# PBI: RecordingContext god-object を崩壊する

## ユーザーストーリー
開発者として、`RecordingContext` の30フィールド以上を持つ god-object を、ステップごとの型付き入力システムに置き換えたい。なぜなら、現在の実装では各ステップが任意のフィールドを読み書きし、ステップ間の依存関係が型レベルで見えないから。

## ビジネス価値
- 各パイプラインステップの依存関係が型レベルで可視化される
- テスト時にステップが実際に使用するフィールドだけを構築できる
- 新規ステップ追加時のフィールド衝突リスクが排除される

## BDD受け入れシナリオ

```gherkin
Scenario: ステップの依存関係が型レベルで見える
  Given パイプラインステップが StepInput<T> を受け取る
  When ステップが未使用のフィールドにアクセスしようとする
  Then TypeScript がコンパイルエラーを報告する

Scenario: テストでの軽量コンテキスト構築
  Given truncateContentStep が content フィールドのみを使用する
  When truncateContentStep のテストを書く
  Then content フィールドだけを含むオブジェクトでテストできる
  And 30フィールドすべてを構築する必要がない

Scenario: 既存ステップの動作維持
  Given 13のパイプラインステップがすべて存在する
  When RecordingContext を StepInput<T> に変更する
  Then 既存のテストがすべてパスする
  And パイプラインの実行結果が変わらない
```

## 受け入れ基準

- [ ] 各ステップが自分が必要とするフィールドを明示的に宣言している

- [ ] `npm run validate` が通過している

## 実装者向け注記

### 現状コードの確認
```bash
# RecordingContext のフィールド数を確認
grep -n "?" src/background/pipeline/types.ts | head -5
# 各ステップが使用するコンテキストフィールドを確認
grep -n "context\." src/background/pipeline/steps/*.ts | head -30
```

### 実装手順
1. 各ステップが使用するフィールドを洗い出す
2. StepInput<T> 型を定義（各ステップごとの狭い入力型）
3. パイプラインがステップ間で型安全にデータを渡すよう修正
4. 既存ステップの関数シグネチャを更新
5. テストを更新

### 落とし穴
- RecordingContext の一部のフィールドはオプショナル（`?`付き）。StepInput でもオプショナルを維持すること
- パイプラインの buildResult/buildErrorResult がコンテキストの一部を読み取る。それらも型安全に修正すること
