# PBI: マスターパスワード忘れ時の削除復旧

## ユーザーストーリー
合言葉を忘れた利用者として、旧パスなしでの維持はできず削除だけを選べるようにしたい、なぜなら解除不能のまま設定が止まるよりAPIキー再入力で復旧できる方が被害が小さいから。

## ビジネス価値
- 忘れた利用者が再導入なしに復旧できるようになる
- 旧パスなしでの維持を不可とし、不正な引継ぎを防ぐ
- 測定方法: 忘れ入口から保護無効化とAPIキー削除が完了し、他設定が残ること

## BDD受け入れシナリオ

```gherkin
Scenario: 忘れ入口から削除復旧が完了する
  Given 保護が有効で旧パスが不明の状態がある
  When 利用者が忘れ入口から二重確認を通す
  Then 保護が無効化されAPIキーが削除される
  And 他設定は残り再入力の案内が出る

Scenario: 旧パスなしでの維持は実行されない
  Given 保護が有効で旧パスが不明の状態がある
  When 利用者が通常の解除を選ぶ
  Then 旧パス必須の扱いが維持され維持処理は実行されない
```

- [x] 削除範囲が保護とAPIキーのみに収まる

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 実時間待ちは使わない。状態は保存値で観測する
- 非機能要件: SW側は変えない。復号前ゲートの順序は維持する
- ロールバック手段: 忘れ入口を無効化すれば現行運用に戻せる。削除済み鍵の復元は不可のため案内で明示する

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -rn "removeMasterPassword\|unlockWithPassword" src/utils/storage --include="*.ts" | grep -v __tests__
grep -rn "removeMasterPassword\|masterPassword" src/dashboard --include="*.ts" | grep -v __tests__
```

確認結果:
- `removeMasterPassword` は旧パスか文脈保持を要求し、旧パスなしの削除復旧は未実装
- 対象経路は3経路で確定済み。設定と変更と解除のいずれも旧パス必須
- 本PBIは旧パスなしの維持を追加しない。削除だけの別経路とする

### 実装手順
1. Outside-Inで忘れ入口から完了までの失敗試験から書く
2. dashboardの保護欄に忘れ入口を追加する。二重確認の後に削除処理を実行する
3. 削除対象は保護の認証記録と無効化で消す鍵群およびAPIキーのみとする。他設定は残す
4. 文書に復旧手順と削除範囲を明示する。旧パスなしでの維持は不可と書く

### 落とし穴
- 通常の解除経路を緩めないこと。旧パス必須の判定は残す
- 削除範囲を広げないこと。設定全体の初期化と混同しない
- 完了後に再入力の案内を出すこと。利用者が止まらないようにする
