# PBI: piiSanitizerタイミング閾値の緩和

## ユーザーストーリー
開発者として、piiSanitizerの性能回帰テストを負荷時にも安定させたい、なぜならフルスイート負荷時に500ms閾値を超過して赤になり、リリースCIを止めうるから。

## ビジネス価値
- リリースゲートの誤赤をなくす
- バックトラッキング保護の回帰検出力は維持する（テストの削除はしない）
- 測定方法: 負荷時の実行でも緑が保たれ、保護無効の劣化版は赤になること

## BDD受け入れシナリオ

```gherkin
Scenario: 負荷時も性能試験が緑になる
  Given フルスイート負荷のかかった状態がある
  When piiSanitizerの性能回帰テストを実行する
  Then 閾値内に収まり緑になる

Scenario: 保護無効の劣化は検出される
  Given 保護を無効化した実装がある
  When 同じ性能試験を実行する
  Then 閾値を超えて赤になる
```

## 受け入れ基準
- [ ] 289行目の閾値が実測根拠付きで緩和される
- [ ] 劣化版が赤になることが確認できる
- [ ] 他の閾値試験は変更しない
- [ ] `npm run validate` の該当部分が通る

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- なし（単体試験の閾値変更に留める）

### 単体テスト
- 閾値の境界値確認
- 劣化版の検出確認

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 実測値で根拠を示す
- 非機能要件: 検出力を下げない。2000msは正常と劣化の中間に置く
- ロールバック手段: 閾値1行の差し戻しで戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -n "toBeLessThan" src/utils/__tests__/piiSanitizer.test.ts
```

確認結果:
- 289行目が対象で500ms固定のまま。緩和は未実装
- 272行目は小入力、401行目は既定値、829行目は別物のため対象外
- APIに変更はなし。`sanitizeRegex` の振舞いは変えない

### 実装手順
1. 閾値を2000に変え、実測根拠の注釈を付ける（単独約110ms・負荷最大518ms・劣化版約4000ms）
2. 通常実行と負荷時の両方で緑を確認する
3. 劣化版で赤になることを確認する

### 落とし穴
- 閾値だけ変えて根拠を書かないこと
- 他の閾値を一緒に変えないこと
- 実時間待ちを足さないこと
