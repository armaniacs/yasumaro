## なぜなぜ分析サマリ

### 01 Page Content Pipeline: なぜ10モジュールに分散したのか？
- **なぜ1**: なぜ1ページの準備に10ファイルを読む必要がある？ → 元々 `contentExtractor` と `aiSummaryCleaner` が別責務として作成され、後から `aiSummaryCleaner` が6オプション→15オプションへ肥大化したが、統合されなかった。
- **なぜ2**: なぜ統合されなかった？ → `extractPageContent` の pageState 結合が純粋性検証を困難にし、統合前に純粋化が必要だった。
- **なぜ3**: なぜ純粋化が遅れた？ → 2026-08-17に純粋化されたが、呼び出し元の `optionBuilder` 連携は手つかずだった。
- **示唆**: 純粋化は完了したため、今が統合の好機。10モジュールは全て in-process で外部依存なし → deepening は低リスク。
- **解**: `PageContentPipeline.prepare()` の1 seamに集約し、10モジュールを内部化。

### 02 Recording Pipeline Steps: なぜ13ステップが shallow なのか？
- **なぜ1**: なぜ各ステップが `context in → context out + ErrorStrategy` の同一 interface なのか？ → Pipeline パターンの教科書的適用で、ステップの再利用性を期待した。
- **なぜ2**: なぜ再利用されていない？ → 実際には各ステップは1箇所（`execute()`）からしか呼ばれず、ordering とフラグ相互作用は `execute()` にしか存在しない。
- **なぜ3**: なぜテストがステップ単位なのか？ → ステップ単位の unit テストは書きやすいが、バグはステップ間の相互作用に宿るため、unit テストでは検出できない。
- **示唆**: 再利用の仮定が外れている。ステップは再利用されない shallow wrapper → 内部化して locality を回復すべき。
- **解**: 13ステップを Pipeline 内部の private 関数にし、公開 interface は `record()` のみにする。テストは interface で行う。

### 03 SQLite Domain Repository: なぜ20の wrapper が残ったのか？
- **なぜ1**: なぜ `callDashboard<TReq,TRes>()` 導入後も20の wrapper が残った？ → 前波で generic path は導入されたが、20関数の呼び出し元移行まで手が回らなかった。
- **なぜ2**: なぜ移行が中途半端なのか？ → 各 wrapper は15行のボイラープレートだが、20個で300行あり、1PBIでは収まらなかった。
- **示唆**: generic path の有効性は実証済み。残りは機械的な集約 → 2pdのクイックウィン。
- **解**: domain メソッド（query/search/toggleStar/delete/getCount 等）に集約し、`callDashboard` を private 化。

### 04 Diagnostics Panel: なぜ681行の god module になったのか？
- **なぜ1**: なぜ1ファイルに11セクションが詰まった？ → dashboard パネル追加時に `diagnosticsPanel.ts` をコピペで拡張するのが最も手早かった。
- **なぜ2**: なぜ共通化されなかった？ → 各セクションは `querySelector → makeStatRow` の同一パターンだが、データソース（storage/sqlite/AI）が異なるため共通化の seam が見えなかった。
- **なぜ3**: なぜ seam が見えなかった？ → 収集（query）と描画（makeStatRow）が同一関数内に混在し、分離点が不明だった。
- **示唆**: 収集と描画を分離すれば、`collect() → snapshot` と `render(snapshot)` の2つの seam が自然に現れる。
- **解**: `DiagnosticsCollector`（収集）と `DiagnosticsRenderer`（描画）に分解。snapshot 型で型安全化。

### 05 Settings Repository: なぜ Confidence 60% なのか？
- **なぜ1**: なぜ storage 側の集約に確信が持てない？ → PBI 05 Settings Schema が DOM 側の `data-storage-key` typo を防ぐが、storage 側にも同様の schema が必要か、2つの schema が並立するかが未確定。
- **なぜ2**: なぜ2つの schema が問題？ → 両方が `StorageKeys` を source of truth としつつ、片方が DOM セレクタ、片方が storage アダプタを持つと、キーの追加時に2箇所を編集する必要がある（二重管理）。
- **なぜ3**: なぜ二重管理を避けられない？ → 現状は `StorageKeys` が唯一の source of truth だが、PBI 05 の Schema が `StorageKeys` を参照する形にすれば一元化できる。
- **示唆**: PBI 05 の shape が確定すれば、repository は `StorageKeys` を source of truth として Schema を参照する形で一元化可能。
- **解**: PBI 05 完了後に着手し、repository が Schema を包含する形で設計。Confidence は着手時点で80%に上昇する見込み。現時点では Speculative として最後に配置。
