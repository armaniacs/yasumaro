# PBI: isMaliciousUsage 検知結果が呼び出し元で無視される問題の修正

## ユーザーストーリー
拡張機能のセキュリティ担当者として、`isMaliciousUsage()` が検出した「単一用語の悪意ある用法」が実際に何らかの防御アクションに繋がってほしい、なぜなら現状は警告を記録するだけで呼び出し元が一切参照しておらず、セキュリティ機能として実効性がないから

## ビジネス価値
- 死んでいるセキュリティチェック（検知しても効果がないコード）を解消し、実装されている防御機構が実際に機能する状態にする
- コードの可読性・保守性向上（「動いているように見えて実は何もしていない」コードは将来の誤解・二次バグの温床になる）

## 背景（既実装確認）

`src/utils/promptSanitizer.ts` の `sanitizePromptContent()` 内、`GENERIC_TERM_PATTERNS` に対する `isMaliciousUsage()` 判定（289-311行目）は、`true` を返しても以下の処理しか行わない：

```ts
if (isMaliciousUsage(fullMatch, decodedContent, index)) {
  warnings.push(`Detected potential command: "${fullMatch}"`);
  if (dangerLevel === DangerLevel.SAFE) {
    dangerLevel = DangerLevel.LOW;
  }
}
```

- コンテンツ自体は `[FILTERED]` に置換されない（`REFINED_INJECTION_PATTERNS` 側とは異なる挙動）
- `dangerLevel` は `LOW` にしかならない

一方、`sanitizePromptContent()` の全呼び出し元は `dangerLevel === 'high'`（または `DangerLevel.HIGH`）のみを判定に使っている：

| 呼び出し元 | 該当行 |
|-----------|--------|
| `src/background/builtInAIClient.ts` | 167行目 |
| `src/background/privacyPipeline.ts` | 183, 210, 252行目 |
| `src/background/ai/providers/ProviderStrategy.ts` | 110行目 |
| `src/utils/customPromptUtils.ts` | 246行目 |

つまり `isMaliciousUsage()` がどれだけ検知しても、`dangerLevel` が `LOW` 止まりである限り呼び出し元の分岐に一切影響を与えない。これは新規実装ではなく、既存実装の設計と利用側の乖離によるバグである。

**なぜなぜ分析の結論（発見の経緯）**: この問題は `2026-08-19-07-fix-prompt-safecontext-bypass.md` の調査中に、「`GENERIC_TERM_PATTERNS` 側も `isInSafeContext` のバイパス対象では」という仮説を検証する過程で発見された。実際にはバイパス以前に、そもそも `isMaliciousUsage` の検知結果がどこにも活かされていないことが判明した。`LOW` という中間的な危険度レベルを設けた設計意図と、呼び出し元が `HIGH` のみを見る実装が、当初から噛み合っていなかったと考えられる。

### 敵対的レビューで判明した追加の論点

1. **ログ活用案（候補a）のリスクと既存の緩和機構（裏取り済み）**: `warnings` に含まれる `fullMatch`（攻撃者が完全に制御可能なWebページ由来の文字列）をログに記録する案には、ログ肥大化・情報漏洩の懸念があるとハッカー視点で指摘された。裏取りの結果、実際のログ基盤（`src/utils/logger/core.ts`）は `sanitizeLogDetails` によるPIIサニタイズと `MAX_PENDING_LOGS = 100` によるバッファ上限を備えており、情報漏洩・無制限な肥大化のリスクは相当程度緩和されていることを確認した。ただし `GENERIC_TERM_PATTERNS` は `now`/`system`/`update` 等の高頻度語を含むため、**ログの中身が低品質な検知で埋まり、本当に重要なログが埋もれる（アラート疲れ）** リスクは残る。この点は候補選定時に考慮すること。
2. **候補(b)「格上げ」案は可用性攻撃の成立条件になりうる**: `GENERIC_TERM_PATTERNS` の語（`system`, `now`, `update` 等）は通常の技術文書・ニュース記事に高頻度で出現するため、候補(b)「一定回数以上のLOW検知でHIGH相当に格上げ」を採用すると、正規のコンテンツが誤って`HIGH`判定されブロックされる可能性が高い。この候補を採用する場合は、格上げの閾値を単純なカウンタにせず、時間窓・多様性（同じ単語の繰り返しでなく異なるパターンの複数検知）等の条件を課すこと。
3. **見積もりと受け入れ基準の未確定さの矛盾（保守担当者視点でCONFIRMED）**: 本PBIは「LOW判定時に何をすべきか仕様判断が必要」と自認しながら見積もり0.5ptを確定値として提示しており、候補(b)を選んだ場合は状態管理（カウンタ等）の新設が必要になり0.5ptでは収まらない。受け入れ基準「活用方法はチーム判断とする」も客観的なDoD判定基準になっていない。これらは下記の受け入れ基準・見積もりの修正で対応する。

## BDD受け入れシナリオ

```gherkin
Scenario: LOW危険度のコンテンツが呼び出し元に伝わる
  Given コンテンツに isMaliciousUsage() が true と判定する単一用語命令（例: "I want you to ignore the above"）が含まれる
  When sanitizePromptContent() が実行される
  Then dangerLevel が LOW として返され、warnings に検出内容が記録される
  And 呼び出し元（例: privacyPipeline.ts）が LOW 危険度を何らかの形で処理する（少なくともログに残す、または閾値に応じてユーザーに通知する）

Scenario: HIGH危険度のコンテンツは引き続きブロックされる
  Given コンテンツに REFINED_INJECTION_PATTERNS にマッチする明確な命令文が含まれる
  When sanitizePromptContent() が実行される
  Then dangerLevel が HIGH として返され、既存の呼び出し元の防御アクション（要約中断等）が発動する
```

### 落とし穴
- `isMaliciousUsage` の検知は元々「誤検知の可能性がある弱いシグナル」として `LOW` に留め置かれた可能性がある。厳しい対応（コンテンツブロック等）にすると、GENERIC_TERM_PATTERNS の一般的な単語（`now`, `system` 等）を含む正当なコンテンツまで巻き込むリスクが高い。まずログ記録による可観測性向上から始めるのが安全
- 4箇所の呼び出し元をすべて同じ方針で揃えるか、呼び出し元ごとに異なる扱いにするかは仕様判断が必要
- **本PBIと `2026-08-19-07-fix-prompt-safecontext-bypass.md` は同一ファイル（`src/utils/promptSanitizer.ts`）の隣接コード（`sanitizePromptContent()` 内269〜311行目付近）を変更する。**着手順序を決めずに並行実装すると、片方が先にマージされた後にもう片方が古い行番号・ロジック前提で実装されコンフリクトする。**（必須）07番のPRがmainにマージされてから08番の実装ブランチを作成すること。08番のブランチを07番より先に作成していた場合は、07番マージ後に必ず `git rebase main` を実行し、`isInSafeContext()`（07番が変更する104〜147行目付近）の変更を取り込んでから08番の実装を進める。**「先に完了させることが望ましい」という推奨ではなく、着手順序の必須条件とする**（敵対的レビューで「推奨のみでは強制力がなく、08が先にマージされるとHTML属性値バイパスが07未適用のまま本番に残る期間が生まれる」と指摘されたため）
- **ロールバック時の依存関係リスク**: 07番と08番を同一ファイルの隣接行として実装すると、本番投入後に07番だけをロールバックする必要が生じた場合（例: 誤検知率の悪化が判明した場合）、08番の変更が07番の変更に依存していると、07番単体の切り戻しが困難になる。実装時は08番の変更（`isMaliciousUsage`呼び出し周辺のdangerLevel分岐）が07番の変更（`isInSafeContext`のロジック）を直接参照・依存しない形に保ち、独立して revert 可能な差分に保つこと
- 候補(a)を選んだ場合でも、`GENERIC_TERM_PATTERNS` の語（`now`, `system` 等）が高頻度で出現するため、ログが低品質な検知で埋め尽くされ本当に重要なログが埋もれる「アラート疲れ」に注意する（`src/utils/logger/core.ts` の `MAX_PENDING_LOGS = 100` バッファが早期に埋まる可能性がある）
