# PBI: issue report トリガーに再入 guard とエラーハンドリングを追加する

## ユーザーストーリー
利用者として、診断画面の不具合報告ボタンを素早く二度押したり収集処理が失敗したりしても、画面が無反応になったり例外で止まったりせず、状態が分かる表示を受けたい、なぜなら二重実行による未処理の拒否は原因究明を難しくし、利用者の報告手順自体を壊すから

## 優先度
- 種別: fix
- 順位: 6
- RICEスコア: 8.0（Reach=2 / Impact=1 / Confidence=1.0 / Effort=0.25週）
- 根拠: 発生頻度は低いが、二重クリックという自然な操作で未処理の拒否が起きる。修正範囲は単一ハンドラに閉じるため工数は小さい

## ビジネス価値
不具合報告という復旧の入口が壊れない。収集失敗時に沈黙せず状態を示すことで、利用者が再試行できる。再入による例外で診断画面全体の信頼を落とさない

## BDD受け入れシナリオ

```gherkin
Scenario: 処理中に二度押しても二重実行しない
  Given 不具合報告ボタンが表示されている
  When 利用者がボタンを連続で二度押す
  Then 収集処理は1回だけ実行され、開いている表示への再表示による例外は起きない

Scenario: 収集処理が失敗しても未処理の拒否にならない
  Given 診断情報の収集が失敗する
  When 利用者が不具合報告ボタンを押す
  Then 例外は捕捉され、利用者に分かる状態表示で失敗が伝わる

Scenario: 既に開いている表示への再表示で例外にならない
  Given 報告内容の確認表示が既に開いている
  When 利用者が不具合報告ボタンを押す
  Then 再表示による状態例外は起きず、未処理の拒否は残らない
```

## 受け入れ基準
- [x] 報告ボタンの押下処理に実行中判定があり、処理中の再押下は無視される
- [x] 収集から表示までの処理全体が例外捕捉で包まれる
- [x] 既に開いている確認表示への再表示で例外が出ない
- [x] 収集失敗時は利用者に分かる状態表示で伝えられる
- [x] 二重押下と収集失敗の回帰試験が新設され通過する
- [x] 未処理の拒否が残らない

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 対象外(単一ハンドラの振る舞い修正)

### 統合テスト
- 収集処理の拒否時に状態表示へ失敗が反映されること
- 開いている確認表示への再表示で例外が出ないこと

### 単体テスト
- 処理中の二度押しで収集処理が1回だけ呼ばれること
- 収集処理の拒否が捕捉され未処理の拒否にならないこと
- 表示の再表示操作が状態例外を起こさないこと

## 実装アプローチ
- **Outside-In**: まず二重押下と収集失敗の振る舞い試験を書き、Red で再入判定と例外捕捉を追加する
- 接続試験の実行中判定の流儀にならい、報告処理にも実行中判定を持たせる
- 収集から表示までを例外捕捉で包み、失敗は利用者に見える状態表示へ流す
- 確認表示の再表示は状態確認を入れて安全に開く

## 技術的考慮事項
- 依存関係: なし。他の診断機能とは独立
- 遵守すべき方針: 接続試験の再入防止の流儀に合わせ、判定の解放漏れを避ける
- 非機能要件: 失敗時に沈黙しない。利用者の設定や記録内容を状態表示に露出させない
