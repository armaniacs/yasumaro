## RICE スコアリング

```
RICE = (Reach × Impact × Confidence) / Effort
```

Reach は開発者タッチ推定、Impact は 3=圧倒的 / 2=大 / 1=中、Confidence は直接検証済み 80% / 探索のみ 50%、Effort は人日。

- **なぜ実バグ 3 件（01/02/03）が上位なのか** → いずれも「ユーザー操作が静かに失敗する／判定が silently 不一致」で、根本原因は「契約を 1 箇所が所有していない」こと。→ 解: gateway 抽出 / snapshot 拡張で契約の所有者を作り、pin テストで恒久化する。
- **なぜ 04 が Effort 2.5 でも切り捨てないのか** → offline リトライの統計欠落は「診断値の静かな劣化」であり、builder を作らないと次の field 追加でも同じ事故が再発する。→ 解: 政策テーブル化で追加コストを 1 行にする。
- **なぜ 06 は「実バグ」から降格したのか** → 直接検証で planQuery が wire 経路の limit を clamp 済みと確認したため（探索エージェントの主張を訂正）。→ 解: 防御層 + backend 差異封じとして実施し、Impact を 1 に落として RICE を据え置く。
- **なぜ 07 が Worth exploring なのに PBI 化するのか** → badge 政策の分散は繰り返し摩擦を生んでおり、SW 内 setTimeout はプロジェクトルール違反（chrome.alarms 必須）で放置できないから。→ 解: state テーブル + seam で統合し、違反を同時に解消する。
- **なぜ 08 をバンドルにするのか** → 各項は RICE 単独では PBI 化基準未満だが、探索で発見済みの欠陥を台帳だけに置くと「顕在化時に再探索」コストが高い。→ 解: 最小 fix 原則を明記した上で 1 PBI に束ね、直列に潰す。
