# PBI: ROADMAP.md の再同期（出荷済み機能との矛盾解消）

## ユーザーストーリー
機能提案を裁定するメンテナとして、ROADMAP.md を現行リリースと一致させたい、なぜなら矛盾した行を持つ SSOT は次の裁定を誤らせるから

## 優先度
- 順位: 4 / 9（全候補）
- RICEスコア: 6.4（Reach=1 / Impact=2 / Confidence=80% / Effort=0.25人週）
- 根拠: RICE順では4位だが、以後の提案裁定の土台（SSOT の矛盾解消）であるため、実行順ではラウンド冒頭の着手を推奨（ユーザー承認済み）

## ビジネス価値
ROADMAP.md（最終更新 2026-10-17、v6.9.48 時点）の 3 行が出荷済み機能と矛盾し、SSOT の矛盾が次の提案裁定を誤らせる。矛盾の詳細は次の 3 組 6 行。
- C2（新規同期先の追加）と E7（外部ツールへの Webhook/エクスポート連携）: 両行とも Webhook 連携を条件付き「今はしない」とする。実際は Webhook エクスポートが実装・出荷済み（PBI 2026-10-22-05、6.9.62/63。条件・履歴/冪等再送・オプション UI 第 29 パネルまで含む）
- C5（タイムライン再生ビュー）と E5（ブラウジングセッションのタイムライン再生ビュー）: 実使用の摩擦報告まで着手しない前提。実際はセッション再生パネル（panel-session-timeline）と読みかけリマインダーの SW 配線が 6.9.63 で出荷済み
- N11（scroll_ratio / visit_duration 依存の機能は NOT-TODO）と E8（閲覧行動に基づくリマインダーは恒久 NOT-TODO）: 根拠の visit_duration / scroll_ratio が常に NULL という前提は 6.9.63 の pickRecordDiagnostics 受渡し欠落修正で解消済み。実際は読みかけリマインダーが出荷済み

測定方法: ROADMAP の行と CHANGELOG の出荷記録の突き合わせリストで、3 組すべてが根拠付きで解消されていること。以後の提案裁定セッションで「ROADMAP が古い」という指摘が再発しないこと。

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。

```bash
grep -n "C2\|C5\|N11" ROADMAP.md
grep -n "webhook\|リマインダー\|セッション再生" CHANGELOG.md | head -20
```

2026-10-31 時点の行番号参照: ROADMAP.md は N11=79 行、C2=87 行、C5=90 行、E2=111 行、E5=114 行、E7=116 行、E8=117 行。CHANGELOG.md は 6.9.63 が 38〜69 行、6.9.62 が 71〜88 行。ずれる場合は grep で再特定する。

### 実装手順
1. 上記 grep で対象行と出荷記録を特定し、突き合わせリスト（行と根拠）を作る
2. 3 行を出荷済み機能に合わせて更新し、各行に理由を 1 行で記録する
3. ブレスト報告書の裁定（やらないこと新規候補 3 件の NOT-TODO 候補追加可否）を ROADMAP.md に反映する
4. 半年ごとの見直し運用がリリースペース（2週間で15版）に対して粗い問題への対処として、CHANGELOG 更新時の ROADMAP 行参照チェック導入を検討し、検討記録を残す
5. 更新後に ROADMAP.md 全体を読み返し、出荷済み機能と矛盾する行が他に無いことを確認する

### 落とし穴
- 判断の軸 5 本そのものは変更しない（変更時は ADR 相当）
- ROADMAP.md の「運用」節に従い、行の理由が消えた時だけ更新する。半年ごとの機械的な見直しで全面書き換えをしない
- この PBI は ROADMAP.md 自体は触らない（実装セッションで ROADMAP 更新を行う）
- N11 の NULL 前提は 6.9.63 の pickRecordDiagnostics 受渡し欠落修正で解消済み。「NULL のまま」という前提で書き直さない
- C2 と E7、C5 と E5 は同じ矛盾の判断側と拡張側のペア。片方だけ直すと矛盾が残る
- pbi/ 配下の文書は SHIFT-JIS で表現できる文字のみ。EM DASH（U+2014）は禁止で、横棒は U+2015 を使う
