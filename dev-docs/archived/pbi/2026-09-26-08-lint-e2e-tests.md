# PBI: E2E テスト（testDir/）を ESLint 対象に追加し、`waitForTimeout` を検出する

## ユーザーストーリー

開発者として、Playwright E2E テストの `page.waitForTimeout` も ESLint で自動検出したい。そうすれば、E2E でも固定待機を見落とさず、すべて `expect.poll` / `page.waitForFunction` に統一できる。

## ビジネス価値

**現状**: ESLint が `testDir/e2e/` を無視（ignores に含まれる）。

`eslint.config.js` L8：
```javascript
ignores: ['node_modules/', 'dist/', 'testDir/', ...],
```

**E2E の固定待機:** 12 件の `page.waitForTimeout` が existing（検出されていない）。

```bash
grep -rn "waitForTimeout" testDir/e2e/ | wc -l
# → 12 件
```

例：
- `testDir/e2e/content-script-recording.spec.ts`: `await page.waitForTimeout(6500);`
- `testDir/e2e/extension.spec.ts`: `await page.waitForTimeout(500);` × 5

## 対応方針

### Phase 1: ESLint config に E2E ブロックを追加

```javascript
{
  files: ['testDir/e2e/**/*.ts', 'bench/**/*.ts'],
  languageOptions: { parser: tsParser },
  rules: {
    'no-restricted-syntax': [
      'error',
      {
        selector: "CallExpression[callee.property.name='waitForTimeout']",
        message: 'Use expect.poll or page.waitForFunction instead of waitForTimeout. See TEST_RULE.md.'
      }
    ]
  }
}
```

### Phase 2: 既存の 12 件を `expect.poll` / `page.waitForFunction` に置き換え

代替手段：
- **UI 要素の表示待ち**: `await expect(locator).toBeVisible()`
- **条件まで待つ**: `await expect.poll(() => condition)`
- **カスタムジョブ**: `await page.waitForFunction(() => window.readyState === 'complete')`

### Phase 3: `npm run lint` が E2E ファイルも検査するように

ESLint config から `testDir/` ignores を削除（またはより細粒度に設定）。

## DoD（Definition of Done）

- [x] `eslint.config.js` に E2E 専用ブロックを追加
- [x] `ignores` から `testDir/` を削除、または `testDir/e2e/**/*.ts` のみ対象に
- [x] 既存の 12 件の `waitForTimeout` を全て裁定済み（9 件を条件待ちへ変換、3 件は理由明示の明示的 opt-out）
- [x] `npm run lint` で E2E ファイルも検査される
- [x] `npm run lint` で violation 0 を確認
- [x] `npm run validate` が PASS する

## 実施記録

### なぜなぜ分析

1. 12 件が放置されていたのは、`testDir/` が `ignores` に入っていたため**検査するツールが存在しなかった**から。
2. 検査するツールが無いのは、E2E 固有の待機（Playwright の `waitForTimeout`）に対応する ESLint ルールが無く、Unit/Integration 用の `local/no-test-sleep` は Playwright API を知悉していないから。
3. そのルールが無いのは、「実時間待ちの禁止」という方針が `dev-docs/TEST_RULE.md` と `AGENTS.md` に散文で書かれており、Unit 層にしか機械的な強制力が無かったから。
4. testDir が lint 対象外だったのは、当初 `testDir/` を「型も lint も挂かっていない補助ディレクトリ」として丸ごと無視していたから。型は `npm run type-check:test` が別 tsconfig で所有しており、lint だけが取り残されていた。
5. 根本原因は **「禁止則は散文で、強制は Unit 層に限定されていた」** ことにある。よって「検査範囲に含める」だけでなく「E2E 固有の待機패턴を検出するルールを新設する」までが解となる。

### 追加したルール

`eslint/rules/no-fixed-wait.mjs`（`eslint/plugin.mjs` に `local/no-fixed-wait` として登録、`error` 相当）

- `local/no-test-sleep` の E2E 版。`page` / `Frame` / `Locator` / `Worker` / `JSHandle` が同じ `waitForTimeout` を持つため、**member call のみ**を対象にする。
- 閾値を持たない。sleep と違い「どの待ち時間も条件を表さない」ため、例外の概念を設けない。
- 抑制は `// eslint-disable-next-line local/no-fixed-wait -- <理由>` のみ。

### lint 対象化の範囲判断

`testDir/**` と `bench/**` を **型非依存（type-aware でない）** 設定にした。
`testDir/tsconfig.json` は `./e2e/fixtures/**` と vitest テストのみを include しており `.spec.ts` を含まないため、`project` を指定すると全 spec の型解決が失敗する。同一 flat config 内で `src/**` の `project: './tsconfig.json'` 解決を壊さないため、型検査は既存の `npm run type-check:test` に委ねた。

また `testDir/e2e/test-pages/**/*.js` はブラウザに読ませるのはずバンドルされない JS だが TS 構文を持つため、TS parser を明示的に割り当てた。

### 12 件の裁定

| ファイル | 裁定 |
|---|---|
| `testDir/e2e/extension.spec.ts`（5 件） | `expect(locator)` / `expect.poll` へ変換 |
| `testDir/e2e/content-script-recording.spec.ts` | `expect.poll` へ変換 |
| `testDir/e2e/pii-wasm-initialization.spec.ts` | **opt-out**（下記） |
| `bench/e2e/autosave-latency.bench.ts` | `waitForFunction(performance.getEntriesByName('ow-send-ready'))` へ変換 |
| `bench/e2e/content-script-impact.bench.ts` | **opt-out**（下記） |
| `bench/e2e/sw-startup.bench.ts` | **opt-out**（下記） |

opt-out 3 件の理由:

- **`pii-wasm-initialization.spec.ts`** — 観測対象が「警告が出ないこと」という**陰性**で、待つべき条件が存在しない。警告は service worker が `PREVIEW_RECORD` の応答を返す前に書き出しており、残っている不確定性は console イベントがプロセスへ届くまでの配送遅延だけ。かつ service worker の成功経路は console に出力しない（logger は `chrome.storage` へ書く。`console.log` 分岐は chrome を持たない offscreen 経路のみ）。警告を待てば断言が構成上常に通ってしまうため、残り 500ms は配送ウィンドウだけを覆うものとして明示的に opt-out した。
- **`content-script-impact.bench.ts`（2s）** — 計測対象である long task 総和规范の**観測窓そのもの**。条件待ちに置き換えると報告値が変わる。`AGENTS.md` の「real time が測定対象である場合（bench/）」の例外に該当。
- **`sw-startup.bench.ts`（500ms）** — 反復間のクールダウン。次のサンプルが cold start であるには worker が再び idle になる必要があるが、**「メッセージが来ないこと」自体が wait できない**。短縮すると bench が測る対象が静かに変わる。

### 残存スコープ

- `no-fixed-wait` は `testDir` / `bench` のみに有効。`src/**/__tests__` は `local/no-test-sleep`（Unit/Integration）が所有している。
- `pii-wasm-initialization.spec.ts` の opt-out 1 件は**実走で検証できていない**。同ファイル冒頭の `test.skip(true, 'requires headed Chrome with display (MV3 service worker)')` により headless 環境では常に skip される。reason の記述が正しいこと（service worker の成功経路が console に出力しない）はコードと `src/utils/logger/storageAdapter.ts` を読んで確認済み。

## 実行による検証（2026-09-26 追記）

lint と型検査だけでは置換の正しさは証明されないため、実際に Playwright を走らせた。

| 実行 | 結果 |
|---|---|
| `npm run test:e2e -- --project=interaction` | 17 passed / 6 skipped（skip 6 件はすべて既存の `test.skip` / `test.fixme`） |
| `npm run bench:e2e` | 3 passed / 1 skipped（skip は `lighthouse.bench.ts` の既存 skip） |
| `npm run test:e2e -- --project=extension` | 初回 1 failed → 修正後 100 passed / 1 flaky / 20 skipped |

### 実走で検出した回帰と修正

`--project=extension` の初回実走で `content-script-recording.spec.ts:148`
「does NOT fire when stay < 5 seconds」が `retries: 2` を使い切って失敗した。

本 PBI の置換が、50% スクロール到達を確認したうえで **「stay > threshold / 2」を待つ**ようにしていたため、
5 秒閾値の陰性窓を 2.0 秒地点から 2.5 秒地点へ押し出していた。閾値の境へ判定を近づけるだけで
意味を持たない変更であり、直前のステップですでに条件（スクロール深度）は成立している。
よってそこを待った直後に `duration < threshold` を検証する形に戻した（コミット `24e3e28f`）。

この spec は 1.5 秒で完了するようになり、元の固定 sleep 版より速い。
`--repeat-each=5 --retries=0` で 25 件全通過を確認している。**retry で緑にして
済ませず、retries=0 で安定することを確認した**点が重要で、緑は retry の効果ではなく
修正そのもので得られている。

### 置換 9 件の実行時カバレッジ

| 置換先 | 実行時の検証 |
|---|---|
| `extension.spec.ts`（5 件） | interaction / extension 両 project で通過 |
| `content-script-recording.spec.ts` | 実行して 1 件の回帰を検出し修正 → 5 周回全通過 |
| `autosave-latency.bench.ts`（`ow-send-ready` の `waitForFunction`） | `bench:e2e` で 17.0s 通過。mark が実際に到達することを確認 |
| `content-script-impact.bench.ts` の opt-out | `bench:e2e` で通過 |
| `sw-startup.bench.ts` の opt-out | `bench:e2e` で通過 |
| `pii-wasm-initialization.spec.ts` の opt-out | **未検証**（上記理由により常に skip） |

`autosave-latency` の置換は「修正前は 6 秒固定、記録が `null` になっても green になる」実装から
「mark が届かなければ timeout で fail する」実装へ変えたため、実際の mark 到達を
`bench:e2e` で確認的解释している。

## 見積もり

1 SP。ESLint config の追加（0.2 SP）+ 置き換え（0.8 SP）。

## 検討事項

- 他の E2E framework（cypress など）は対象外
- bench も同時に対象に入れるか（現在 `waitForTimeout` が 2 件）
- `page.waitForLoadState()` の妥当性（このコマンドは condition-based なので許可）
