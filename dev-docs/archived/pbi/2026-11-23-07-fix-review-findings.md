# PBI: レビュー指摘14件の対応

## ユーザーストーリー
開発者として、レビューで見つかった問題を全て直したい、なぜなら未処理のまま残すと性能と安全性と正確さが損なわれるから。

## ビジネス価値
- 分割バックアップの作成と復元が実用的な速度になる
- 誤削除と誤表示の事故を防ぐ
- 測定方法: `npm run validate` が緑で全指摘が閉じること

## BDD受け入れシナリオ

```gherkin
Scenario: 分割バックアップが実用速度で往復する
  Given 30MB級の履歴DBがある
  When 分割バックアップを作成し復元する
  Then パート数分のKDF繰返しが起きない
  And 復元結果が従来と一致する

Scenario: 不可逆操作は確認を経て実行される
  Given 忘れ復旧の入口がある
  When 利用者が削除を選ぶ
  Then 明示確認なしに削除は実行されない
```

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 分割往復の操作確認

### 統合テスト
- 修正前後の差分確認
- ロックと復旧の連携

### 単体テスト
- 数え上げの境界値
- 文言と分岐
- 上限と抑止

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

## 技術的考慮事項
- 依存関係: なし。各指摘は独立ファイルで対応する
- テスタビリティ: 実時間待ちは使わない
- 非機能要件: 復号前ゲートの順序は維持する。上限は緩めない
- ロールバック手段: 指摘別に無効化できる形で残す

## 実装者向け注記

### 現状コードの確認
レビュー時に確認済み。対象は以下になる。

```bash
grep -rn "Uint8Array.from(input)" src/dashboard/encryptedBackupSplitCodec.ts
grep -rn "omittedRows" src/dashboard/importLogsAiRepair.ts
grep -rn "forgotArmed" src/dashboard/masterPassword.ts
```

確認結果:
- 指摘1から3は分割コーデックの繰返し処理が原因
- 指摘4と6はAI修復の数え上げが原因
- 指摘8は二重操作の確認不足が原因
- 指摘11から14はAI修復の本番呼出しが未配線

### 実装手順
1. 指摘別に担当を分け、触るファイルを重ねない
2. Outside-Inで失敗試験から書く
3. 既存試験を緑に保つ
4. 全体検証を通す

### 落とし穴
- KDF回数を下げないこと。繰返しをなくす方向で直す
- 復号前ゲートの順序を変えないこと
- 上限を緩めないこと
