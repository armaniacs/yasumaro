# PBI: PBIのDefinition of Doneをテスト存在確認込みで強制する仕組みの導入

## ユーザーストーリー
プロジェクトの保守担当者として、PBIの「全BDDシナリオが自動テストとして実装されパスする」というDoD項目が、実装者の自己申告だけでなく機械的にも検証されてほしい、なぜならテストが存在しないままDoDが達成済みとして扱われ、後続のコードレビューで初めてバグが発覚するケースが発生したから

## ビジネス価値
- PBIプロセスの信頼性向上（DoDが「達成した体で終わっているPBI」を防ぐ）
- 後工程（コードレビュー・本番運用）でのバグ発見コストを、PBI完了時点での検証コストに前倒しできる

## 背景（既実装確認）

`2026-08-19-01`〜`05` の5件のPBIは、いずれもDoDに「全BDDシナリオが自動テストとして実装されパスする」という項目を含んでいた。当初は「対応するテストファイルが存在しない」と認識していたが、敵対的レビューでの裏取りにより**この認識は不正確**と判明した。

**訂正**: `src/utils/__tests__/promptSanitizer.test.ts` / `promptSanitizer-false-positives.test.ts` / `promptSanitizer-owasp-matrix.test.ts` は実在し、`sanitizePromptContent()` を経由して `isInSafeContext()` の効果を間接的にテストしている（`promptSanitizer.test.ts:125-126` に「safe-context プレフィックスがあってもインジェクションを検出する」というテストが存在）。ただし、このテストは「safe-context 判定がフィルタのバイパス経路にならないこと」を確認する目的であり、`isInSafeContext()` 自体の positive ケース（実際に安全な文脈が正しく救済されるか）・negative ケース（HTML属性値バイパス等）を単体で検証するテストは存在しない。同様に `isRateLimitedVisit()` のTTLロジックも、`src/background/handlers/__tests__/messageHandlers-recordSecurity.test.ts` に直接の言及がなく、TTL境界値のテストは存在しない。

**なぜなぜ分析の結論（訂正後）**: 問題は「テストファイル自体の不在」ではなく、「対象ファイルに対応するテストファイルはあるが、変更・追加されたロジック（`isInSafeContext` の新規分岐、TTLエビクションの境界条件）に対応する具体的なテストケースが欠けている」という、より粒度の細かい欠落である。DoDのチェック項目は「実装者が手動でチェックを入れるだけのチェックボックス」であり、CIやレビューフローに機械的な強制力を持つゲートが存在しない点は変わらないが、**ファイル単位の存在チェックでは今回のケースを検出できない**ことを踏まえて対策を設計し直す必要がある（詳細は「敵対的レビューでの追加指摘」参照）。

### 敵対的レビューでの追加指摘（本PBIのスコープに反映）

1. **ファイル単位の粗いチェックでは実際の欠陥を検出できない**: 当初提案していた「`src/**/*.ts` の変更に対して `src/**/__tests__/*.test.ts` の変更が伴っているか」という仕組みは、既に対象ファイルのテストファイルが存在するケース（今回のPBI02・05がまさにそう）では「テストファイルは変更されている（かもしれない）」という理由でスルーしてしまい、実際に足りていない「新規ロジックに対する具体的なテストケース」の欠落を検出できない。
2. **仕組み自体が容易に回避可能**: ダミーの1行変更（空行追加、コメント追加）をテストファイルに加えるだけでゲートを通過できてしまう。当初案が「機械的すぎるルールは誤検知を生む」ことを理由に厳密なマッピングを避ける方針だったことが、この回避余地を直接生んでいる。さらに再レビューで、テストケース数の単純比較（`test(`/`it(`/`describe(`の出現数のみ）には「既存テストを1件削除し、無意味なテストを1件追加する」という差し引きゼロのすり替えを検出できないことが判明した。出現数の増減だけでなく、削除された行と追加された行の両方が存在するdiffパターン（変更行数 > 0 かつ 出現数の変化 = 0）も別途警告対象に含めること。
3. **差分比較の基準が未定義**: CIチェックの比較対象（PR全体の差分か、直近コミットとの差分か）が明記されておらず、実装によっては複数コミットへの分割やbase branchの選び方次第で容易にすり抜ける。
4. **「コードレビュー完了」というDoD項目がPBI群共通で未定義（再レビューで新規発見）**: `2026-08-19-06`〜`09` の4本すべてのDoDに「コードレビュー完了」という項目があるが、承認者数・承認者の権限（セキュリティ関連PBIである07・08はセキュリティレビュアーの承認が別途必要か）・GitHub PR上のapprove状態を指すのか口頭確認で足りるのかが、いずれのPBIにも定義がない。本PBI（09番）はDoD強制の仕組みを扱うため、このスコープにも含めるのが適切。
5. **本番投入後のロールバック手段が4本すべてに欠落（3周目の敵対的レビューで新規発見）**: `2026-08-19-06`〜`08` はいずれも本番投入後に問題が発覚した場合の切り戻し手段（feature flag、`chrome.storage.local`経由のkill switch、段階的ロールアウト）に一切言及していない。本プロジェクトはChrome Web Store配布であり、CLAUDE.mdが暗黙の前提とする「npm packageのような即時ロールバックができない」という制約（審査待ち・ユーザーの手動更新待ちで数日単位のタイムラグが生じる）を踏まえると、挙動変更を伴うPBI（特に06のTTLスイープ、07のsafeMarker変更、08のdangerLevel分岐）は本来ロールバック手段の検討をDoDに含めるべきだった。本PBI（09番）に、今後のセキュリティ・挙動変更系PBIのテンプレートへ「ロールバック手段の検討」をDoD項目として追加するスコープを含める。
6. **CIスクリプトのglobパターン実装ミスの余地（3周目の敵対的レビューで新規発見、条件付き）**: 実装手順1で提示した `src/**/*.ts` というglobパターンは、シェルスクリプトとして素朴に実装した場合、bashの `globstar` シェルオプション（`shopt -s globstar`）が有効でないと深い階層（実測でプロジェクト内には深さ8〜11のテストファイルが多数存在する）を再帰的にマッチできない。裏取りの結果、本プロジェクトの `.github/workflows/pages.yml:9` は既に `src/**/*.ts` をGitHub Actionsのpath filterとして使用しており、これはYAML側のpath matcherが処理するためbashのglobstar制約を受けない。実装時はこの既存パターン（GitHub Actionsのpath filter、またはNode.jsの `glob`/`minimatch` パッケージ）を踏襲し、シェル組み込みの `**` 展開に素朴に頼らないこと。

## BDD受け入れシナリオ

```gherkin
Scenario: 新規PBIに対応するテストファイルが一切存在しない場合に検出される
  Given PBIの受け入れ基準に記載された対象ファイル（例: newFeature.ts）が新規作成され、対応するテストファイルが1つも存在しない
  When PRの差分にテストファイルの追加が含まれていない
  Then レビュープロセスまたはCIで警告・ブロックが発生する

Scenario: 既存テストファイルへのダミー変更だけではゲートを通過できない
  Given 対象ファイル（例: promptSanitizer.ts）に新規ロジックが追加されている
  When 対応するテストファイルに空行やコメントの追加のみが含まれ、新規の describe/test/it ブロックが追加されていない
  Then レビュープロセスまたはCIで警告が発生する（テストケース数の増減を見る、または人間のレビュアーに明示的な確認を促す）

Scenario: テストファイルが正しく含まれるPBIは通常通りマージできる
  Given PBIの対象ファイルとテストファイルの両方が変更され、テストケース数が増加している
  When PRがCIを通過する
  Then マージがブロックされない
```

## 受け入れ基準
- [ ] PBIのDoD「全BDDシナリオが自動テストとして実装されパスする」を検証する具体的な手段（CIチェック、PRテンプレートのチェックリスト、レビュアー向けガイドライン等）が導入される
- [ ] 導入した仕組みが既存の開発フロー（`npm run validate` 等）を大きく損なわない
- [ ] 「対象ファイルの差分があるのにテストファイルの差分が一切ない」ケースを検出できる
- [ ] 「テストファイルは変更されているが、テストケース数が増えていない（ダミー変更のみ、または削除+追加による差し引きゼロのすり替え）」ケースを、少なくとも警告レベルで検出できる。テストケース数の単純比較に加えて、変更行数が0より大きいのにテストケース数の変化が0であるパターンも対象に含める
- [ ] CIチェックの差分比較基準（PRのbase branchとの差分であること）を明記し、コミット分割による回避を防ぐ
- [ ] 本仕組みが「ファイル単位の存在確認では検出できない粒度の欠落」を持つことを開発者向けガイドラインに明記し、機械チェックだけに頼らずレビュアーが実際のテストケース内容を確認する運用を併記する
- [ ] 「コードレビュー完了」というDoD項目の判定基準（承認者数・GitHub PR上のapprove状態を必須とすること）を開発者向けガイドラインに明記する。セキュリティに関わる変更（`src/utils/promptSanitizer.ts`、`src/utils/ssrfGuard.ts`、`src/utils/crypto/`配下等）は、通常のレビュアー承認に加えて `CLAUDE.md` の「For Security Review Agents」節に基づく観点確認を実施したことをPR説明に明記することを必須とする
- [ ] `pbi-create-bdd` スキルのPBIテンプレートに「ロールバック手段の検討」という項目を追加し、挙動変更を伴う修正PBI（性能変更・フィルタロジック変更・閾値変更等）では、本番投入後に問題が発覚した場合の切り戻し手段（feature flag、設定による無効化、影響範囲の限定等）をDoDまたは技術的考慮事項に記載することを促す
- [ ] CIスクリプトのファイル差分検出ロジックは、シェル組み込みの `**` 展開ではなく、GitHub Actionsのpath filterまたはNode.jsのglobライブラリ（`glob`/`minimatch`等）を用いて実装し、深い階層のディレクトリ（本プロジェクトでは深さ8〜11のテストファイルが実在）も確実に検出できることを確認する

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- なし（プロセス改善のため対象外）

### 統合テスト
- 導入する仕組み自体の動作確認（例: CIスクリプトを実際のPRで試験実行）

### 単体テスト
- 該当なし（プロセス・ツールの導入が中心）

## 実装アプローチ
本PBIはコード実装ではなくプロセス改善が中心のため、TDDサイクルは直接適用しない。ただし導入するCIスクリプト自体にはテストを書く。

## 見積もり
1ストーリーポイント（技術的な実装は小さいが、チームでの合意形成にコストがかかる可能性がある）

## 技術的考慮事項
- 依存関係: なし
- テスタビリティ: CIスクリプトはリポジトリのファイル変更差分を解析する程度の軽量な仕組みを想定
- 非機能要件: 厳格すぎるゲート（テストファイルが1行でもないとブロック等）は開発速度を損なうため、警告レベルからの段階導入を推奨する

## 実装者向け注記

### 現状コードの確認
（着手前に必ず実行すること）
```bash
# 既存のCI設定を確認
cat .github/workflows/*.yml 2>/dev/null | grep -A5 "test\|validate"
# PBIテンプレートの所在を確認
find pbi -name "*.md" | head -1
```

### 実装手順
1. まず軽量な仕組みから着手する: `git diff --diff-filter=ACM <base-branch>...HEAD` で対象ファイル（`src/**/*.ts`、テストファイル除く）とテストファイル（`src/**/__tests__/*.test.ts`）双方の変更有無を比較するスクリプトを作成する。base branch は明示的にPRのマージ先ブランチとし、コミット単位ではなくPR全体の差分を対象にする
2. テストファイルが変更されている場合でも「ダミー変更でないか」を簡易的に見分けるため、変更前後で `test(` / `it(` / `describe(` の出現数を比較し、増えていなければ警告に留める（フォールスポジティブを許容する軽量な近似でよい。テストの意味的な妥当性まで機械検証しようとしない）
3. CI（GitHub Actions等）に警告ジョブとして組み込む（いきなりブロッキングにはしない）
4. 一定期間運用して誤検知が少ないことを確認したら、ブロッキングゲートへの昇格を検討する
5. PBIテンプレート（`pbi-create-bdd` スキルのテンプレート）のDoD項目に「本チェックはCIで自動検証されるが、テストケースの意味的妥当性は人間のレビューが必要」旨を追記する

### 落とし穴
- 1対1でファイルとテストファイルが対応しない構成（統合テストでまとめて検証するケース等）もあるため、機械的すぎるルールは誤検知を生む。最初は「変更ファイル一覧」「テスト変更の有無」「テストケース数の増減」程度の粗いチェックに留め、厳密なマッピングは求めない
- このPBI自体が「プロセスのためのプロセス」にならないよう、実際に過去2件（02番・05番）で「テストファイルは存在するが新規ロジックへの具体的なテストケースが欠けていた」という事実を根拠に、必要最小限の仕組みに留めること
- 本チェックはあくまで「明らかな欠落（テストファイル自体がない、変更もない）」を拾う安全網であり、「意味のあるテストが書かれているか」の判定はレビュアーに委ねる。機械チェックが通ったことを「テストが十分」と誤解させる運用にしないこと（このPBI自身が別の形骸化した安全機構を生まないための歯止め）

## Definition of Done
- [ ] 導入した仕組みが実際に「対象ファイルの変更はあるがテストファイルの変更がない」PRを検出できることを確認する
- [ ] コードレビュー完了
- [ ] ドキュメント更新済み（開発者向けガイドラインへの追記）
