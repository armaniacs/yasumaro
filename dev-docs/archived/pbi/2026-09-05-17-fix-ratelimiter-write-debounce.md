# PBI: RateLimiter の chrome.storage.session 即時書き込みをデバウンス

## ユーザーストーリー
拡張機能の利用者として、パスワード認証の失敗時も UI がもたつかずに応答してほしい、なぜなら連続した試行のたびにストレージ書き込みが同期発生すると認証ダイアログの応答が遅れ使いにくいから

## 優先度
- 順位: 12 / 26
- RICEスコア: 1,400（Reach=1000 / Impact=1 / Confidence=0.7 / Effort=0.5日）
- 根拠: 認証失敗バースト時に毎回 session＋local の二重書き込みが発生し、短時間に書き込みが集中する。修正は書き込み合体のみで挙動変更が小さく効果が確実。

## BDD受け入れシナリオ
```gherkin
Scenario: 連続した失敗試行の書き込みが合体される
  Given レート制限のカウンタが初期状態
  When  短時間に複数回の失敗試行を記録する
  Then  最終的な試行回数と初回試行時刻が正しく永続化され、実際のストレージ書き込み回数が試行回数より少ない

Scenario: ロックアウト判定は遅延しない
  Given 上限回数に達する直前の状態
  When  上限を超える失敗試行を記録する
  Then  次の checkRateLimit は直ちにロックアウトを返し、ロック期限が両ストアに書き込まれている
```

## テスト戦略
- 単体: `StoragePort` にモックを注入し、連続記録時の `session.set` 呼び出し回数が合体されること、ロックアウト到達時に即時書き込まれることを検証する（`RateLimitService` 系テストを拡張）
- 単体: デバウンス待ち中の `checkRateLimit` がメモリ上の最新値を読むことを検証する

## 実装アプローチ
`RateLimitService.recordFailedAttempt` の session 書き込みを短時間（例: 数百ms）の合体ウィンドウで束ね、最終値のみを書き込む。local への書き込み方針は現状維持か同時合体のいずれかとし、ロックアウト到達時・`resetFailedAttempts` 時は保留中の書き込みを即時フラッシュする。読み取り側は保留中の最新値を優先して参照する。
