## 5 Whys サマリー（ラウンド共通の根本原因）

1. なぜ sender/通知が seam の外に散らばったのか → 変換・送信が同居した関数が、変換の要件を送信の複製ごと連れて移動したから（dashboard / content 両方で同型）。
2. なぜ retry や遷移順序の「政策」が所有者を持たないのか → 条件のデータ（retriable フラグ・initParams）は seam を横断済みなのに、実行の owner を決める工程が feature 実装に含まれていなかったから。
3. なぜ dead seam や 2 signature が残るのか → 本番消費者の存在確認が削除判断に組み込まれていなかったから（削除テストを PR 前に回していない）。
4. なぜ同一ファイルの候補が複数ラウンドに跨るのか → ラウンド間で「どの friction が残ったか」の記録は backlog にあるが、ファイル単位の衝突視点が欠けていたから。
5. なぜ並行セッションで番号が衝突したのか → INDEX を唯一の番号台帳として使う運用が明文化されていなかったから。
→ 解: 政策の owner を seam に決め、消費者ゼロの表面は削除し、同一ファイル候補は依存として明示し、番号台帳は INDEX に一本化する（本ラウンドの 6 件）。
