## PBI 06（Provider Catalog）— 効果確認済み（2026-09-01）

2026-08-31 に `ProviderCatalog` を先行実装した（csp / diagnostics / getMaxContentChars を Catalog 駆動化）。2026-09-01 に再評価トリガー（下記）を実行し、**「追加が 1 箇所で済む」は未達**と判定。トリガーの指示どおり 2 件の deepening PBI（06b / 06c）を実装し、達成した。

**再評価の方法**: 実 provider 追加要求が無かったため、cloud provider 1 つを追加する手順を現行コードに機械的にトレースして検証した。

**検証結果（着手前）**: cloud provider 1 つの追加に約 20 ファイルを触る。Catalog が吸収していたのは派生関心（CSP init loop / diagnostics 列挙 / getMaxContentChars）のみで、以下が分散したままだった:
- Catalog モジュール内だけで 4 箇所（registry 1 行 + `CSP_DOMAINS` / `LABELS` / `CONTENT_CHARS_KEYS` の 3 独立表）
- provider label が 4 コピー（Catalog placeholder / `aiProviderLabels.PROVIDER_LABELS` / ダッシュボード UI 3 配列 / i18n キー）
- `urlWhitelist.ts` の 3× コピペ `if` ブロック
- `DiagnosticsCollector.settingsKeys` / `diagnosticsPanel.KNOWN_DETAIL_PROVIDERS`
- ダッシュボード UI 層（`index.html` の `<option>` ×4 select + 7 個の per-provider `<div>`、`settings/aiProvider.ts` の if/else 連鎖、`aiProviderB` の 2 配列、`aiProviderLayoutManager` の map）
- conformance test なし（half-wired provider が全 green で出荷され得る）

**対応（実装済み、2026-09-01）**:
- **06b**（[refactor-provider-catalog-consolidation](2026-09-01-03-refactor-provider-catalog-consolidation.md)）: Catalog のデータソースを `PROVIDER_REGISTRY` 1 箇所に統合。`aiProviderLabels.ts` 削除。`urlWhitelist` を catalog loop 化。conformance test を新設。
- **06c**（[refactor-provider-ui-catalog-driven](2026-09-01-04-refactor-provider-ui-catalog-driven.md)）: `registry` に UI メタデータ（labelI18nKey / fieldPlaceholders / supportsCustomPrompt / settingsBlockKind）を追加。`aiProviderCatalogView.ts`（`renderProviderOptions` / `renderProviderSettings`）を新設し、A/B 両レイアウトと custom-prompt select を catalog 駆動に。`index.html` の静的 provider マークアップを削除。`CustomPrompt.provider` 型を lm-studio/ollama に拡張。

**到達点**: provider 追加 = `PROVIDER_REGISTRY` 1 行 + i18n キー。conformance test（`providerCatalog.test.ts`）が未接続分岐を検出する。

**スコープ外（→ 06d 候補、下記）**。

## 06d 候補（PBI 06 効果確認で洗い出した残債、2026-09-01）

catalog で吸収し切れず、かつ 06b/06c のスコープ外とした分岐。次に provider を実際に追加するとき、または関連リファクタの機会に着手を検討する。

| 項目 | 内容 | 備考 |
|------|------|------|
| `cspDomains.ts` manifest host-permission | manifest の host_permissions / optional_host_permissions リストが provider ドメインを個別列挙 | build 時生成が必要。manifest.json 直書きとの整合 |
| `cspValidator.PROVIDER_TO_DOMAIN` | Models.dev サブ provider（openai-compatible 配下の 70+ provider）→ ドメイン写像。catalog の provider とは別概念 | Models.dev データ由来。別レイヤ |
| `aiLimits.PROVIDER_MAX_TOKENS` | provider ごとの max tokens 上限マップ | catalog に `maxTokens?` を足すのが素直だが、値の出典（各 provider の API 仕様）管理が別課題 |
| `RemoteAIService` factory の `if (id === ...)` 分岐 | provider id → Provider クラス生成の分岐。Strategy は既に深いモジュールで、これ自体は 1 箇所 | catalog に `createProvider` を持たせると循環依存リスク。要設計 |
| `StorageKeys` + `defaults` の per-provider key | `GEMINI_API_KEY` 等の宣言と DEFAULT_SETTINGS エントリ | 型の自動生成が必要。影響範囲が広く単独 PBI 相当 |

### 再評価トリガー（当時の記録）

> 次に AI provider を 1 つ追加するとき（`PROVIDER_REGISTRY` へのエントリ追加時）。そのタイミングで:
> - Catalog 駆動化で「追加が 1 箇所で済んだか」を確認する
> - 済んでいなければ、まだ Catalog に吸収できていない分岐を洗い出し、次の deepening PBI の候補にする
> - Catalog で十分なら、本 PBI を「効果確認済み」として archive する
