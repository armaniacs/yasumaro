# PBI: 生成側例外のSSOT集約

## ユーザーストーリー
開発者として、oxlint用の例外を生成側ではなく定義書側に持ちたい、なぜなら二箇所に意図が分散すると将来の変更で食い違いが起きるから。

## ビジネス価値
- 例外の見落としによる層違反の素通りを防ぐ
- 測定方法: 例外が定義書側に一本化され、食い違い検出の試験が緑になること

## BDD受け入れシナリオ

```gherkin
Scenario: 例外が定義書側に集約される
  Given 例外が定義書側に書かれている
  When 生成を実行する
  Then 生成物に例外が反映される
  And 生成側に個別の例外記述が残らない

Scenario: 食い違いは検出される
  Given 生成物が定義と食い違っている
  When 照合試験を実行する
  Then 不一致として失敗する
```

## 受け入れ基準
- [x] 生成側の個別例外記述がなくなる
- [x] 例外が定義書側の資料として読める
- [x] 照合試験が緑になる
- [x] `npm run lint` が通る

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- なし（生成物の整合性確認に絞る）

### 統合テスト
- 生成物の照合試験

### 単体テスト
- 例外資料の形状確認

## 実装アプローチ
- **Outside-In**: E2Eテストから開始し、失敗を確認してから実装
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

## 見積もり
S （要チームでの見積もり）

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 生成物を標準出力で取得し照合する
- 非機能要件: fail-closedの扱いは変えない
- ロールバック手段: 定義書側の資料を消して生成側に戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。レビュー時に確認済みの内容を記載する。

```bash
grep -n "oxlint-specific overrides" -A 25 scripts/gen-oxlintrc.mjs
grep -n "export default" eslint.config.js | head -3
```

確認結果:
- 例外2件が生成側に直書きされている。定義書側には無い
- 定義書は実行されない資料のため、資料項目の追加は安全
- 生成物の照合試験は未実装

### 実装手順
1. 照合試験の失敗試験から書く
2. 例外を定義書側の資料項目として移す
3. 生成側は資料を読むだけにする
4. 生成物を再作成しlintを通す

### 落とし穴
- 生成物の差分が出ないことを確認すること
- 資料の形が崩れたら生成を止めること
