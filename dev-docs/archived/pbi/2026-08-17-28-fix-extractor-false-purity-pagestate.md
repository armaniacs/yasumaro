# PBI: extractor.ts の誤った純粋性とpageState結合を修正する

## ユーザーストーリー
開発者として、`src/content/extractor.ts` の `extractPageContent` がpageStateを副作用として変更し、`shouldRecordVisit` が純粋であると主張しているが実際にはモジュールレベルの可変状態を読み取る問題を修正したい。なぜなら、pageStateが隠れた出力チャネルとして機能し、抽出と検証を結合しているから。

## ビジネス価値
- 抽出関数と検証関数が独立してテスト可能になる
- pageStateの所有権が明示的になり、bug発見が容易になる
- 関数が真に純粋になり、モックなしでテスト可能になる

## BDD受け入れシナリオ

```gherkin
Scenario: ページ内容の抽出
  Given コンテンツスクリプトがページに注入される
  When ページ内容が抽出される
  Then 結果オブジェクトが返され、pageStateが変更されない

Scenario: 訪問条件の検証
  Given ページが特定の条件を満たす
  When 訪問条件が検証される
  Then 明示的なパラメータに基づいて結果が返される
  And モジュールレベルの状態を読み取らない

Scenario: 純粋関数のテスト
  Given テストで抽出関数を呼び出す
  When パラメータを渡す
  Then モックなしで結果が検証できる
```

## 受け入れ基準
- [ ] `extractPageContent` が結果オブジェクトを返し、pageStateを変更しなくなる
- [ ] `shouldRecordVisit` が明示的なパラメータを受け取る形に変更される
- [ ] pageStateの所有権がオーケストレーターに移動する
- [ ] 関数が真に純粋になり、モックなしでテスト可能になる
- [ ] 既存のテストがすべてパスする
- [ ] 新しいユニットテストが追加される

## テスト戦略（t_wadaスタイル）

### 統合テスト

- オーケストレーターとの連携テスト

### 単体テスト
- 各関数の純粋なロジック
- パラメータの検証

## 実装アプローチ

## 技術的考慮事項
- 依存関係: コンテンツスクリプトの制約
- テスタビリティ: 純粋関数としてモックなしでテスト可能
- 非機能要件: コンテンツスクリプトのパフォーマンスを維持

## 実装者向け注記

### 現状コードの確認
```bash
# pageStateの変更を検索
grep -rn "pageState\." src/content/extractor.ts | head -20
# shouldRecordVisitの純粋性を確認
grep -rn "shouldRecordVisit" src/content/extractor.ts
```

### 実装手順
1. `extractPageContent` のシグネチャを変更
2. 結果オブジェクトの型を定義
3. `shouldRecordVisit` に明示的なパラメータを追加
4. pageStateの所有権をオーケストレーターに移動
5. 既存テストを更新
6. 新しいユニットテストを追加

### 落とし穴
- pageStateの変更箇所が多いため、正確な抽出が必要
- 既存のテストがpageStateに依存しているため、テストの更新が必要
