## 5 Whys サマリー (Phase 0 → Phase 1 で解明した根本原因)

### なぜ P0 (cookie) が FAIL したのか
1. なぜ checkbox欠落？ → rules.ts に cookie 追加時、entrypoints/options/index.html の手書きリストが追従する仕組みがなく、人手の同期に依存。
2. なぜ型乖離？ → AiSummaryCleansingSettings が手書き列挙で RuleKey からの導出ではなく、追加キーが型レベルで検出されない shallow interface。
3. なぜ totalRemoved二重？ → stripPopupElements と stripCookieConsentElements が同一 COOKIE_TEXT_PATTERNS 走査を重複実装、DRY違反。
→ 解: SSOT を CLEANSING_RULES に一本化し、型は mapped type、HTMLはループ生成 or 1行追加、重複は helper抽出。

### なぜ Offscreen が God 化したのか
1. なぜ 24-case switch？ → SQLite操作追加のたびに union型と switch を手で2箇所編集する shallow seam、追加コストが低いため放置。
2. なぜ guard散在？ → payload size check が各case内に埋もれ、共通 middleware がないためコピペで追加。
3. なぜ mapper重複？ → buildRecordFromPayload と recordsRepo の逆mapperが別所有、deletion test で「消しても2箇所に再出現」だが抽出されなかった。
→ 解: Registry Map + assertPayloadSize middleware + BrowsingLogRecordCodec 単一所有。

### なぜ Provider追加が4ファイル漏洩したのか
1. なぜ 4ファイル編集必要？ → provider別の baseUrl/apiKey/modelKeyが StorageKeys/aiModelKey/OpenAIProvider/RemoteAIService に分散 (locality欠如)。
2. なぜ string replace が fragile？ → normalizeProviderKeyName が 'openai2' 等の例外を replace で吸収する浅い抽象。
→ 解: ProviderRegistry テーブルに集約し GenericOpenAICompatibleProvider 1クラスに。

### deferred を今回見送る理由
- 02 (StorageKeys facade): 130キー一括はリスク高。09 の clean seam (CleansingConfigCodec) 上で incremental に着手するため、0824b では 09を先に。
- 04/06: Speculative/low RICE、単独着手が安全。
