# PBI: 暗号化バックアップの分割コーデックと往復対応

## ユーザーストーリー
履歴の多い利用者として、大きな履歴DBでも暗号化バックアップを作成して別プロファイルで復元したい、なぜなら単一ファイル形式では50MB前後の上限に当たり正規の移行手段が無くなるから。

## ビジネス価値
- 履歴の多い利用者がパスワードによる正規手段で移行できるようになる
- 上限超過による復元不可を構造的に解消する
- 測定方法: 30MB級DBを含むバックアップの作成と復元が往復成功すること

## BDD受け入れシナリオ

```gherkin
Scenario: 大容量バックアップが分割形式で往復する
  Given 30MB級の履歴DBを持つプロファイルがある
  When 暗号化バックアップを作成し別プロファイルで復元する
  Then 設定と履歴が復元される
  And 単一パートは10MB級の上限内に収まる

Scenario: パート欠落は原因特定して拒否される
  Given 正規の分割バックアップがある
  When 1パートを欠落させて復元する
  Then 欠落パート番号を示して復元が拒否される
  And 既存データは変更されない
```

## 技術的考慮事項
- 依存関係: なし。本PBI単独で完結する
- テスタビリティ: 実DB割当てを避け、境界値は小さな合成データで検証する。KDF回数は既存試験と同様に下げて実行時間を抑える
- 非機能要件: 復号前ゲートの順序は維持する。形状確認、長さゲート、KDF、認証復号の順序は変えない。VULN-036の予算を広げないため各パートの上限は汎用上限内に抑える。メモリ増幅を避けるため全文保持の箇所を増やさない
- ロールバック手段: 本PBIは新規形式の追加のみとし、単一形式の読み書きは残す。問題時は分割作成を使わない運用に戻せる

## 実装者向け注記

### 現状コードの確認
着手前に必ず実行すること。Phase0で確認済みの内容を記載する。

```bash
grep -rn "MAX_BACKUP_FILE_BYTES\|MAX_BACKUP_ENVELOPE_BASE64_LENGTH\|MAX_ENVELOPE_CIPHERTEXT_LENGTH" src/ --include="*.ts" | grep -v __tests__
grep -rn "exportEncryptedBackup\|importEncryptedBackup\|encryptEnvelope\|decryptBackupEnvelope" src/ --include="*.ts" | grep -v __tests__
```

確認結果:
- 暗号化バックアップは単一 `EncryptionEnvelope` 形式で実装済み。分割形式は未実装
- 対象経路は3経路で確定済み。暗号化バックアップ、設定の暗号化export、復元DB
- 設定の暗号化exportは小容量のため本PBIの対象外とし、履歴DBを含む暗号化バックアップのみ分割対象とする
- `MAX_ENVELOPE_CIPHERTEXT_LENGTH` は定義のみで強制箇所は無い。50MB級の2層ゲートが実効上限

### 実装手順
1. Outside-Inで分割往復の失敗試験から書く
2. 分割コーデックを追加する。マニフェスト作成、パート分割、結合、検証を `encryptedBackupService` から分離する
3. 形式案: マニフェストに版数、出力日時、設定本体、パート数、各パート長、全体平文長、結合用IDを持たせる。各パートは独立した `EncryptionEnvelope` とし `index`、`total`、`manifestId` を暗号化対象に含める
4. 圧縮は分割と併用可とする。DBバイト列を暗号化前に圧縮し、効果を測定して記録する
5. 単一形式の読み込みは残し、後方互換の試験を追加する

### 落とし穴
- 上限を上げるだけでは再発する。分割で各パートを汎用上限内に抑えること
- 順序入替と切詰め対策を忘れないこと。マニフェストのパート数と各パートのハッシュで検出する
- `MAX_BACKUP_ENVELOPE_BASE64_LENGTH` と `MAX_ENVELOPE_CIPHERTEXT_LENGTH` は別層のため混同しないこと。比較対象を誤ると誤った上限緩和になる
- 実測の根拠: 11.7MBのDBで46MBバックアップが作成された事例がある。増幅率は約1.8倍で見積もること
