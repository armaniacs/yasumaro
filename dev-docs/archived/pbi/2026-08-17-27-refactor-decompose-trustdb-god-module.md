# PBI: trustDb 1024行ゴッドモジュールを分解する

## ユーザーストーリー
開発者として、`src/utils/trustDb/trustDb.ts` の1024行ゴッドモジュールをocusedモジュールに分解したい。なぜなら、7以上の責務を持ち、settingsStore.tsとの循環依存を動的importで解決し、シングルトンパターンとstatic initPromiseでテストが信頼性を欠いているから。

## ビジネス価値
- 各ドメイン概念が独立してテスト可能になる
- 循環依存が解消され、保守性が向上
- テストの信頼性が向上し、bug発見が容易になる

## BDD受け入れシナリオ

```gherkin
Scenario: ドメイン検証
  Given ユーザーが任意のURLにアクセスする
  When ドメインが信頼データベースで検証される
  Then 3ステップ検証が正しく実行される

Scenario: ブルームフィルター管理
  Given Trancoリストが更新される
  When ブルームフィルターが構築される
  Then ドメインの存在確認が高速に実行される

Scenario: センシティブドメイン管理
  Given 管理者がセンシティブドメインを追加する
  When ドメインがリストに追加される
  Then そのドメインへのアクセスが制限される
```

## 実装者向け注記

### 現状コードの確認
```bash
# 循環依存を確認
grep -rn "await import" src/utils/trustDb/trustDb.ts
# プリセットドメインの重複を確認
grep -rn "SENSITIVE_DOMAINS_PRESETS" src/utils/trustDb/
```

### 実装手順
1. 各モジュールを新規作成
2. 循環依存を解消（依存性の逆転）
3. プリセットドメインの重複を解消
4. `TrustDb` を薄いオーケストレーターに変換
5. 既存テストを更新
6. 新しいユニットテストを追加

### 落とし穴
- 循環依存の解消が複雑になる可能性がある
- 既存のテストがシングルトンに依存しているため、テストの更新が必要
