## なぜなぜサマリー

- **なぜ recordBtn 二重所有が復活したのか** → round 3 で statusStore seam 経由に統一した際、statusPanel の updateTrustStatus に残る直書き 2 箇所（LOCKED disable / grant enable）が見落とされた。「Sole button writer」doc と矛盾する書き込みが隣接関数に残る形。→ 解: statusPanel からの書き込み全削除（doc の契約どおり status は session 経由でしか signal しない）。
- **なぜ search path に tag が届かないのか** → round 4 の移行が plain listing の builder（buildPlainListStatements）だけを対象にしたため。search builder は ExtraWhere のみを受け付ける旧 shape のまま。→ 解: tagFilter を search builders に貫通し parametric で pin。
- **なぜ STATUS の 4 重リストが残ったのか** → round 4 は「drop された 3 フィールドの修復」に留め、リスト統合は次ラウンドへ回した（実バグ修正と構造統合を分離する判断）。→ 解: 本ラウンドで SqliteMigrationExtras を唯一の field list に昇格。
- **なぜ e2e に stale バージョンが残るのか** → e2e は `make clean test` の test 段に入らず手動実行が前提のため、版上げループがハーネスを更新しない。→ 解: package.json 派生にして構造的に解消。
- **なぜ pending が legacy パネルにだけ残ったのか** → panel catalog 化（PBI 25）で panel-history は「登録のみ・hidden」の状態で温存され、機能移設が先送られていた。PBI 15 完了で撤去前提が整った。→ 解: PBI-P で移設し、PBI 16 で機械削除。
