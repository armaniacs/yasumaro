## 重要指摘事項（優先度順）

### [Medium] 🎯 buildPendingPage が url/title を無制限で保存 — storage quota DoS
- 指摘者: Red Team Leader + Blue Team Leader（重複統合）
- 場所: src/utils/pendingStorage.ts:120-139（buildPendingPage）
- 影響: headerValue のみ 1024 truncate で、url/title は攻撃者制御可能な値が無制限で永続化される。MAX_PENDING_PAGES=200 は件数上限でありサイズ上限ではないため、回転 URL で 200件×数十KB を積まれ chrome.storage.local の quota を枯渇させられると、API キー・設定・ログを含む全 storage 書き込みが失敗する
- 対処: buildPendingPage 内で url（2048文字）/ title（512文字）を truncate する定数を追加し pin テストで固定

### [Medium] 🎯 WASM 単一パスは silent divergence を検出できず、UTF-8 index 意味論の比較不一致が実在
- 指摘者: Red Team Leader
- 場所: src/background/pipeline/piiSanitizeHybrid.ts:132（maskedItems の index < MAX_OUTPUT_SIZE 比較が UTF-8 バイトオフセットと UTF-16 長の混在）、src/utils/wasmHybridRuntime.ts:127-138
- 影響: WASM 正常終了時の TS との不一致（silent divergence）は検出されず PII が素通しうる。Rust 移植時に boundary bug 2件の実績あり。共有 runtime 化で4 hybrid に影響半径が拡大
- 対処: 短期 — サンプリング突合 oracle（不一致は fail-closed で TS 採用）。長期 — index 意味論の統一＋非 ASCII/truncation 境界の parity 追加

### [Medium] 🎯 cspValidator が LIST_SOURCES の6ホストを2箇所で手書き（SSOT 再手書きの再発）
- 指摘者: Maintainability Guardian
- 場所: src/utils/cspValidator.ts:53-56（OPTIONAL_DOMAINS）、:225-228（isUrlAllowed 内4ドメイン直書き）
- 影響: リストソース追加時に cspValidator だけ置き去りになり fail-close で fetch がブロックされる。conformance テストは cspDomains/urlWhitelist 側のみ検証（isUrlAllowed は未検証・存在しない関数参照で空集合フォールバック）
- 対処: 2つの直書きを ALL_LIST_SOURCES 派生 Set から判定に置換し、conformance テストに「全 host が isUrlAllowed で true」pin を追加

### [Medium] 🎯 search 既定リミットが gateway 経路で 100 に解決される（PBI 意図 50 と不一致）

## コンフリクト調整結果

1. **privacy pre-decision をめぐる3観点の対立**: Refactoring Evangelist（Low）「pre-decision は素朴ガードで十分・decidePrivacy は fetch 後のみに」、Domain Logic（Low）「placeholder（isPrivate:false）が恒真 gate で実質 force||whitelisted の再記述」、PBI-28 実装（pre-decision 採用）。**System Architect 判断（優先）**: Domain Logic の指摘が本質 — decidePrivacy の allow は isPrivate:false でも成立するため placeholder 呼び出しの verdict は情報を持たず、fetch-skip の実判定は呼び出し側の連言に依存する。→ **明示的な `force || shouldSkipPrivacyCheck` ガードに戻し、decidePrivacy は fetch 後の isPrivate マトリクス専用とする**（Refactoring 指摘と合流）。PBI-28 の意図（fetch スキップの byte 等価保持）は維持される。
2. **Legacy Bridge（search 既定 50 不一致）vs Ops/Tuning（既定 50 統一を良好と評価）**: Tuning は「検索量が半減する方向」を評価したが Legacy は gateway 経路が実際には 100 に解決される（統一が未達）ことを指摘。矛盾ではなく補完 — Tuning の評価は planSearch 直送経路について正しい。修正は Legacy の対処に従う。
