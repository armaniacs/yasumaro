# Yasumaro 6.7.100 が軽いのはなぜか — 「最適化」を一行も書いていないのに

Yasumaro を 6.7.90 から 6.7.100 に上げたら、動きが軽くなった気がします。

「気がする」で済ませるのはもったいない。git log を 6.7.90 まで遡って、どのコミットが体感の正体になりそうかを一つずつ確認してみました。結論を先に言うと、パフォーマンスのためのコードは一行も書いておらず、モジュールの構造を正す整理だけで速さが副産物として付いてきた、という話です。

## いそがしい人向けのまとめ

| やったこと | 軽くなる理由 |
|---|---|
| 設定キャッシュの二重化を解消 | 起動のたびに走る読み書きの経路が2層から1層に |
| facade（中継専用モジュール）の撤去 | 記録1回あたりの呼び出しが直接届く |
| ダッシュボード UI の catalog 駆動化 | 全プロバイダー分の DOM を手書きから定義生成へ |
| 未接続コード 296 行の削除 | バンドルと読む人の負担が減る |

体感の主犯は一番上だと思っています。

## まず答え合わせ: 6.7.100 の中身

CHANGELOG を開くと、6.7.100 自体はドキュメント整備だけのリリースでした。コードは動いていません。

体感の正体は直前の 6.7.99 です。このバージョンで Architecture Deepening と銘打った構造整理が一括で入り、CHANGELOG の通り挙動変更はありません。変わったのはモジュールの中身です。

## 二重キャッシュを1つにした

記録のたびに読まれる設定は、これまで2箇所にキャッシュがありました。旧実装の settingsStore が持つ1秒キャッシュと、後から作った SettingsRepository のキャッシュです。同じデータを2つの層が別々に抱えているため、整合を取るための読み替えと無効化が毎回走っていました。

settingsStore を削除して SettingsRepository に一本化したのが 6.7.99 です。キャッシュは1つ、経路も1本です。

Chrome 拡張の Service Worker は約30秒でスリープし、イベントのたびに起こされて設定を読み直すため、この経路の長さは起動コストにそのまま乗ります。層が1つ減る意味はここにあります。

## facade という中継を外した

記録の処理は RecordingOrchestrator という1つのクラスに集約されていました。ただその手前には、RecordingPipeline という facade が残っていました。facade は実装を持たない中継専用の層で、呼び出しを受けたらそのまま中へ流すだけのものです。消しても動作は変わりません。

消しました。記録の呼び出しが中継を経由せず Orchestrator に直接届くようになり、併せて同じ URL への同時記録を防ぐ Mutex の配線ミスも直りました。機能追加のときに挟み込んだ層は、役目を終えたら外す。この「外す」を一気にやったのが 6.7.99 です。

## ダッシュボードの UI 構築を catalog 1枚に寄せた

AI プロバイダーの設定画面は、従来プロバイダーごとの HTML と手動の対応表で組み立てていて、ダッシュボード起動時に全プロバイダー分の DOM を作っていました。provider を1つ追加するたびに HTML と JavaScript の両方を直す必要がありました。

ProviderCatalog という1枚の定義表に寄せて、UI は定義から自動生成するようにしました。静的な option タグと per-provider の div は撤去しています。プロバイダー追加は「定義表に1行 + 翻訳キー」で済むようになりました。

軽さへの効き方は2つあります。起動時に組み立てる DOM が定義駆動になって手書き時代の余分な要素が消えたことと、provider を選ぶときの if 文の連鎖が表引き1回に縮んだことです。

## 死にコード 296 行を葬った

dashboard には BrowsingLogRepository という 296 行のクラスがありましたが、どこからも参照されていませんでした。SQLite への経路が2系統あった時代の残骸です。削除しました。

バンドルサイズの削減としては小さいのですが、こういう繋がっていないコードは読む人の時間を確実に奪います。今回の整理では、この種の残骸をあちこちで回収しています。

## 次のリリースで入る追加整理

6.7.100 以降にマージした整理がさらに2件あります。

1つは互換 shim の物理削除です。trustDb.ts（122行）と sqliteClient.ts（87行）です。どちらも実装を持たず import を流すだけの中継ファイルで、起動時に評価されるモジュール列に余計な2つとして残っていたため、本体側に中身を吸収して削除しました。2つとも消えました。

もう1つは書き込み排他の統合です。設定・TrustDB・パーミッション・保存済みURLの4つの保存先が、それぞれ独自に競合チェック（CAS）をしていました。307行と75行の2モジュールに散っていたロジックを StorageTransaction という1モジュールに統合し、外に出すインターフェースを2メソッドに絞りました。

次のバージョンで入ります。

## 測っていない、という正直な話

この記事にベンチマーク数字はありません。申し訳ない。

理由は2つあります。1つは今回の整理が「速くするため」ではなく「構造を正すため」のもので、速さは仮説のまま出したこと、もう1つは体感の要因が構造整理だけとは限らないことです。その間の 6.7.92〜97 では BBC や CNN で記録が失敗する不具合を相次いで修正していて、「軽くなった」の一部は「エラーで止まらなくなった」ことかもしれません。

とはいえ、構造として確実に言えることがあります。起動時に評価されるモジュールは減り、記録1回あたりの経路は短くなり、キャッシュの再読込は切れたキャッシュだけに閉じました。次のバージョンでは記録開始までの時間を測って答え合わせをする予定です。

## 何をすればいいか

6.7.90 以前からお使いの方は、そのまま 6.7.100 に上げて問題ありません。設定の引き継ぎへの影響はありません。

自分の拡張機能で似たことが起きているなら、git log の refactor コミットを読み飛ばしていないか見直してみてください。「最適化」というラベルのないコミットの中に、速さの種が埋まっていることがあります。
