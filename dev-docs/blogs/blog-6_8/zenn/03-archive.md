Yasumaro は閲覧履歴をローカルの SQLite（OPFS 上）に貯めます。使い続けると当然肥大化します。

v6.7 系で、古い履歴を安全に退避する機能を入れました。`Dashboard → Archive` パネルからの操作です。この記事はその設計です。

## 課題

「古い履歴を消したい」というニーズはあります。ただ、拡張機能が勝手に消すのは怖いし、消す前にバックアップを取る導線がありませんでした。

やりたいこと:

- 指定日より前の履歴を、標準的な形式でエクスポートする
- エクスポートを確認してから、本体 DB を縮小する
- あとから戻せる

## 2フェーズ設計

エクスポートと削除を1つの操作にまとめると、「ファイルのダウンロードに失敗したのに本体からは消えた」という事故が起きます。分けました。

### フェーズ1: アーカイブ作成（退避）

1. 日付を選び、「Check records to archive」で対象件数を確認（スター付き・削除済みの内訳も表示）
2. 「Create archive file」で `yasumaro_archive_<日付>.db` を生成し、ダウンロード

**この時点で本体 DB は一切変更しません。** 削除済みレコードはデフォルトで除外します（含めるオプションあり。除外した分は後から復元できません）。

### フェーズ2: 本体からの削除（ストレージ解放）

1. ファイルのダウンロードを確認してから、「Delete records from main database」を実行
2. 削除はフェーズ1で作ったファイルの内容と突合せてから行う
3. フェーズ1以降に追加されたレコードは保護される

この「突合せてから削除」が不変条件です。フェーズ1で書き出した ID 集合に含まれるものだけを消します。フェーズ1とフェーズ2のあいだにユーザーが新しいページを記録しても、それは消えません。

## なぜ標準 SQLite 形式か

アーカイブファイルは、本体とは別の素の SQLite ファイルです。FTS のない単純なスキーマにしています。

理由は「開発元の拡張機能がなくても中身を読めること」です。DB Browser for SQLite などの汎用ツールでそのまま開けます。ユーザーのデータがユーザーの手元でロックインされない形にしておきたい、という判断です。

## 復元

アーカイブ `.db` を選ぶと、件数と対象期間を確認してから本体 DB へマージ復元できます。

- 既存レコードは保持
- 重複（同一 URL・同一時刻）はスキップ
- ID は再採番
- 行単位のエラーハンドリング（1行の失敗で全体が止まらない）

## 一時オープン（取り込まずに開く）

本体に取り込まずに、アーカイブファイルをパネル上で直接開けます。「Open archive session」です。

- アーカイブ内を検索できる
- タイトルを編集して、アーカイブファイルに書き戻せる
- 未保存の変更がある状態で閉じようとすると確認ダイアログが出る
- オプションページをリロードしてもセッションを再接続する

編集の書き戻し先はアーカイブファイルだけです。本体 DB には触れません。

## セキュリティ上の注意

アーカイブファイルは平文・非署名です。暗号化されていません。

書き出したあとの保管・移動・削除はユーザーの責任です。この点はプライバシーポリシーにも明記しています。

## レガシーストレージの残存

Yasumaro は過去のバージョンで OPFS 以外のストレージ経路を持っていた時期があり、そのコピーがレガシークリーンアップの実行まで残ることがあります。フェーズ2の削除後も、レガシー側のコピーが一時的に残る可能性がある、という注意書きをガイドに入れています。
