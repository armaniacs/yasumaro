Yasumaro の AI 設定画面には「接続テスト」ボタンがあります。v6.7 系で、これを疎通確認から実推論テストに作り替えました。

## 旧テストの問題

以前のテストは、プロバイダーの `GET /models`（モデル一覧の取得）を叩くだけでした。

これで分かるのは「エンドポイントに届いて、キーが認証を通った」ことだけです。分からないこと:

- そのキーが推論エンドポイントで有効か（一覧取得だけ許可されたキーもある）
- 設定したモデル名が実在するか
- 実際に本文が返ってくるか

結果、テストは緑なのに本番の要約が空になる、という状態が起きていました。

## 実推論化

全プロバイダーで、短いプロンプトを実際に1往復させる方式に統一しました。要約と同じ経路（同じクライアント、同じパラメータ組み立て）を使います。

空応答は成功扱いしません。`hasContent` を見て、本文が返ったかどうかを明示的に判定します。

## 送受信の可視化

テスト結果に、次を表示します。

- 送信先エンドポイント
- 送信内容（prompt）
- 受信内容（response）
- エラー（error）
- モデル名
- トークン数
- HTTP ステータス

`prompt` / `response` / `error` / `hasContent` が画面に出るので、失敗したときの切り分けができます。「送ってはいるが返りが空」「そもそも 401」「モデル名が違って 404」といった区別がつきます。

## 進捗と所要時間

複数プロバイダーを優先度順にテストするとき、テスト中のプロバイダー名・モデル名・経過時間・スピナーをリアルタイム表示します。内蔵 AI のように応答が遅いプロバイダーでも、止まっているのか処理中なのかが分かります。

各プロバイダーの所要時間（秒 / ミリ秒）も結果に残します。1秒未満は `42ms` のようにミリ秒表示です（旧実装では「0.0秒」に丸められていました）。

## 優先度リストとの関係

Yasumaro は AI プロバイダーを優先度リスト（フェイルオーバー順）で持ちます。1位が失敗したら2位、というフォールバックです。

接続テストはこのリストを上から順に実行します。どのプロバイダーが使える状態で、どれがダメなのかが一覧で分かるので、「1位に設定したプロバイダーが実は死んでいて、毎回2位にフォールバックしていた」という状況に気づけます。

## 関連する修正

このテスト作り替えと同時期に、周辺のバグもいくつか直しました。

- **Gemini の空応答** — Gemini 2.5 系は thinking トークンが `maxOutputTokens` に加算されます。既定値 1000 だと通常の要約でも枠を使い切って空応答になり得ました。`thinkingBudget: 0` を指定して解消
- **接続テストの HTTP キャッシュ** — Obsidian / Gist の接続テストが `no-store` なしでキャッシュに当たり、キー失効後やオフラインでも「成功」と誤答していた問題を修正
- **リモート AI の失敗が失敗扱いされない** — `success` / `error` が呼び出し元に転送されていなかった問題を修正

## トラブルシュートの見分け方

テスト結果からの切り分け:

| 症状 | 見当 |
|---|---|
| 証明書エラー | ローカルプロバイダー（Ollama / LM Studio）の TLS 設定 |
| 接続エラー | エンドポイント URL、ポート、プロバイダーの起動状態 |
| 401 / 403 | API キー |
| 404 | モデル名 |
| ステータス 200 だが `hasContent` が false | Gemini の thinking トークン、または `maxOutputTokens` が小さすぎる |
